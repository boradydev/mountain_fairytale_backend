## Дефекты

### BUG-001 — смешанный текстовый запрос ошибочно ищется как телефон (закрыт)

- Обнаружен: 07.11.2026, ручной осмотр «История доставок → Клиенты» после seed этапа 2. **Повторно проверен владельцем во Flutter; приоритет P2 (поиск/UX).**
- Воспроизведение: `QA-CORE-00` показывает многих клиентов вместо 00; `QA-CORE-01` также показывает клиентов 10, 11, 16, 17, 18 и другие. `QA-CORE-07` возвращает 07.
- Причина (проверена в GitHub): `delivery_document_repos.py::get_history` извлекает цифры из любого запроса через `re.sub(r"[^0-9]", "", term)`; в `get_client_history.sql` полное текстовое совпадение объединено по OR с поиском по телефону `LIKE '%<digits>%'`. `QA-CORE-00` для телефонного поиска становится `00` и совпадает с телефонами `QA-TEST-00xx`. Текстовая ветка цифры не удаляет.
- Аналогично затронуты `src/feat/clients/infra/client_repos.py` (обычный поиск/обзвон) и legacy-ветка `get_history.sql`.
- Принятое правило (исправление 07.11.2026): поиск по нормализованным цифрам телефона включать **только для запроса из цифр и обычных телефонных разделителей**, содержащего хотя бы одну цифру. При наличии букв искать полную строку по текстовым полям; `QA-CORE-01` и `Ленина, 10` не превращать в телефон `01` и `10`. Чисто цифровые и форматированные телефонные запросы (например, `+7 (999) 123-45-67`) сохраняют старое поведение.
- Реализация: общая чистая `src/common/domain/search.py::extract_phone_search_digits`; оба репозитория используют её при подготовке параметров. Допустимы только ASCII-цифры и обычный пробел, `+`, `-`, `(`, `)`, `.` после strip; нужна хотя бы одна цифра, минимальной длины нет. Текстовый поиск, SQL, сортировка, пагинация и фильтры не менялись. Проверка дублей отдельно не затронута.
- Регрессии: `tests/unit/test_phone_search.py` (29 случаев) и `tests/integration/api/test_mixed_phone_search.py` (8 HTTP/SQL-проверок): все три пути, оба режима клиентов, короткие/форматированные номера, текущие/исторические реквизиты, уникальность точек, отменённые документы/самовывозы, пагинация, активность, literal `%`, `_`, обратная косая черта. Итоговый совместный прогон с прежними тестами истории, клиентов и обзвона: **80 passed**. По явному разрешению владельца в старом test_client_search_literal_details_phone_and_total изменён только входной телефон (20 синтетических ASCII-цифр вместо UUID с буквами); все его проверки сохранены. Ruff check/format — успешно.
- QA после штатного перезапуска только управляемого API: `QA-CORE-00`, `QA-CORE-01`, `QA-CORE-07` — по одной ожидаемой точке; `01` — 10 точек; `9000` (текущий) и `0000` (исторический) — по одной точке клиента00. UUID совпали с манифестом. Контрольные суммы 14 таблиц вне аудита и манифеста не изменились, прежний аудит сохранён. Обычный HTTP-вход qa_admin добавил один EmployeeLoginEvent; других записей QA-проверка не делала.
- Это **не проблема seed-данных**, этап 2 остаётся «На проверке». Исправление выполнено по отдельному заданию владельца. Владелец подтвердил корректную работу поиска во Flutter в задании финальных доработок этапа 2; дефект повторно проверен владельцем. Этап 3 не начат, коммит не создавался.
- 07.11.2026 — стабилизация полного набора после BUG-001: **646 passed, 0 failed, 0 skipped**, включая дополнительные PostgreSQL-проверки при работающем QA API на 8001; покрытие 90%. Общий генератор телефонов теперь выдаёт уникальные синтетические `+79…`, тест обзвона обходит страницы по 25 и содержит контрольные посторонние совпадения, временная инфраструктура использует атомарный bind порта 0. Все пять исходных падений устранены без изменений бизнес-кода/поиска и ослабления проверок. Локально пять случаев прошли отдельно, связанный набор — 84 passed, проблемный обзвон повторён трижды успешно. Ruff check/format изменённых Python-файлов — успешно; все 15 таблиц постоянной QA, манифест, .env.qa и состояние процесса неизменны по контрольным суммам.
