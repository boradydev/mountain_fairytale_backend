`objects.*.group` в манифесте — точная принадлежность CORE/MANUAL/SHARED.
**Общие справочники имеют имена QA-MANUAL, но являются зависимостями CORE**:
их полный список находится в `coreDependencies`. В ручных сценариях выбирать
их в новых документах, а не менять имена, ставки, активность или каталог товаров.

порчей эталона. Для изменения справочников использовать отдельные согласованные
данные; неизвестные новые справочники текущий seed консервативно отклонит.

MANUAL-клиентов можно менять. Новые MANUAL-маршруты с ними и анонимные самовывозы
seed не изменяет и не удаляет. Не включать CORE-клиентов в новые ручные документы:
это меняет эталонную историю и определяется как конфликт.

## Эталонные сценарии

Логические ключи `route0`…`route7`, `pickup0`…`pickup2` стабильны; UUID назначает
API. У документов нет бизнес-поля названия: найти их можно по дате, клиентам,
водителю и UUID из отчёта/манифеста. В маршрутах памятки точек содержат ключ сценария.

| Ключ | Сценарий |
| --- | --- |
| route0 | Пять клиентов, разные количества, обычные товары, три оплаты, разные представители и точка без представителя |
| route1 | Успешные и неуспешная точки; обычный бесплатный товар; нулевая свободная строка, две строки product8 с разными ценами, driverNote и itemId; product9 с дробной ценой |
| route2 | Две строки `1 × 1.005`: 1.01 + 1.01 = 2.02; округление только общей суммы дало бы 2.01 |
| route3 | Другой плановый день; несколько точек и способов оплаты |
| route4 / route5 | Даты старше 30 дней; разные календарные месяцы относительно anchorDate |
| route6 | После смены текущей ставки rep0 с 5% на 7.5% и деактивации rep2; исторический rep2 у клиента17, но получатель комиссии отсутствует; client18 затем деактивирован |
| route7 | Повторные заказы client0/client2, маршрут отменён и исключён из истории клиентов |
| pickup0 | Три анонимные покупки в исходном порядке, разное количество товаров и оплата, включая null |
| pickup1 | Другая дата/месяц, только обычные товары, без клиента/представителя |
| pickup2 | Отменённый анонимный самовывоз |

После сохранения документов client0 изменены имя, телефон, адрес и уточнение;
product0 изменены имя и базовая цена с 10 на 99.99. Снимки маршрутов сохраняют
исходные сведения. Комиссии ранних документов сохраняют 5% rep0 после изменения
ставки. Деактивированный rep2 имеет исторические начисления по прежним документам.

У недоставленной точки route1 исходная сумма 47.00 сохраняется, оборот и
комиссия равны нулю. Обычные товары этой точки входят в ожидаемую загрузку.
Свободные строки исключены из загрузки при любой цене; нулевая свободная строка
исключена из ожидаемых продаж, обычный бесплатный товар сохраняет количество.
PDF визуально предстоит проверить владельцу; PDF формирует Flutter,
в этом этапе сохранены данные и независимые ожидания загрузки.

## Команды

Из корня backend, `.venv` и существующая `.env.qa`:

```powershell
.\scripts\qa\qa.ps1 check
.\scripts\qa\qa.ps1 seed
.\scripts\qa\qa.ps1 seed-status
```

API должен быть запущен через `qa.ps1 start` в отдельном терминале.
В конце подготовки этапа 2 управляемый QA API оставлен работающим для осмотра.
Повторный `start` не нужен, если `check` уже успешен.

Авторизация использует `qa_admin` и первоначальный локальный QA-пароль.
Если владелец его менял, при HTTP 401 запрашивается текущий пароль скрытым вводом;
для неинтерактивного запуска допустима `QA_SEED_ADMIN_PASSWORD` только в текущем
окружении. Пароли и токены в манифест/отчёт не попадают. Версия HTTP-клиента
читается из существующего `client_compatibility.toml`.

## Манифест и независимые ожидания

Путь: `.codex-tmp/qa-seed/manifest.json`, игнорируется Git. **Не удалять эту
директорию при чистке временных файлов**: это постоянный локальный журнал набора.
Переносить/сохранять его вместе с QA-базой. Если манифест утрачен при непустой
базе, seed отказывает; нельзя удалять данные ради восстановления журнала.

Содержит версию, первую anchorDate, Git HEAD (изменения этапа ещё не закоммичены),
Alembic revision, логические ключи/UUID/группы, исходные запросы `initial`,
прочитанные состояния `saved`, первоначальные и изменённые реквизиты,
независимые `expected`, `expectedMonthly`, `clientDocuments`, `coreDependencies`,
шаги, незавершённое намерение и результат первичной проверки.

`expected.points` фиксирует суммы строк и точки, учитываемый оборот, получателя,
историческую ставку и точное начисление, участие каждой строки в продажах,
UUID строк и состояние доставки. `expected.warehouse` — количество обычных
товаров по productId, включая недоставленные точки. Отмена документа сохраняет
его собственные суммы/снимки; `expected.isActive=false` исключает их из месячных итогов.

Формулы в `seed_plan.py` не импортируют production-код: `Decimal(str(price)) ×
quantity`, затем каждая строка `quantize(0.01, ROUND_HALF_UP)`, сложение строк и
учитываемых точек. Начисление — точный оборот × ставка / 100, без округления
до копеек (актуальный контракт commissions.md). Ответ API не используется как
источник эталонной денежной суммы.

Опорная дата первого запуска **2026-11-07**; повторный запуск сохраняет её.
`createdAt` — настоящий серверный момент, отдельно от плановых дат. Через месяцы
набор не будет покрывать текущие последние 30 дней: новый набор требует отдельного
решения о его идентичности/сосуществовании, автоматического reset нет.

## Безопасность и повторный запуск

Перед каждой HTTP-записью используются существующие `load/verify` из manage.py:
фактическая БД, сервер, порт, session/current role, привилегии, владельцы,
доступность и значение read-only QA-маркера. Дополнительно проверяются Alembic head,
точный HTTP base URL `http://127.0.0.1:8001`, запрет redirect/proxy окружения,
PID/исполняемый Python/время создания управляемого процесса и `/health/ready`
с `X-QA-Run`, который подтверждает реальный engine API и его маркер.

Первый запуск разрешён только с пустыми бизнес-таблицами и отдельным qa_admin.
Неизвестные данные, конфликт версии/цели, отсутствующие или изменённые CORE и
зависимости вызывают отказ. После успешного набора разрешены новые документы,
не использующие CORE-клиентов. Все проверки перед новым наполнением выполняются
до создания бизнес-объектов. SQL используется только для чтения; все прикладные
создания, изменения, отмены и аудит проходят через HTTP API.

Повторный успешный `seed` только читает объекты, проверяет эталон и обновляет
локальные результаты проверки; прикладные POST/PATCH не выполняются.
MANUAL-карточки не сравниваются с первоначальным содержимым и не исправляются.
Сброс, миграции, `.env/.env.qa`, PostgreSQL роли/QA-маркер не изменяются.
Ограничение PUBLIC CONNECT этапа 1 сохраняется; кластерной изоляции не заявляем.

## Частичный сбой

Журнал атомарно записывается через временный файл + fsync + replace перед HTTP.
Windows OS-lock предотвращает параллельные seed/seed-status и освобождается
при завершении процесса; удалять lock-файл для продолжения не требуется.

1. Устранить причину недоступности API/ошибки генератора, сохранить журнал и БД.
2. Запустить `seed` с прежним манифестом.
3. Создание документа восстанавливается тем же `creationRequestId` штатной
   идемпотентностью API. Создание справочника/клиента — чтением по уникальной
   метке и проверкой исходных полей, затем регистрацией уже созданного UUID.
4. Прерванный PATCH/cancel сверяется GET: если целевые поля уже применены,
   записывается завершение; если состояние целиком прежнее, шаг выполняется
   штатно при продолжении. При несовместимом состоянии — отказ без перезаписи.
5. Неизвестные данные, неоднозначность, изменение CORE — остановиться и
   предоставить владельцу ключ/UUID/поле; не удалять записи, не править saved
   ради обхода проверки, не запускать reset.

Во время разработки первый pickup0 был отклонён с 422 из-за непустого route-only
memo. Подтверждено чтением отсутствие документа по creationRequestId; исправлены
план и только неподтверждённое намерение журнала. Причина сохранена в diagnostics.
Повторное продолжение сохранило UUID восьми уже созданных маршрутов.
Контракт/бизнес-логика не менялись; это ошибка входных данных генератора.

## Первичные проверки и ограничения

`seed-status` проверяет наличие каждого объекта, неизменность CORE и справочников,
UUID и состав документов, порядок покупок, анонимность, исходные снимки клиента
и товара, состояния/причины, независимые суммы строк/точек/документов через историю,
получателей/ставки/обороты/точные комиссии чтением SQL. Проверяет связь клиентов
с историей, исключение отменённых и самовывозов из клиентской истории. При чистом
наборе месячные итоги сверяются также через API комиссий. После появления ручных
документов общие месячные итоги не считаются эталонными; CORE проверяется отдельно.

Это начальная проверка подготовленных данных, не общий проверяющий этапа 3.
При дефекте приложения — зафиксировать расхождение, не исправлять бизнес-логику.

Не подготовлено различие **двух ненулевых** исторического представителя и
получателя: публичное переназначение клиентов не переписывает начисления, а
согласованное назначение отсутствующего представителя выставляет оба значения
одновременно. Подготовлен доступный штатный случай исторический rep2 / получатель
null после деактивации, без SQL-подмены. Ручная визуальная приёмка PDF/Flutter,
полная проверка поиска и ручных изменений относятся к следующим согласованным этапам.

Тесты генератора: `tests/qa/test_seed.py` используют изолированные doubles
HTTP/SQL и временные JSON-файлы; постоянная QA-база не является pytest-фикстурой.
Проверяются полный план, неправильная цель/маркер, неизвестные данные, конфликт
версии, повторы, изменение CORE/MANUAL, частичный сбой до HTTP и потеря ответа
после commit, восстановление/конфликт PATCH, независимые расчёты и манифест.
Проверки реальных идентичностей дополнительно находятся в test_environment.py.
