## Цель

Реально проверить Windows-приложение, а не только widget tests:
обнаружение версии, получение feed, native WinSparkle 0.9.2,
Ed25519-проверку, скачивание установщика, завершение приложения,
установку A→B, запуск B, повторы и отказоустойчивость.
Выяснить, что подтверждает/опровергает наблюдавшийся на старом выпуске
сбой `v1.1.2 → v1.2.0` с сообщением «нет интернета»,
**не объявляя историческую причину найденной без доказательств**.
В этом блоке **разрешено исправить S6-01** — неверную диагностику
HTTP-ответов GitHub — минимальным изменением Flutter production-кода
с регрессионными тестами.

## Особое разрешение владельца на ПК разработки

- Владелец **разрешил удалить, переустановить и обновить текущее
  установленное Mountain Fairytale** на своём Windows-ПК разработки.
  Проверка A→B может заменить реальную локальную инсталляцию.
- **Создавать резервную копию пользовательских настроек, токенов и
  авторизации НЕ нужно** — это явное решение владельца. Риск потери
  локальной сессии/настроек владельцем принят. Не притворяться,
  что сохранение сессии доказано, если локальные учётные данные недоступны.
- При этом для проверки **сохранения** настроек при нормальном обновлении
  использовать не секретные контрольные значения до/после (например,
  настройка URL, тема, окно); по возможности проверить вход/сессию,
  не печатая и не экспортируя refresh-токены. Не очищать пользовательский
  профиль специально, если сценарий этого не требует.
- Разрешение касается **только Mountain Fairytale на ПК разработки**.
  Не трогать рабочую VM, другие машины, системный PostgreSQL,
  QA/LOAD, чужие контейнеры и приложения. Не делать system-wide cleanup.
  Закрывать/удалять только подтверждённые процессы и инсталляции приложения.
- Не использовать production Ed25519 private key. Нельзя создавать
  GitHub Release/tag, менять `latest`, отправлять GHCR, менять
  backend production policy или `master`.
  **Две отдельные физические сетевые конфигурации VM-host/LAN исключены.**

## Подготовка и стратегия реального локального стенда

1. Сверить чистоту/локальные изменения Git, HEAD обоих репозиториев;
   сохранить изменения пользователя; при необходимости безопасно
   `fetch` + fast-forward, без `reset`/`stash` поверх чужого кода.
   Инвентаризировать текущую установку, запущенные процессы, версии,
   доступные инструменты, `%LOCALAPPDATA%\Programs\MountainFairytale`,
   рабочие порты и тип установленной сборки. Не читать токены/секреты.
2. Прочитать актуальные `docs/windows-updates.md`,
   `scripts/windows/{package.ps1,prepare_release.py,publish_release.py}`,
   `windows/runner/update_bridge.cpp`, `windows/installer/app.iss`,
   `lib/features/app_updates/`, экраны принудительного обновления и тесты.
   Учитывать: Dart `UpdateService.latest()` запрашивает `update.json`
   через `appcastUrl.resolve('update.json')`, native WinSparkle скачивает
   appcast/installer **самостоятельно**. Это два разных HTTP-пути.
3. Подготовить **исключительно локальные** A/B, временный Ed25519-ключ,
   подписанный installer B и `appcast.xml` с корректной подписью,
   размером и `enclosure` на `127.0.0.1`.
   `update.json` должен соответствовать B.
   Feed/установщик обслуживать из ignored каталога loopback HTTP-сервером,
   с адресом `http://127.0.0.1:<port>/appcast.xml`.
   Запретить внешний bind и запросы на production feed.
   Проверить фактическое URL-resolve для JSON и XML, MIME/HTTP,
   подпись B и точное сравнение `major.minor.patch.build`.
4. Важное ограничение **production Release/Profile native bridge**:
   он принимает только официальный HTTPS GitHub appcast;
   `http://127.0.0.1` допускается **только в DEBUG** через
   `#if defined(_DEBUG)` в native runner. Нельзя заявить, что
   обычный Release с подставленным Dart URL автоматически годится
   для локального WinSparkle-теста. Применить безопасный, реально
   работающий **debug-стенд A/B** либо другое явно изолированное
   решение. Если штатный упаковщик поддерживает только Release,
   адаптировать тестовую сборку/пакетирование в ignored каталоге,
   не ослабляя production feed allowlist и подпись.
   Документировать, какая нативная конфигурация действительно проверена.
5. Версии A/B выбрать согласованно с backend minimum `1.3.0`
   (например, тестовые `1.3.0+101 → 1.3.1+102`),
   при необходимости использовать `--build-name` и `--build-number`
   **без изменения официального `pubspec.yaml`**.
   Не публиковать тестовые версии, не создавать git tags, не подключать
   production GitHub feed. При реальном updater достаточно локального
   backend/test stub для compatibility; VM заказчика не нужна.
   Если локальная установка уже новее A, допускается её удаление
   штатным способом по разрешению владельца.
6. Для любого test Setup тщательно сверить `FileVersion`,
   `DisplayVersion`, установочный каталог, подпись тестовым ключом,
   флаги `/UPDATE=1`, mutex, установку без UAC; не отключать
   проверку подписи/сравнения версий, не обходить штатные native callbacks.

## Сценарии

- **S6-01 — диагностика.** Воспроизвести 403, 429, 500, 503,
  DNS/connect/timeout, повреждённый JSON, некорректную метаинформацию,
  нормальную 404 до первого выпуска, успешный 200 и повтор после ошибки.
  Минимально исправить код, чтобы сообщение об отсутствии интернета
  показывалось только для настоящих сетевых проблем, а HTTP-отказы
  (с кодом/понятным смыслом) и повреждённый feed отличались.
  Никаких ложных сообщений «обновлений нет» при 403/429/5xx.
  Сохранить существующие правила: не устанавливать автоматически,
  не блокировать совместимого пользователя при временной ошибке GitHub,
  не пропускать несовместимую версию backend.
  Обновить тесты 6.1, которые сейчас **закрепляют ошибочный текст**,
  и добавить регрессии для каждой ветки обработки и восстановления.
- **Нативный A→B.** Установить A, открыть приложение, выставить
  контрольные несекретные настройки, проверить кнопку/пассивную проверку,
  «Позже», подтверждение; WinSparkle должен скачать B,
  проверить реальную Ed25519, закрыть A только после безопасного callback,
  выполнить Inno Setup и открыть B. Сверить реальную версию B,
  отсутствие UAC, сохранность контрольных настроек при штатном обновлении,
  корректность исполняемых файлов. Если для действия Windows UI нужен
  человек — сообщить владельцу точную кнопку и ожидаемый результат.
- **Отказы и повтор.** Проверить недоступный feed, не-200/невалидный
  metadata, исчезновение связи во время скачивания, отмену,
  восстановление связи и повтор, отсутствие дублей/повреждённой установки,
  корректное снятие modal barrier. Отдельно проверить отказ
  подписи (подписан другой ключ или изменён файл): установка запрещена
  и существующая работающая версия остаётся целой.
  Не подменять native тесты только mock/widget-тестами.
- **Совместимость.** Проверить локально состояние
  `CLIENT_UPDATE_REQUIRED`, блокировку рабочих API,
  доступность действия обновления на экране входа и после
  несовместимого ответа. Не изменять настоящую backend policy;
  использовать отдельный stub/изолированный тестовый API.
  Тестировать сохранение токенов без их раскрытия, если доступна
  полноценная авторизованная сессия; иначе честно отметить SKIP.
- **Исторический случай.** Сопоставить исходники/артефакты
  `v1.1.2`/`v1.2.0` с нынешним путём updater, проверить
  семантическое сравнение версий, доступ к GitHub feed и native
  ошибки без догадки «сеть отсутствует». Старые условия,
  ключ/артефакт/сеть на момент инцидента могут быть невоспроизводимы;
  в таком случае обозначить это как ограничение, а не как PASS
  исторического перехода.
- **Регрессии.** Flutter analyze, автономные Flutter tests,
  release-tool tests, relevant native/integration проверки,
  а при изменениях Release-логики — локальная Windows Release сборка.
  Оценить влияние исправления S6-01 на пассивную проверку,
  совместимость и UX экранов.

## Критерии и отчёт

В `docs/qa/reports/2026-11-10-stage-6-block-3.md`:
собранные версии A/B, native build/configuration, ключи **только как
указание на тестовое происхождение** (не содержимое),
способ локальной подачи feed/installer, точные команды, что проверил
native и что только widget/mock, HTTP/WinSparkle/Inno исходы,
результаты сохранения настроек, S6-01 до/после,
границы старого инцидента, PASS/FAIL/SKIP и необходимые
ручные действия с конкретными инструкциями.

По окончании безопасно остановить **только свои** локальные HTTP-серверы,
тестовые процессы и удалить только подтверждённо свои временные ресурсы.
Тестовые инсталляции на ПК разработчика удалять/заменять разрешено;
отдельного восстановления пользовательского профиля и backup не требуется.
При FAIL сохранить диагностические артефакты вне Git.
Приложение оставить в понятном работоспособном состоянии, если возможно.

**Не начинать блок 6.4** до приёмки владельцем. Не объявлять
полную native-приёмку, если существенные реальные действия пропущены.
Коммитить Flutter-код/тесты и backend QA-отчёт на `codex/delivery-history`,
не трогать `master`; отсутствующие полномочия/GUI-шаги сообщить явно.
