## Уточнение по уже работающему production

По подтверждению владельца, **backend уже развёрнут на рабочей Ubuntu VM,
работает штатно и ранее успешно обновлялся при выпуске серверных релизов**.
Поэтому блок 6.2 — не первая проверка возможности production-деплоя и
не основание заново разворачивать или обновлять рабочую VM.
Это **локальная регрессионная репетиция** для текущей версии кода:
проверка воспроизводимости сборки, миграций, целостности тестовых данных
и восстановления из отдельной копии.

Существующая работоспособность production не доказывает, что **текущие**
миграции и сценарий восстановления проходят на чистом изолированном стенде;
эти вещи и проверяются. Полный production pull-deploy, GitHub Actions/GHCR
и доступ к рабочей VM не повторять. Не интерпретировать локальный
pg_dump/pg_restore как реальную проверку удалённого S3-бэкапа.

## Цель

На **ПК разработки** выполнить реальный (не mock) цикл:
локально построенный backend Docker-образ → отдельная PostgreSQL 17 →
Alembic upgrade head → реальный FastAPI и синтетическая запись →
pg_dump custom format → **другая пустая PostgreSQL** →
pg_restore → независимая SQL/API-сверка восстановленных данных.
Сопоставить результат с эксплуатационными инструкциями, но не запускать
настоящий production pull-deploy или S3-сервис.

Ориентиры: `compose.yaml`, `compose.build.yaml`, `Dockerfile`,
`docs/operations/backend-deploy.md`, `docs/operations/restore.md`,
`docs/operations/backups.md`, `docs/operations/first-install.md`,
`docs/qa/stages/06-release-readiness.md`.
Старый дефект диагностики Flutter updater **S6-01 не исправлять в 6.2**;
он назначен на 6.3.

## Среда и ограничения

- Работаем только на Windows-ПК разработки; Docker Desktop/Linux containers
  и локальные инструменты доступны при наличии разрешений sandbox.
  До изменений проверить `docker version/info/context/ps -a/volume ls/network ls`,
  список слушающих портов, статусы Git и состояние запущенных процессов.
- Существующие контейнеры, сети, тома и локальный PostgreSQL 5432 считать
  **чужими**. Пользователь подтвердил, что ранее удалил контейнеры Guacamole
  самостоятельно; дальнейшая инвентаризация — новая точка отсчёта.
- Использовать уникальный префикс проекта, например `mf-s62-<run-id>`,
  с рандомным run-id, отдельными именованными сетями/томами, labels ownership,
  локальным manifest созданных ресурсов в ignored `.codex-tmp/stage6-block2/`.
  Перед созданием проверять отсутствие совпадающих имён. Не усыновлять чужие
  ресурсы и не удалять что-либо только по маске имени.
- **Не запускать исходный `docker compose up` без изолирующего стенда:** его
  `compose.yaml` задаёт production-подобное имя проекта, external сеть
  observability и обычные тома. Создать отдельный ignored тестовый Compose-файл
  с явным `-p <unique-project>` либо эквивалентные `docker run`; он должен
  ссылаться только на собственные тестовые ресурсы и локальный образ.
  Для API, если нужно, bind только `127.0.0.1` на заранее проверенный
  свободный непроизводственный порт; PostgreSQL лучше без publish port.
  Запретить присоединение к рабочим сетям и использование bind-mount из
  `/opt/mountain-fairytale`, пользовательских и production-каталогов.
- Только **синтетические** пароли/ключи/данные. Не читать и не изменять
  production `.env`, секреты клиента, S3 credentials, реальные dump;
  не записывать секреты в Git/отчёты/вывод терминала.
  QA/LOAD и все существующие тестовые БД не пересоздавать.
- Docker images допускается строить/при необходимости получать для
  изолированного стенда; `docker system prune`, глобальный `compose down`,
  удаление посторонних volumes/networks и GHCR push запрещены.
  `master`, релизные теги, `deployment/production.json` не менять.

## Проверки

1. **Предварительная проверка.** Подтвердить ветку/HEAD, состояние двух рабочих
   деревьев, Docker context/daemon, список ресурсов до запуска. Зафиксировать
   собственный `run-id`, имена контейнеров, сетей, томов и образа, расположение
   лога и manifest. Если Docker недоступен из sandbox — получить целевое
   разрешение на конкретную операцию или сообщить владельцу точную ошибку.
   Не объявлять mock/локальный PostgreSQL равноценной проверкой Docker.
2. **Сборка backend.** На актуальном commit построить локальный
   `Dockerfile --target runtime` образ с правильным VCS_REF, не публиковать.
   Сверить метаданные с текущим `pyproject.toml`, migration head и commit.
   Если `docker build` требует доступа к сети, не вводить production-учётные
   данные и не заменять проверяемый образ ранее опубликованным незаметно.
3. **Первая установка.** Поднять собственную пустую PostgreSQL 17 из
   закреплённого образа, подтвердить уникальные DB/container identities.
   Из собранного backend-образа запустить реальные Alembic миграции до head.
   Проверить revision `alembic_version` независимым SQL, список таблиц,
   ограничения и повторный `upgrade head` без изменений схемы/данных.
   Никаких миграций по локальной PostgreSQL 5432, QA и LOAD.
4. **API и тестовые записи.** Запустить собственный FastAPI из этого образа;
   проверить readiness, app-info, реальную авторизацию, чтение и один-два
   представительных бизнес-сценария записи через API. Использовать небольшую
   синтетическую выборку со связями (например клиент/товар/документ),
   сравнить HTTP-данные с независимым SQL. Сохранить counts и устойчивые
   SHA-256 канонизированной выгрузки всех public-таблиц и Alembic revision
   перед backup; даты/случайные UUID сравнивать по фактически сохранённым
   значениям, не ждать фиксированных ID.
5. **Backup.** После фиксации данных сделать `pg_dump -Fc` исключительно
   собственной DB, проверить ненулевой exit code как ошибку, получить
   SHA-256 и `pg_restore --list`; сохранить файл только в ignored каталоге
   без Git. Не обращаться к Timeweb S3. Этот pg_dump/pg_restore доказывает
   локальную восстанавливаемость PostgreSQL, но **не** полный S3 pipeline.
6. **Restore.** Поднять **другую** собственную пустую PostgreSQL 17/БД,
   заранее проверить отсутствие прикладных таблиц и зафиксировать её
   identity. Выполнить `pg_restore --exit-on-error --no-owner --no-acl`
   без `--clean` / `--create`, не накатывая Alembic поверх восстановленного
   содержимого. При ошибке остановить восстановление: не выполнять
   повторный restore в частично наполненную БД; для повтора подготовить новую.
   Сверить schema head, все таблицы/counts/канонические хеши (с учётом
   возможных источников нестабильности сериализации) и репрезентативные
   связи/комиссии/документы независимо от production use-cases.
   Затем направить отдельный тестовый API к восстановленной БД и проверить
   readiness, login и чтение восстановленной записи; исходные данные должны
   оставаться неизменными.
7. **Итоги и уборка.** Проверить `docker ps/volume/network` и защищённые
   ресурсы до/после. Если всё PASS, удалить **только** ресурсы из собственного
   manifest после независимой проверки labels/ID/owner и сохранить безопасные
   логи. Если есть FAIL/неопределённое происхождение — ничего чужого не
   удалять, описать точный ручной шаг. Для собственных диагностических
   ресурсов указать их ID и состояние; не выполнять широкую очистку.

## Критерии приёмки

- Собранный локально runtime-образ и реальный API работали с независимой
  тестовой PostgreSQL, Alembic до head и повторно idempotent.
- Бэкап сформирован после записи данных, восстановлен в отдельной пустой БД,
  проверен по independent SQL; API с восстановленной БД работает.
- Ни одна чужая база/контейнер/том не была модифицирована действиями Codex;
  QA/LOAD, рабочие процессы и Docker-сервисы не затронуты.
- Результат оформлен как PASS/FAIL/SKIP с точными границами: локальная
  цепочка pg_dump/pg_restore **не приравнивается** к S3 или production deploy.
- В `docs/qa/reports/2026-11-10-stage-6-block-2.md` указать команды,
  версии/SHAs/мigrations, исходную/восстановленную сверку, сведения об
  изоляции, результаты и оставшиеся риски (без секретов и личных данных).
  Обновить `docs/qa/progress.md` до статуса «На проверке владельцем»;
  самостоятельно этап не принимать и к 6.3 не приступать.
- Код production, бизнес-правила, миграции и финансовые алгоритмы
  не менять без отдельного согласования. Проверочные скрипты/тесты и
  документацию допускается коммитить в `codex/delivery-history` при PASS;
  без merge/push в `master`, релизов и publish.

Если для запуска нужен ручной доступ к Docker, сообщить конкретную команду,
разрешение и ошибку, а не выполнять обход ограничения доступа.
