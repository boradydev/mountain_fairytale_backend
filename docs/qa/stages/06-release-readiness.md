# Этап 6 — локальная подготовка релиза

Статус: **В работе; блок 6.1 принят владельцем 10.11.2026; ближайший блок 6.2 — локальное развёртывание и восстановление**.
Этап 5 принят полностью. Известный дефект диагностики обновлений S6-01 оставлен на 6.3.
Рабочие ветки обоих репозиториев: `codex/delivery-history`.
Рабочая среда: ПК разработчика с Windows 10, Flutter, Python,
локальным PostgreSQL и Docker; CI/production не используются как испытательный стенд.

## Цель и границы

Локально проверить сборку Flutter Windows, установщик, версии и совместимость
API/Flutter, миграции, безопасное развёртывание backend на изолированном
окружении, реальное восстановление из тестового бэкапа, механизм Windows
обновлений и минимальный end-to-end smoke. Подготовить доказательства и
перечень остаточных рисков для **отдельного решения владельца о выпуске**.

Запрещено на любом блоке без отдельного разрешения: менять или останавливать
рабочую VM/API/PostgreSQL, обновлять рабочие ПК, использовать рабочий том
Docker, изменять или удалять постоянные QA/LOAD базы, создавать GitHub Release,
тег, публиковать GHCR-образ, запускать production-деплой или миграции
на неизвестной базе. `master` не менять. Проверка VM-host против LAN-клиента
**не проводится**: владелец счёл две сетевые конфигурации избыточными.

Если технический инструмент требует выполнения потенциально необратимой
операции, не пытаться автоматически «исправить» окружение: остановиться
и передать владельцу конкретное действие для ручного выполнения.
Не копировать в отчёт секреты, дампы, пароли, токены, абсолютные пути
с конфиденциальными данными и персональные сведения.

## План и контрольные точки

### 6.1 — Аудит и сборка Windows / совместимость (ближайшее задание Codex)

1. Проверить ветки, рабочие деревья, коммиты, локальные инструменты и
   доступные изолированные ресурсы. Не изменять состояние пользователя,
   включая запущенный Flutter debug. Осмотреть `docs/windows-updates.md`,
   `docs/client-api-compatibility.md`, `scripts/windows/`,
   `windows/installer/`, `windows/runner/update_bridge.cpp`,
   `lib/features/app_updates/`, workflow Flutter, `client_compatibility.toml`,
   миграции и backend-deploy runbook. Сверить версии и правила обязательного
   обновления. Отдельно отметить устаревшие сведения в документации.
2. Запустить **локально** релевантные unit/widget тесты, analyzer,
   проверки release-скриптов и версии. Если окружение позволяет —
   собрать Windows Release и per-user Setup.exe только в локальном
   игнорируемом каталоге, без установки и публикации. Проверить версии,
   необходимые DLL/ресурсы и артефакты; не использовать production Ed25519
   private key и не генерировать новый рабочий ключ.
3. Проверить сценарии совместимости: актуальный клиент/минимальная версия,
   неподдерживаемый клиент, ошибка app-info, старт и повторная проверка.
   Для старого обновления `v1.1.2 → v1.2.0` выполнить статическую
   проверку кодового пути и существующих регрессий; конкретная
   native-проверка обновления относится к блоку 6.3.
4. Записать точные команды, результаты PASS/FAIL/SKIP, локальные версии,
   невыполненные проверки, безопасные пути артефактов и обнаруженные дефекты
   в `docs/qa/reports/2026-11-10-stage-6-block-1.md`.
   При дефекте — сначала воспроизведение/объяснение; production-изменения
   и рискованные исправления согласовать отдельно.

**Граница блока 6.1:** не запускать установщик, не изменять пользовательскую
инсталляцию, не запускать реальную миграцию или restore, не делать
необратимых действий. Полный тест обновления отложен до 6.3.

### 6.2 — Развёртывание, миграции, восстановление

Блок 6.1 принят владельцем 10.11.2026. Следующий блок согласован к запуску:
[подробный локальный план и границы](06-2-local-deploy-restore.md).
На ПК разработки: собственный локально собранный backend Docker-образ,
уникальные изолированные PostgreSQL/API/сети/тома, реальные миграции,
небольшие синтетические данные, отдельный pg_dump, восстановление **в другую**
пустую базу, независимая сверка SQL и API после восстановления.
Не подключать рабочие тома/Compose-проект/observability-сеть;
не обращаться к Timeweb S3 и не трогать чужие контейнеры.

### 6.3 — Локальный Windows updater, в том числе старый инцидент

Только после принятия 6.2: проверить Dart `UpdateService`,
`UpdateProvider`, WinSparkle/Win32, feed и подпись на локальном стенде.
Воспроизвести/опровергнуть старое сообщение «нет сети» на конкретных
ошибках: DNS/таймаут/HTTP/некорректный feed, повторная попытка,
скачивание и установка, сохранение авторизации/настроек.
Отдельно проверить обязательное обновление при несовместимости backend.
Только изолированные тестовые версии A/B и тестовый Ed25519-ключ;
debug loopback feed разрешён по `docs/windows-updates.md`, Release
использует штатный HTTPS. Не публиковать test latest и не подменять
официальный feed. **Не моделировать две физические сетевые топологии.**
Реальную установку на тестовой машине проводить с владельцем и лишь
после проверки безопасности — она не входит в блок 6.1.

### 6.4 — Финальный smoke и решение о релизе

На локальной изолированной среде пройти вход, типовой маршрут, самовывоз,
клиентов, историю, комиссии/PDF, повторный запуск клиента и серверной части,
а также подтверждённые обновление и восстановление. Сопоставить сборки
с совместимостью API/Flutter. Подготовить итоговые PASS/FAIL/SKIP,
верифицированные артефакты, известные риски и конкретные ручные шаги.
Этап 6 завершает только владелец; merge/release/deploy — отдельное разрешение.

## Отчётность и процесс

- Каждому блоку — отдельное локальное задание Codex и отчёт в `docs/qa/reports/`.
- Codex самостоятельно выполняет все безопасные локальные операции в пределах
  блока, не перекладывая доступные автоматические тесты на владельца.
- Если действительно требуется ручное действие (Windows UI, UAC, права,
  секрет или установка), сообщить точно **что, где и зачем**; не продолжать
  рискованную операцию без подтверждения.
- Codex фиксирует изменённые файлы, артефакты, тесты, нерешённые вопросы,
  состояние ресурсов до/после. Коммит в `codex/delivery-history`
  только по согласованной части; без merge в `master`.
- Изолировать процессы по PID/владению, файлы — в ignored каталоге.
  Не завершать чужие процессы и не чистить общие Docker-ресурсы.
