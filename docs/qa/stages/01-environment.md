с правами SELECT/INSERT/UPDATE/DELETE/TRUNCATE для новой роли.

**Граница изоляции:** в существующем кластере действует PUBLIC CONNECT.
Поэтому роль может технически установить соединение с другими БД и читать общие
каталоги; это не даёт ей доступа к проверенным прикладным таблицам. Строгий запрет
самого CONNECT потребовал бы изменения существующих ACL или pg_hba; этого не делали.
Если владелец требует такую сетевую/кластерную границу, нужно отдельное решение.
Существующие роли и их права не изменены; ACL изменены только у новых QA-ресурсов.

## Управление из PowerShell

Из корня backend, без Poetry и без экспорта рабочей конфигурации:

```powershell
# В отдельном терминале; работает в foreground, без автоматических миграций/сброса:
.\scripts\qa\qa.ps1 start

# Во втором терминале:
.\scripts\qa\qa.ps1 check
.\scripts\qa\qa.ps1 stop
```

Скрипт использует `.venv\Scripts\python.exe -m scripts.qa.manage`.
`start` перед запуском проверяет базу/роль/маркер и свободный порт. QA-обёртка
lifespan проверяет **реальный async engine до bootstrap**, а затем engine штатного
приложения. Каждый QA `/health/ready` дополнительно сверяет реальную БД и маркер.
Ответы имеют случайный `X-QA-Run`; `check` сверяет его с текущим запуском,
чтобы не принять другой сервер на этом порту за QA. Бизнес-логика, маршруты и JWT
не подменяются; код обычного приложения не изменён.

`check` требует запущенный QA API; печатает базу, роль, сервер, статус маркера,
ревизию Alembic, расширения и live/ready. Пароли и token маркера не выводит.

`stop` сверяет PID, время создания процесса, путь Python и HTTP-идентификатор
запуска. При несовпадении/недоступности проверки — отказ. Для зависшего API
используйте Ctrl+C в его исходном терминале. Нельзя вручную подставлять другой PID.
Штатный Ctrl+C удаляет файл состояния; если процесс уже отсутствует, `stop`
убирает оставшееся состояние. PostgreSQL и обычный backend не останавливаются.
Остановка через `stop` завершает только QA-процесс принудительно; перед этим
закончите ручные действия во Flutter.

### Первичная подготовка и миграции

**На этом компьютере init уже выполнен, повторять не нужно.** На новой чистой
установке с той же локалью и свободным портом:

```powershell
.\scripts\qa\qa.ps1 init
```

Скрыто запрашивается пароль локального администратора PostgreSQL. Для явных
автоматических тестов допускается переменная `QA_PG_ADMIN_PASSWORD`, но пароль
не передаётся аргументом и не записывается в скрипты. Если БД, роль или `.env.qa`
уже существуют, init отказывает без очистки/замены. Частичный сбой оставляет
ресурсы для исследования; автоматического rollback через DROP DATABASE нет.

Применить имеющиеся миграции только после проверки QA-цели:

```powershell
.\scripts\qa\qa.ps1 migrate
```

Обёртка запускает штатный `alembic ... -x qa_guard=1 ... upgrade head` с явно переданным окружением
дочернего процесса; `.env` не получает приоритет. Выполнена вся цепочка из 18
существующих ревизий до `1e8c3a5d907b`; присутствуют `pg_trgm` и `uuid-ossp`.
Новые прикладные миграции на этапе 1 не создавались. Будущие изменения схемы
разрабатываются обычным Alembic-процессом отдельно от этого задания.

### Администратор

Один `qa_admin` создан штатным bootstrap, существование/роль прочитаны из QA-БД.
Первичный случайный пароль находится только в локальном `.env.qa`.
Предпочтительно перед ручным входом задать собственный QA-пароль:

```powershell
.\scripts\qa\qa.ps1 start
# Во втором терминале, ввод дважды скрыт:
.\scripts\qa\qa.ps1 admin-password
```

Используется существующая backend-команда смены пароля после проверки QA-базы.
Не используйте рабочие учётные данные. После смены пароля `ADMIN_PASSWORD` в
`.env.qa` остаётся первоначальным bootstrap-значением: оно понадобится только
при создании администратора в пустой схеме после отдельно подтверждённого сброса.

### Разрушительный сброс — только по решению владельца

Постоянная QA-БД **не сбрасывалась**. Для будущего сброса:

```powershell
.\scripts\qa\qa.ps1 stop
.\scripts\qa\qa.ps1 reset
# Ввести вручную: RESET mountain_fairytale_qa
.\scripts\qa\qa.ps1 start
```

Защиты: явный QA_ALLOW, фиксированная допустимая цель (не суффикс), фактические
имя/сервер/порт, роль и её права/владение, read-only маркер со случайным token,
полное текстовое подтверждение. Отсутствие любого условия блокирует операцию.
Сброс требует отсутствия управляемого процесса и других подключений к QA-БД.
Проверка и DROP SCHEMA public выполняются **в одном соединении и транзакции**.
Схема `qa_control` сохраняется; затем восстанавливается public и выполняется
`upgrade head`. При сбое миграций не начинайте ручную приёмку, устраните причину
и выполните `migrate`. Сброс не вызывается при старте API. Тестовый bootstrap
никогда не вызывается. Механизм защищает от ошибочной цели, а не от намеренного
саботажа владельцем БД/администратором PostgreSQL.

## Дополнение 07.11.2026 — независимый guard Alembic

Все пути применения миграций в QA CLI (`init`, `migrate`, `reset`) используют
единую `migrate()`. Предварительные проверки сохранены. Дополнительно команда
передаёт через argv:

```text
-x qa_guard=1
-x qa_database=mountain_fairytale_qa
-x qa_host=127.0.0.1
-x qa_port=5432
-x qa_role=mountain_fairytale_qa_app
```

Ожидаемая цель берётся из констант QA CLI независимо от `POSTGRES_*` дочернего
процесса. Пароли и секретный token не передаются через argv. `QA_MARKER` и явное
разрешение `QA_ALLOW=local-qa-only` передаются в окружении; отсутствие любого
обязательного параметра означает отказ.

Настоящий `migrations/env.py` включает guard по явному `-x qa_guard=1`.
На фактически открытом SQLAlchemy-соединении он проверяет `current_database()`,
`host(inet_server_addr())`, `inet_server_port()`, `current_user`, `session_user`
против ожидаемых значений из argv. Затем читает `qa_control.identity` и сверяет
секретный token. Отсутствующая, недоступная или пустая таблица маркера, неверный
маркер и любое несовпадение цели блокируют миграции.

Guard вызывается **до context.configure/run_migrations**, в том же соединении
и явной внешней транзакции, что и миграционные операции. Это также обеспечивает
commit успешных миграций после guard SELECT, исключая проблему autobegin/rollback.
При отказе транзакция откатывается; сообщения `QA migration guard: ...` не содержат
паролей, маркера или URL подключения. QA offline `--sql` запрещён: без реального
соединения доказать идентичность нельзя. `qa_guard=0` тоже вызывает отказ.

Если QA CLI передаст переменные подключения другой БД, аргументы `-x` сохранят
ожидаемую QA-цель: env.py откажет до миграций даже при наличии такого же маркера
в ошибочно выбранной БД. Обычные миграции без `qa_guard` сохраняют прежний путь
и не требуют QA-конфигурации или маркера. Новые прикладные ревизии не создавались,
старые не менялись; защитная функция вынесена в небольшой `alembic/qa_guard.py`,
не зависящий от QA CLI.

Дополнительные проверки находятся в `tests/qa/test_alembic_guard.py`. Они вызывают
реальный env.py в subprocess, используя новые случайные `mf_guard_probe_*` БД и
роли. Только временные тестовые ревизии делают переход наблюдаемым: изменяют
контрольную запись, создают таблицу и продвигают `alembic_version`. При каждом
отказе сверяются неизменность ревизии, контрольной записи и отсутствие новой
таблицы, в том числе в подставленной БД. Отдельный тест намеренно портит `env`
в момент запуска дочернего процесса настоящей `qa.migrate()`.
