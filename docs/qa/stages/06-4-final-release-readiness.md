## Зачем этот блок

Уже проверены QA 1–5, локальные Windows Release/Setup 6.1,
Docker/Alembic/backup/restore 6.2, реальный Debug updater A→B 6.3.
Не повторять нагрузочные испытания, аварийный TCP и весь A→B без причины:
опираться на подтверждённые протоколы и выполнять финальный
**интеграционный smoke настоящего Flutter Windows Release** против
изолированного реального FastAPI/PostgreSQL, плюс регрессии после S6-01.

Известные ограничения 6.3: **S6-01 исправлен**, **N6-01** (сам WinSparkle
неточно описывает HTTP 503 и обрыв installer) остаётся,
native сохранение реальной авторизованной сессии A→B не проверено,
настоящий Release HTTPS GitHub updater не проверялся,
историческая первопричина v1.1.2→v1.2.0 не доказана.
Переносить их в итоговую матрицу как residual/skip, не превращать в PASS.
При выявлении нового критического дефекта приостановить финальную приёмку.

## Границы и подготовка

- Начать с `git status/branch/log` в обоих репозиториях и безопасной
  синхронизации с GitHub. Сохранить чужие локальные изменения;
  не применять `reset`/`stash`/force push.
- После 6.3 на ПК разработчика установлена **тестовая Debug B 1.3.1+102**
  с временным публичным ключом и `127.0.0.1` feed/API, оба сервера
  выключены. Это не релиз. Пользователь явно разрешил удаление/
  переустановку Mountain Fairytale на **своём ПК разработки** и не
  требует backup настроек/авторизации. Проверить версию и исходное
  состояние прежде чем заменять установку. Не очищать профиль без нужды.
- Собрать `Flutter Windows x64 --release` **из актуальной ветки**,
  с `API_BASE_URL` на `127.0.0.1` тестового API; зафиксировать
  build-name/build-number, подпись, версию PE и commit.
  Обычный Release/native bridge не принимает loopback feed; не изменять
  production allowlist и **не использовать production private key**.
  Для smoke допускается Release с пустым/тестовым `UPDATE_PUBLIC_KEY`
  при выключенных проверках обновлений, либо другой безопасный
  локальный конфиг: обязательно назвать его отличие от будущего
  production artifact. Не нажимать кнопку обновления, если она
  может обратиться к публичному GitHub latest.
  При необходимости собрать локальный per-user Setup в ignored каталоге;
  устанавливать в рамках разрешения владельца, не публиковать.
- Для сценариев записи использовать **отдельную тестовую БД**, а не
  постоянные QA/LOAD, штатные pytest базы, рабочую VM или реальные
  данные. Допустим уже проверенный Docker-подход с уникальным owner/run
  label, независимой внутренней сетью и loopback API-port; не нужны
  повторная полная нагрузка или повторный backup 6.2.
  Проводить миграции лишь после проверки уникальной цели.
  Не использовать рабочий S3, GHCR-publish, production `.env`.
- Запрещены merge в `master`, GitHub Release/tag, принудительная смена
  backend minimum в production, SSH/деплой на рабочую VM, обновление
  клиентских рабочих ПК. Испытания не требуют сравнений VM-host/LAN.
  Все процессы и временные ресурсы создавать с manifest ID/owner
  и убирать адресно по подтверждённой принадлежности.

## Приоритетные проверки

### A. Финальная консистентность версий и кода

1. Проверить актуальные версии frontend/backend, schema head,
   client minimum, app-info, release tooling и commit SHA.
2. Запустить Flutter `flutter analyze`, полный автономный
   `flutter test --exclude-tags live_api` и release tools unittest;
   на backend — релевантные регрессии и полный pytest только если
   можно гарантировать изоляцию/сохранность штатных тестовых баз.
   Не запускать опасные fixture reset на чужих БД.
   При отказе от полного pytest зафиксировать конкретные основания,
   перечислить повторно использованные полные результаты этапа 5.
3. Проверить формат Windows bundle/Setup и корректную передачу
   сборочных параметров, актуальность version/commit/URL.
   Smoke на тестовой Release-сборке не объявлять равным проверке
   финального production signed artifact.

### B. Сквозной операторский smoke (Windows Release + реальный API)

На изолированном backend и синтетике пройти через настоящие Windows GUI
как минимум: старт приложения, успешную авторизацию, переход по основным
разделам, поиск/создание клиента, создание маршрута с водителем, машиной,
товаром и ценой, самовывоз (в том числе анонимный),
историю документов и клиентов, продажи/комиссию, экран PDF и печатный
preview (физическая печать не требуется), отмену/проверку
редактирования по согласованному контракту, если это быстро доступно.
Проверить независимую SQL-сверку хотя бы созданных документов,
количеств, выручки и комиссии с `Decimal`, а не только внешний UI.
Отдельно проверить совместимость API, `CLIENT_UPDATE_REQUIRED` в
локальной контролируемой политике/заглушке без изменения рабочей VM.
Если для Windows GUI нужны действия владельца, вывести короткие
конкретные шаги и дождаться их результатов; не засчитывать
невыполненные действия как PASS.

### C. Запуск после перезапуска и итоговые риски

Проверить завершение и повторный старт test Release, сохранение
контрольных не секретных настроек и сессии при перезапуске
при наличии доступной изолированной авторизации.
**Не выдавать restart login за уже выполненный native A→B auth refresh.**
Сопоставить результаты всех этапов по матрице, включая миграции,
backup/restore, обновления, экономные регрессии и UX.
Проверить, что тестовая Debug B больше не принимается за штатную
сборку; описать что установлено на ПК разработки в конце.
