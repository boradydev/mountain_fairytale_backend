# Этап 5, блок 1 — массовые данные и базовые измерения

Статус на 10.11.2026: **В работе**. Подготовлены инструменты; создание реальной
нагрузочной базы, массовый seed, замеры и ручная QA-029 ещё не выполнялись.
Конкурентное редактирование, блокировки, аварии и релиз в этот блок не входят.

## Изоляция и защита

Используется существующий PostgreSQL `127.0.0.1:5432`, отдельные
`mountain_fairytale_load`, `mountain_fairytale_load_app`, `.env.load` и API
`http://127.0.0.1:8002`. Docker не нужен. `.env`, `.env.qa`, QA-база и API 8001
не используются для записей и не останавливаются.

На реальном соединении проверяются `current_database()`, `inet_server_addr()`,
`inet_server_port()`, `current_user`, `session_user`, владелец БД, отсутствие
повышенных привилегий и членства в ролях. Уникальный случайный маркер хранится
в `load_control.identity`, схема и таблица принадлежат `postgres`;
приложению выданы только USAGE/SELECT. Маркер должен совпасть с `.env.load`.
Любое отсутствие доказательств приводит к отказу.

Alembic использует независимый `load_guard=1` на **своём** соединении в одной
транзакции с миграциями. Нельзя совмещать его с `qa_guard`; прежний QA guard
не изменён. Нагрузочная конфигурация без явного guard и offline-миграции
отклоняются. Проверка срабатывает и при унаследованном неверном имени БД.

Отдельный launcher устанавливает SQLAlchemy guard перед каждым SQL-запросом
нагрузочного API, включая создание администратора при старте. Проверяется
именно DBAPI-соединение запроса; настройки бизнес-приложения не меняются.
`/health/ready` дополнительно проверяет фактический engine. Клиент проверяет
nonce `X-Load-Run`, локальный адрес и отсутствие redirect/proxy перед записью.
Stop проверяет PID, время создания, executable, nonce и владельца порта 8002.

Единственное исключение из проверки роли/маркера — `init`: на проверенном
локальном административном соединении создаются **только отсутствующие**
роль, база и защищённый маркер. Существующие ресурсы или `.env.load` вызывают
отказ, без перезаписи, усыновления или автоматической очистки. Частичный init
требует диагностики владельцем. Пароли генерируются отдельно и сохраняются
только в игнорируемом `.env.load`; не копировать его в отчёты.

## Первый запуск — только после отдельного разрешения владельца

Из корня backend, Windows PowerShell; зависимости не устанавливаются автоматически:

```powershell
.\scripts\load\load.ps1 -Help
.\.venv\Scripts\python.exe -m scripts.load.manage --help

# После проверки защит и отдельного разрешения на создание БД:
.\scripts\load\load.ps1 init -Confirm mountain_fairytale_load
.\scripts\load\load.ps1 migrate
.\scripts\load\load.ps1 start
```

`init` запрашивает пароль локального `postgres` скрытым вводом. `start` работает
на переднем плане в отдельном PowerShell. Во втором окне:

```powershell
.\scripts\load\load.ps1 check
# Основной профиль — только после разрешения на массовое наполнение:
.\scripts\load\load.ps1 seed -Profile main -Seed 20261110 -BatchSize 25 -Rate 5
.\scripts\load\load.ps1 seed-status -Profile main
.\scripts\load\load.ps1 verify -Profile main
.\scripts\load\load.ps1 benchmark -Profile main -Requests 20 -Concurrency 1
.\scripts\load\load.ps1 benchmark -Profile main -Requests 20 -Concurrency 2
.\scripts\load\load.ps1 report
.\scripts\load\load.ps1 stop
```

`check` требует работающий API и актуальную схему. `seed-status` читает журнал
и проверяет окружение; полная сверка данных — отдельная команда `verify`.
`report` читает локальные результаты, не подключаясь к PostgreSQL.

## Профили и наполнение

| Профиль | Клиенты | Документы | Точки | Строки товаров |
| --- | ---: | ---: | ---: | ---: |
| main | 1 000 | 5 000 | 15 000 | 30 000 |
| high | 5 000 | 20 000 | 60 000 | 120 000 |

Плановые даты фиксированы: 01.01–31.12.2026; seed по умолчанию `20261110`,
версия генератора `load-v1`. Детерминированы входы и распределение, UUID и
`createdAt` выдаёт настоящий API. Первые 300 документов имеют дату 15.06.2026
и создаются последовательно с разным временем. В июне есть 50+ документов
и точек для прокрутки, включая историю первого клиента.

Каждый документ содержит три точки по две товарные строки. Каждый десятый —
анонимный самовывоз, остальные — маршруты с несколькими клиентами. Есть
недоставки с причинами, памятки, свободные цены и нулевые цены, три способа
оплаты, представители и сотрудники со ставками. Каждый 17-й документ
отменяется. Последние 10% клиентов не имеют заказов; каждый десятый клиент
деактивируется после наполнения. Имя/адрес первого клиента и ставка
представителя меняются **после** создания документов для проверки снимков.
Данные синтетические; телефоны имеют префикс `LOAD-PHONE-`, реальные номера
не используются. Ожидаемая активность и количество заказов воспроизводимы.

Все бизнес-записи создаются штатным HTTP API: валидация, аудит, клиентские и
комиссионные снимки сохраняются обычным способом. Пакетной SQL-генерации нет.
Переиспользуются QA-каталоги, Decimal-ожидания, HTTP create, UUID idempotency,
восстановление неизвестного результата POST, атомарное сохранение и OS lock.
Поведение `qa.ps1` и QA-генератора не меняется.

Один POST за раз, по умолчанию до пяти бизнес-запросов/с, не более десяти;
проверочные `/health/ready` добавляются перед записью. Каждые 25 документов
пауза и контрольная точка; допустимый размер группы 1–100. Полное наполнение
и сверка могут занять десятки минут. Закрытие окна не сбрасывает данные.

Журнал: `.codex-tmp/load/manifest.json` и отдельные `objects/*.json`.
Манифест содержит профиль, seed, версию, диапазон дат, количества, ожидаемый
оборот и SHA-256 входов. Отпечаток поколения базы запрещает повторное
использование журнала с другой базой того же имени. Нужен весь каталог,
а не один manifest. Он сохраняется на локальном диске вне Git.

После прерывания повторить **ту же** команду с теми же profile/seed:
завершённые ключи не создаются повторно; неизвестный POST документа
повторяется с тем же `creationRequestId`; каталог сверяется по уникальному
синтетическому имени и полям. Конфликт/неоднозначность вызывают отказ.
Прерванная мутация сравнивается с сохранённым before/desired. Завершённый
seed при повторе не пишет бизнес-данные; актуальность проверять `verify`.
Не редактировать набор вручную до измерений и сверки.

Повышенный профиль **не запускается автоматически**. Профиль/seed журнала
нельзя сменить поверх существующего набора. После main сохранить отчёт,
получить отдельное разрешение на очистку **только load** и выполнить:

```powershell
.\scripts\load\load.ps1 stop
# Разрушительная команда: только с отдельным разрешением владельца!
.\scripts\load\load.ps1 reset -Confirm mountain_fairytale_load
.\scripts\load\load.ps1 start
# В другом окне, отдельно разрешённый повышенный профиль:
.\scripts\load\load.ps1 seed -Profile high -Seed 20261110 -BatchSize 25 -Rate 5
.\scripts\load\load.ps1 seed-status -Profile high
.\scripts\load\load.ps1 verify -Profile high
.\scripts\load\load.ps1 benchmark -Profile high -Requests 20 -Concurrency 1
.\scripts\load\load.ps1 benchmark -Profile high -Requests 20 -Concurrency 2
```

## Независимая сверка и QA-029 API

`verify` требует завершённого набора. Сверяет фактические количества объектов
и UUID, все внешние ключи публичной схемы через anti-join, связи и содержимое
документов/точек/строк, снимки реквизитов, сохранённые ставки представителей
и сотрудников, анонимность самовывозов. Деньги считает независимо через
`Decimal`: HALF_UP до копеек **каждой строки**, сумма доставленных точек,
комиссия точно `turnover * rate / 100`. Production-алгоритмы для ожиданий
не вызываются. Активный месячный отчёт продаж сравнивается с суммой входов;
отменённые документы и недоставки из оборота исключены.

Пагинация идёт до пустой страницы с шагом 50. Каждая страница и `total`
сравниваются с независимым порядком из журнала: дата DESC, время создания
DESC, UUID документа DESC, затем position и UUID точки ASC. Проверяются
все документы с отменёнными и без них, все точки, июнь, оба типа документов,
поиск по имени/адресу/цифрам телефона после полного прохода предыдущего
набора. Это обнаруживает пропуски, дубли и нестабильный порядок при равных
плановых датах. При ошибке выводится идентификатор/поле, expected и actual.
PASS автоматической QA-029 допустим только после реального `verify`.

## Измерения

`benchmark` выполняет реальные HTTP GET: клиенты, поиск по трём полям,
история клиентов и страницы 2/3, история документов с календарём и типом,
полный маршрут с товарами, продажи июня, все справочники конструктора.
Перед каждым сценарием два прогревочных запроса, не входящих в статистику.
Измеряемых запросов 1–100 на сценарий, concurrency 1–4; начать с 1 и 2.
Это короткая контролируемая нагрузка, без стресс-тестирования.

Сохраняются число/успехи запросов, типы ошибок (HTTP, транспорт, attestation,
schema), min/p50/p95/max в миллисекундах и запросы/с по полному измеряемому
интервалу. p95 — nearest rank; при 10–20 запросах он ориентировочный.
При доступном Get-Process: CPU seconds/% одного ядра, текущий WorkingSet
управляемого API. Это не CPU PostgreSQL и не пик RAM; короткие интервалы
могут давать шумные значения. Проверяется время создания PID.

Результаты: `.codex-tmp/load/verification.json`, `benchmark.json` и
неперезаписываемые `benchmark-<timestamp>-c<N>.json`. Каталог уже исключён
из Git правилом `.codex-tmp/`; `.env.load` — правилом `.env.*`.
В репозиторий переносить только краткий обезличенный итог, без журналов,
паролей и токенов. Не устанавливать SLA до реальных замеров. Сравнивать
одинаковые profile/seed, версию кода, машину и фоновые процессы; SQL guards
добавляют накладные расходы, это часть данного защищённого baseline.

## Короткая ручная проверка Flutter Windows

Только после seed и `verify`. Нагрузочный API должен работать на 8002:

```powershell
Set-Location D:\AndroidStudioProjects\mountain_fairytale
flutter run -d windows --dart-define=API_BASE_URL=http://127.0.0.1:8002
```

1. Войти как `load_admin`, пароль взять локально из `.env.load`, не публиковать.
   Перед входом проверить в настройках сервера именно `http://127.0.0.1:8002`:
   сохранённый ранее адрес имеет приоритет над `--dart-define`. При необходимости
   явно выбрать 8002 в диалоге настроек; после проверки вернуть обычный QA-адрес.
2. Открыть историю клиентов за июнь 2026. Прокрутить ниже 50 и 100 строк:
   следующая страница загружается автоматически, строки не повторяются.
3. Сверить `total` с соответствующим GET `/protected/client-delivery-history`
   через локальный API; при необходимости открыть журнал результата verify.
4. После прокрутки изменить диапазон, выполнить поиск `LOAD Клиент 00000`,
   затем `LOAD Синтетическая улица 00000` и `00000000`. Старые страницы
   не подмешиваются; повторно прокрутить результаты ниже 50 строк.
5. Открыть историю документов за июнь, проверить тип маршрут/самовывоз,
   отменённые, поиск, прокрутку. У документов 15.06 сохраняется порядок
   по времени создания при уходе назад и повторном открытии истории.
6. Открыть полный маршрут и отчёт продаж июня, убедиться в отзывчивости UI.

Зафиксировать профиль, версию Flutter/backend, действия и наблюдения.
Ручная QA-029 остаётся **PENDING OWNER**, пока владелец не подтвердит PASS.
Никакие автоматические результаты не заменяют настоящую прокрутку Flutter.

## Очистка и ограничения

Обычные команды ничего не сбрасывают. Только `reset -Confirm mountain_fairytale_load`
при остановленном API и отсутствии других сессий проверяет фактическое
соединение и в одной транзакции очищает бизнес-таблицы **этой** БД.
Схема, ревизия Alembic и защищённый маркер сохраняются; старый локальный
журнал и отчёты перемещаются в `.codex-tmp/load/archives/`.
После прерванного reset другие команды заблокированы до диагностики
и повторной явной команды reset. Саму БД/роль инструмент не удаляет.

В этом задании реальные init/reset/seed/migrate/start/benchmark не запускались.
Проверены безопасные тесты с поддельными соединениями/HTTP; интеграционный
прогон настоящего load API и PostgreSQL ещё предстоит после разрешения.
Нет результатов производительности и вывода о готовности к нагрузке.
Этап 5 не завершён; сетевые отказы и несколько операторов — отдельные блоки.
