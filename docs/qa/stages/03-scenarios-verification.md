Инструменты и автоматические проверки готовы. Завершение возможно только

## Запуск

Из корня backend в PowerShell, при работающем управляемом QA API:

```powershell
.\scripts\qa\qa.ps1 check
.\scripts\qa\qa.ps1 scenario-prepare QA-001
# Выполнить действия во Flutter по выданной инструкции
.\scripts\qa\qa.ps1 scenario-verify QA-001
.\scripts\qa\qa.ps1 scenario-status
```

Далее те же prepare/verify для QA-002, QA-003. QA-004 независим и может
выполняться первым или последним. Во время одного подготовленного сценария
не создавать другие документы того же типа. Для доставки дата 08.11.2026,
для самовывоза 09.11.2026; это плановые даты, а не даты создания.

## Архитектура и безопасность

`scripts/qa/scenarios.py` разделяет `Live` (защищённое чтение HTTP/SQL),
`Runner` (состояние цикла) и `Checks` (expected/actual с путями полей).
CLI использует прежние проверки фактической БД, роли, адреса, порта,
QA-маркера, head миграций, PID/executable/start-time и nonce управляемого API.
Затем проверяет stage2-v1, снимки CORE и справочников, состав активных
получателей, цены, ставки, назначения представителей и способы оплаты.
Финансовые снимки CORE дополнительно сверяются SQL с seed-манифестом.

SQL-соединение сценариев работает в READ ONLY; снимки собираются в
REPEATABLE READ. Сценарии используют только GET бизнес-API. Авторизация
через POST login может добавлять `EmployeeLoginEvent`; это не бизнес-событие
сохранения документа. Журнал не содержит пароль, password_hash или JWT.
Пароль берётся существующим механизмом QA из окружения/.env.qa.

Prepare и verify не создают, не исправляют, не отменяют документы,
не меняют справочники, не запускают seed/reset/migrate. Seed-манифест
открывается только для чтения. Общая seed-блокировка исключает параллельную
запись манифеста CLI; отдельная блокировка защищает журнал сценариев.

## Что сравнивается

| Источник | Проверки |
| --- | --- |
| GET документа | Плановая дата, активность, водитель/машина/пробег, порядок точек, товары, снимки, оплата, UUID, revision |
| PostgreSQL | Исходные строки документа/точек/товаров; исторические снимки; точные NUMERIC ставок, оборота и комиссий представителей/сотрудников; события аудита |
| История документов | Единственное вхождение UUID, сумма документа |
| История клиентов | UUID точек/строк, снимки, суммы каждой строки и полной точки, сумма документа; отсутствие покупок самовывоза |
| latest-order | После QA-003 — последний подходящий активный доставленный непустой маршрут по created_at/document UUID/point UUID |
| Отчёт продаж | Независимый расчёт всего дня из SQL, общая сумма/количество и пары способ оплаты/товар |
| Снимок CORE | Неизменность CORE-клиентов, документов, дочерних строк, начислений, существующего аудита и общих справочников (пробег машины допускает штатное изменение) |

Готовые суммы строк и документов в SQL не хранятся. Они рассчитываются
независимо: `money(price * quantity)` для каждой строки (`Decimal`,
`ROUND_HALF_UP`, 0.01), затем сумма строк/точек; недоставленная точка имеет
полную собственную сумму, но нулевой оборот. Комиссия равна точному
`turnover * rate / 100`, без округления до копеек. Используются чистые
формулы `scripts/qa/seed_plan.py`, без импортов production-расчётов.

Перед PASS повторный SQL-снимок исключает смешение разных состояний при
параллельном сохранении. Длительная активная работа другого оператора может
дать диагностический FAIL stableRead; повторить verify после окончания записи.

Товарная сводка загрузки формируется во Flutter/PDF, отдельного backend
endpoint нет. Проверяющий подтверждает сохранность исходного набора обычных
товаров, включая недоставленную точку. Внешний вид и сам PDF проверяет человек.
PASS данных не означает визуальную приёмку интерфейса.

## Журнал и повторные запуски

`.codex-tmp/qa-scenarios/journal.json`, `schemaVersion=1`, массив `cycles`.
Каждый цикл хранит UUID, QA-идентичность с SHA-256 маркера, время и `runs`.
У запуска: runId, номер сценария, preparedAt, status, before (SQL-снимок),
core, catalogs, manifestHash, beforeDocument, plan, expected, documentId,
lastVerification (время, API/SQL и все проверки), confirmedDocument,
confirmedAt и диагностика `errors` при прерывании чтения.

Атомарная запись: временный файл, flush/fsync, replace под OS-блокировкой.
Падение до replace оставляет предыдущий полноценный журнал; временный файл
не является подтверждённым результатом. После закрытия терминала повторить
verify. Если prepare не опубликовал журнал, повторить prepare **до** действий
во Flutter. Повреждённый JSON или неизвестная версия не исправляются автоматически.

Повторный prepare того же сценария отказывает. Повторно увидеть точные
значения и маркер можно без новой подготовки:

```powershell
.\scripts\qa\qa.ps1 scenario-status QA-001
```

Повторный успешный verify неизменившегося документа оставляет журнал
побайтно прежним. Авторизация при этом может добавить отдельное событие входа.
Предыдущие confirmedDocument/confirmedAt сохраняются и после последующего FAIL.
После следующего шага проверка прежнего состояния сообщает HISTORICAL PASS,
не объявляя прежнюю ревизию текущим PASS. Статус предупреждает о последующем шаге.

Документ QA-001 идентифицируется как ровно один новый UUID доставки относительно
before и по точному маркеру `QA-001 run=<UUID>` в памятке первой точки.
QA-002/003 используют уже сохранённый UUID и снимок предыдущего PASS.
В самовывозе Flutter не даёт памятку: QA-004 требует ровно один новый UUID
самовывоза относительно before и полное совпадение даты/покупок/оплат/аудита.
По одной дате или сумме поиск не выполняется. Несколько новых документов — отказ.

Явный новый цикл (старые записи и документы сохраняются):

```powershell
.\scripts\qa\qa.ps1 scenario-prepare QA-001 -NewCycle
# Или начать независимым QA-004
```

Это явно архивирует текущий цикл, даже если он не завершён; никакой очистки
БД нет. Старые циклы остаются в `cycles`, последним считается активный.
При смене QA-идентичности существующий цикл не используется — нужен NewCycle.
Во всех случаях новая подготовка проверяет фактическую QA и stage2-v1.
Не применять NewCycle как автоматическое лечение дефекта: сначала сохранить
диагностику и согласовать дальнейший ручной цикл.

При FAIL не удалять документы и журналы, не запускать reset/seed и не
исправлять SQL. Сохранить путь проверки, UUID, expected/actual и визуальные
наблюдения, передать владельцу/разработчику. Сетевой сбой — повторить verify;
бизнес-запись при повторе не выполняется.
