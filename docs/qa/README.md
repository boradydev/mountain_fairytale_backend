# QA-приёмка «Горной сказки»

Дата согласования стратегии: 06.11.2026.  
Статус: **этапы 1–3 — Завершены; этап 4 — В работе (блоки 1–4 приняты 09.11.2026; проверка подгрузки истории после 50 записей отложена до этапа 5)**.
Проекты: [backend](https://github.com/boradydev/mountain_fairytale_backend/tree/codex/delivery-history) и [Flutter Windows](https://github.com/boradydev/mountain_fairytale/tree/codex/delivery-history).  
Рабочие ветки: `codex/delivery-history` в обоих репозиториях.

## Назначение

Создать воспроизводимый QA-набор для проверки коммерческого приложения перед
приёмкой и выпуском, а затем повторно использовать его при разработке новых
функций. Проверяем не только код и API, но и полный сценарий оператора:
**данные → действия человека в Flutter → автоматическая сверка результата**.

Это единый источник истины для QA-стратегии. Во Flutter хранится
[ссылка на него](https://github.com/boradydev/mountain_fairytale/blob/codex/delivery-history/docs/qa/README.md),
а не независимый дублирующий план. Статусы — в [progress.md](progress.md).
Исходные требования: [итоговый реестр заказчика](../contracts/client-requirements-completion-2026-11.md).

## Исходные возможности и принципы

- Среда разработчика: Windows 10, локальная PostgreSQL, FastAPI с запуском
  напрямую, собираемый Flutter Windows; доступны WSL и Docker.
- В backend уже есть pytest, отдельные тестовые БД с Alembic и фикстуры.
  В Flutter есть widget- и live-тесты с настоящим HTTP backend.
- Не создаём ещё один сервер PostgreSQL или Compose без обоснованной потребности:
  способ изоляции окончательно выбирается на этапе 1 по результатам аудита.
- Выделяем QA-базу и отдельные настройки API/учётные записи. Предлагаемое имя
  базы `mountain_fairytale_qa`, окончательно фиксируется на этапе 1.
- QA-база долговечна в пределах ручного сценария; обычный pytest может
  пересоздавать собственные базы, но не должен сбрасывать QA-данные.
- Для сумм, округлений и комиссий ожидаемые значения вычисляет **независимый**
  проверяющий с `Decimal` и явно заданными правилами, а не повторно вызванный
  производственный расчёт.
- Тестируем backend и базу автоматически, Flutter — в основном руками по
  воспроизводимым инструкциям. Полная роботизация Windows UI не является целью
  начального QA-набора.

## Шесть этапов

| Этап | Цель и объём | Критерий завершения |
| --- | --- | --- |
| **1. Аудит и QA-среда** | Проверить существующие тесты, миграции, PostgreSQL, API, Flutter, Docker/WSL; выбрать минимально сложную изоляцию; организовать запуск и безопасный сброс только QA-данных | Flutter подключается к QA API; миграции применяются только к QA; опасные операции проверяют явную цель; рабочие базы не изменены |
| **2. Детерминированные данные** | Seed клиентов, сотрудников, представителей, автомобилей, товаров, оплаты, маршрутов, самовывозов и исторических/пограничных данных | Набор повторяем, маркирован и имеет манифест исходных данных и ожидаемых значений; повторный запуск не порождает неконтролируемые дубликаты |
| **3. Сценарии и автоматическая сверка** | Описать QA-001…: ручные шаги Flutter, подготовленные входные данные, контрольные точки; сверка API/SQL, сумм, комиссий, снимков и аудита | Минимум один полный цикл «seed → ручное действие → PASS/FAIL» воспроизводим; ошибки содержат ожидаемое/фактическое и идентификаторы |
| **4. Функциональная приёмка** | Маршруты, самовывозы, цены, итоги, комиссии, клиенты, история, PDF, темы, геометрия UI | Согласованные критические сценарии пройдены вручную и автоматически; дефекты либо исправлены и повторно проверены, либо явно зафиксированы и согласованы |
| **5. Нагрузка и аварии** | Массовые данные, поиск/пагинация, несколько операторов, edit lock, обрывы сети, перезапуск API, неопределённый ответ сохранения | Получены измерения и проверены инварианты данных и восстановления; известные ограничения документированы |
| **6. Подготовка релиза** | Совместимость API/Flutter, миграции и восстановление из копии БД, сборка Windows, обновление, итоговый smoke-тест | Подготовлены отчёт и список остаточных рисков для решения владельца; production-изменения и релиз только по отдельному разрешению |

**Этапы строго последовательные по приёмке**, но инструменты и тесты могут
переиспользоваться. После каждого этапа владелец смотрит результаты и
явно согласует следующий. Codex не должен самостоятельно начинать все шесть
этапов по одному заданию.

## Правила безопасности

1. **Никаких разрушительных операций в рабочей или неизвестной БД.**
   Перед очисткой требуется независимая проверка фактического имени БД,
   подключённого хоста/порта, явный QA-маркер окружения и подтверждение
   оператора. Нельзя полагаться лишь на переменную окружения или суффикс имени.
   Для неизвестной цели — отказ от операции.
2. Существующий `tests/integration/db_helpers.py::bootstrap_test_database`
   выполняет `DROP SCHEMA public CASCADE` в целевой тестовой БД. Не применять
   этот механизм к QA или production без отдельного согласованного
   безопасного решения.
3. QA FastAPI должен быть явно направлен в QA-базу; рабочий `.env` не
   перезаписывать. Пароли, токены, ключи, дампы, личные данные и большие логи
   не помещать в Git.
4. Существующие Flutter `test/live/` могут создавать записи, а отменённые
   документы и аудит сохраняются. Не запускать такие тесты против production
   или неизвестного API.
5. Для тестирования пользоваться синтетическими данными. Если понадобятся
   копии реальных данных, отдельно решить вопросы обезличивания и хранения.
6. Все сбои сети и падения сервера в этапе 5 проводить только в QA-окружении.
   Не изменять service/volume/compose общего или рабочего стека.
7. Устранение дефектов допускается в рамках согласованной задачи, но любые
   изменения бизнес-правил, миграций, финансовых расчётов и механизма сохранения
   заранее согласовать с владельцем; закрывать дефекты регрессионным тестом.
8. Обычный релиз, обновление серверов, применение production-миграций,
   создание релизных тегов и публикация артефактов — **отдельные действия**.

## Организация работы с Codex

1. Обсудить подробный план **только ближайшего этапа** и утвердить границы.
2. Передать Codex отдельное задание на этап, не на весь проект.
3. Codex реализует инструменты/скрипты, запускает доступные проверки и
   предоставляет список изменённых файлов, результаты и ограничения.
4. Владелец выполняет предусмотренные ручные действия и оценивает UX/PDF.
5. При ошибке: зафиксировать воспроизведение → определить причину →
   исправить с нужным согласованием → добавить регрессионный тест →
   повторить сценарий.
6. Обновить [progress.md](progress.md), приложить короткий отчёт, согласовать
   переход к следующему этапу.
