# QA-036 — независимая проверка и базовые нагрузочные измерения

Дата: 10.11.2026. Ветка: `codex/delivery-history`. Профиль `main`,
генератор `load-v1`, seed `20261110`.

**QA-036: автоматические проверки PASS.** Ручная прокрутка Flutter после
50/100 элементов (QA-029) остаётся **PENDING OWNER**. Этап 5 целиком не завершён.

## Причины расхождений и исправления

1. Сохранено предыдущее исправление телефонной ветки: смешанный запрос
   `LOAD Клиент 00000` не должен превращаться в телефон `00000`.
   Ранее это давало 1713 вместо 255 записей клиентской истории.
2. Верификатор ошибочно переносил совпадения исторических точек в историю
   документов. Теперь независимые правила разделены: клиентская история
   использует текущие реквизиты и снимок конкретной точки; legacy-история
   документов — только текущие имя, адрес и телефон связанного клиента.
   Уточнения доставки в legacy-поиск не входят. Один документ включается один раз.
   Ожидания вычисляются из входов и журнала генератора, без production-поиска
   и без использования ответа проверяемого API как источника ожиданий.
3. После исправления истории повторный полный verify обнаружил ложное
   расхождение цены. Точное воспроизведение: документ
   `01a1c26c-6ed7-767b-b9bf-c574e954f3df`, строка
   `01a1c26c-6ee0-7ce5-8911-34c32e35d7ff`, поле `price`:
   `Decimal('1.005')` против
   `Decimal('1.00499999999999989341858963598497211933135986328125')`.
   Контракт `delivery_document.md` сохраняет JSON number для цены полного GET.
   Виновато преобразование `Decimal(float)` в верификаторе; теперь используется
   `Decimal(str(value))` без округления и допусков. Реальное отличие цены на 0.001
   по-прежнему отклоняется. Финансовые алгоритмы приложения не менялись.
4. Штатная авторизация load-команд через POST login записывала событие входа.
   Для check/seed-status/verify/benchmark добавлена авторизация без записи:
   guard соединения, SELECT существующего активного администратора,
   проверка его пароля и локальный access token с действующим LOAD-секретом.
   POST login не вызывается; HTTP/SQL защиты сохранены. Seed сохраняет прежний login.
5. В бенчмарке исправлен отсутствующий `/protected/employees` на контрактный
   `/admin/employees`. Поиск клиентов по старым имени/адресу client0 после его
   переименования возвращал бы пустой результат: сценарии теперь берут текущие
   имя/адрес/цифры телефона из сохранённой карточки генератора.

На этой машине LOAD API первоначально отсутствовал. Перед его запуском
подтверждено наличие активного администратора, поэтому bootstrap не создавал
учётную запись. Запущен только изолированный API 127.0.0.1:8002;
существующие API не останавливались. Дефектов production-логики не обнаружено.

## Сохранность данных и ограничения

До запуска API и проверок сохранены SHA-256 отсортированных JSON-строк
всех 15 таблиц public LOAD, включая аудит и сотрудников. После verify и обоих
бенчмарков количество строк и контрольные суммы всех таблиц совпали.
SHA-256 manifest и 6023 файлов objects генератора также совпали (6024 файла).
Отпечатки снимались в read-only SQL-транзакциях; верификатор использовал SELECT и HTTP GET. Журналы не менялись.
Локальные доказательства: `.codex-tmp/load/qa036-data-before.json`,
`qa036-journal-before.json`, `verification.json`, оба архивных benchmark JSON,
`qa036-report-command.txt`. Секреты и журналы генератора в Git не включены.

Не выполнялись init/seed/reset/migrate, изменение QA/LOAD данных, production
FastAPI/SQL/Flutter, финансовых правил или защит PostgreSQL, high, стресс и релиз.
LOAD API оставлен на 8002 для последующей ручной проверки владельцем.
Ручная QA-029 прокрутка Flutter всё ещё PENDING OWNER. Перемежающиеся
Windows-блокировки временных файлов расширенного pytest остаются замечанием среды.
