## Обязательное обновление и старый инцидент

Существующие тесты проверяют блокировку до bootstrap, реальные заголовки всех
методов/auth/long polling, 409 CLIENT_UPDATE_REQUIRED без refresh/logout,
сохранение токенов, прекращение рабочих запросов, сброс форм, повтор после
недоступного app-info и сохранение блокировки после неудачного повтора/отмены.
Сеть и обычные 400/409 не выдаются за требование обновления.
Отсутствующий/повреждённый app-info не разрешает старт работы.

Updater использует независимый GitHub HTTP-клиент, timeout 15 с, допускает
404 как отсутствие первого выпуска, отвергает не-200, повреждённые и чрезмерные
metadata. Пассивная проверка не вызывает установку; пользователь подтверждает
её отдельно. Открытый редактор блокирует запуск; native modal barrier снимается
после dismiss. Callback-и WinSparkle доставляются через PostMessage на UI thread.
Setup работает с `PrivilegesRequired=lowest`, ждёт running mutex до 10 с,
не завершает чужие приложения, запрещает downgrade по DisplayVersion и сохраняет
профиль. Нативное выполнение этих защит здесь не заявляется.

Для `v1.1.2 → v1.2.0` прочитаны именно локальные теги:
`v1.1.2:windows/runner/update_bridge.cpp` уже передаёт WinSparkle полную
`MAJOR.MINOR.PATCH.BUILD`, а `v1.2.0:scripts/windows/prepare_release.py`
формирует ту же четырёхкомпонентную `sparkle:version`. Dart-регрессия усилена
точным переходом `1.1.2+65535 → 1.2.0+20`: PASS. Гипотеза о сравнении только
build number этими исходниками не подтверждается. Это не проверка бинарника,
который реально стоял у владельца, его ключа, сети, appcast и installer того дня.
Причина исторического отказа **не установлена**, native-проверка остаётся 6.3.

### S6-01 — недостоверная диагностика updater (открыт)

Воспроизведение: MockClient возвращает HTTP 403, 429, 500 либо 503 на штатный
`/releases/latest/download/update.json`; `UpdateProvider.check()` показывает
«Не удалось проверить обновления. Проверьте подключение к интернету.» при
полученном HTTP-ответе. Причина: `UpdateService.latest()` превращает не-200
в FormatException; `UpdateProvider.check()` ловит все исключения одним catch
с одинаковым текстом. Повреждённый JSON также попадает в этот catch.

Это дефект диагностики, а не доказанный обрыв сети; он может объяснять текст
исторического сообщения, но не его первопричину. Блокирующее требование версии
при этом не обходится; повтор после восстановления HTTP работает.
Новые тесты фиксируют текущее поведение и recovery, production-код не менялся.
Для исправления нужно отдельно согласовать различение HTTP/feed/network причин
и затем заменить assertion на корректный текст; до исправления дефект открыт.

## Решение по блоку

Локальная Windows build/package цепочка воспроизводима и прошла проверки в
границах 6.1. Технических препятствий подготовке отдельного блока 6.2 не найдено.
Это не готовность к production: S6-01 открыт, документация требует актуализации,
настоящие миграции/restore/native updater и финальный smoke ещё не проверены.

Изменения: этот отчёт и запись progress в backend; во Flutter только два
updater-теста. Production-код, зависимости, миграции, настройки и workflow не менялись.
Коммиты и push не выполнялись; diff оставлен для просмотра.
Обязательных ручных действий с установщиком сейчас нет. Владельцу необходимо
принять отчёт 6.1 и отдельно определить дальнейшую работу с S6-01/блоком 6.2.
