## Принятые, но не закрытые ограничения

| Риск | Решение |
| --- | --- |
| **N6-01**, неточные сообщения WinSparkle при XML 503 и обрыве installer | Неблокирующий для выпуска: безопасный отказ и повтор доказаны; улучшение диагностики — отдельная задача |
| Исторический сбой обновления v1.1.2→v1.2.0 | Точная первопричина **не установлена**; не обозначать как устранённую |
| Авторизация при **native A→B** | **SKIP**: проверен restart текущего Release, но не авторизованный native upgrade; риск требуется учитывать при приёмке production-обновления |
| Реальный Release HTTPS feed, production Ed25519 и опубликованный installer | Локальные тестовые подписи/Debug updater не заменяют **штатные проверки CI/sign/hash/appcast** при реальном выпуске |
| S3 и production VM | Локальный restore проверен; актуальная production S3-цепочка здесь заново не тестировалась; backend VM ранее работала штатно по сообщению владельца |
| Чистый клиентский ПК, отдельные LAN-топологии, остановка ОС/PG/электропитания | Не проверялись в указанных условиях; см. отчёты 5/6 |
| Отложенный UX QA-020, общий Ruff backlog | Не блокировали QA; остаются отдельными задачами |

Ни одна из перечисленных границ не должна автоматически превращаться
в PASS при оформлении будущего production-релиза. Новых критических
сбоев данных, комиссий, сохранения или штатного restart в 6.4
не выявлено.

## Gate перед фактической публикацией и деплоем

Перед каждым **отдельно разрешённым** действием выпуска:

1. Сверить актуальные ветки, версии и diff к `master` в обоих репозиториях;
   выполнить штатные CI/checks после merge. Проверить, что в релиз не попал
   тестовый loopback API URL, выключенный update key или Debug runtime.
2. Сверить текущую версию backend/миграции **на рабочей VM** и
   реально установленные Flutter-версии клиентов с новым
   `minimumClientVersion` и `app-info`. Выбрать порядок rollout
   **по фактической совместимости**, чтобы работающие ПК не оказались
   внезапно заблокированы backend minimum. Нельзя предполагать, что
   backend-first безопасен только потому, что backend deploy ранее работал.
3. Убедиться в годности свежей production резервной копии и доступности
   процедуры восстановления до потенциальной миграции. Не подменять
   проверку production копии локальным тестовым `pg_dump`.
4. Проверить release feed, хеши, корректный Ed25519 public/private
   pairing, Windows build number/version и итоговый штатный
   CI-generated Setup. Не изменять публичный `latest` до готовности
   контролируемого выпуска.
5. Зафиксировать план наблюдения (readiness, API/Flutter ошибки,
   Sentry/GlitchTip), короткий post-deploy smoke и процедуру
   rollback/восстановления при несовместимости схемы или клиента.
6. Публикация Flutter GitHub Releases, GHCR push, merge, изменение
   production и установка на рабочие ПК — **новая отдельная задача**
   с явным разрешением владельца, а не автоматическое продолжение QA.

## Итог

**Этапы QA 1–6 завершены в согласованных границах.**
Решение GO относится к переходу от тестирования к контролируемой
подготовке выпуска, не к самопроизвольному развёртыванию.
Тестовая Release 1.3.0+104, оставшаяся на ПК разработки, использует
loopback API URL и выключенный updater; она **не предназначена для
установки на рабочие клиентские ПК**.

Следующий шаг: отдельно согласовать и выполнить release/deploy,
по одному проверяемому действию с явными контрольными точками.
