## Что реализовано

`scenario-prepare QA-001…004`, `scenario-verify QA-001…004`, `scenario-status`.
Дополнительно `scenario-status QA-001` повторно выводит сохранённую инструкцию,
а `scenario-prepare QA-001 -NewCycle` явно начинает новый цикл без удаления
старых документов, журналов и результатов. Последний цикл активен.
QA-001 → QA-002 → QA-003 работают с одним сохранённым UUID маршрута;
QA-004 не имеет зависимостей от этой цепочки.

Архитектура: Live читает существующие API и SQL; Runner управляет подготовкой,
зависимостями и результатами; Checks формирует пути/UUID/expected/actual.
Для каждого запуска сохраняется исходный SQL-снимок, план и независимые
ожидания. Детали: [описание инструмента](../stages/03-scenarios-verification.md).

Журнал `.codex-tmp/qa-scenarios/journal.json`: schemaVersion=1, cycles,
QA-идентичность (секретный маркер представлен хешем), runId, before, core,
catalogs, manifestHash, plan, expected, documentId, beforeDocument,
confirmedDocument/At, lastVerification и errors. Паролей/JWT нет, seed-манифест
не используется как журнал. Запись атомарна с fsync/replace под OS-блокировкой.
Есть также общая блокировка seed для исключения CLI-изменений манифеста.

Создание доставки обнаруживается по ровно одному новому UUID относительно
before и точному run-маркеру в памятке первой точки. Самовывоз — по ровно
одному новому UUID своего типа и полному плану: памятка в его UI недоступна.
Наличие нескольких новых документов даёт отказ. После первого обнаружения
UUID хранится; при повторной проверке контролируется и отсутствие дубликатов.
Редактирования используют только UUID предыдущего подтверждённого документа.
При переходе к следующему шагу прежний результат отделяется как исторический.

HTTP: документ, история документов/клиентов, latest-order, отчёт продаж,
справочники и health. SQL: точные строки документов, точек, товаров,
point_commissions/document_employee_commissions, события, снимок CORE.
Проверяются UUID, порядок, оплаты, исторические имена/реквизиты, ревизия,
исходные количества для загрузки и неизменность CORE/общих зависимостей.
Для аудита проверяются события документа, точек/строк, операция, существующий
actor и его соответствие payload, создание снимков и old/new согласованных
изменений. EmployeeLoginEvent учитывается отдельно от сохранения документа.

Расчёт — чистые QA-формулы seed_plan: Decimal, HALF_UP до 0.01 **каждой**
строки, затем сумма; оборот недоставленной точки 0; комиссия — точный
оборот × ставка / 100. Production-функции расчёта не импортируются.
Отчёт продаж рассчитывается заново из SQL за весь плановый день, включая
группы способ оплаты/товар; готовый HTTP-отчёт не является эталоном.

## Ограничения и следующий шаг

- Внешний вид Flutter, возврат к просмотру после сохранения, PDF и его товарная
  сводка проверяются владельцем. SQL-подтверждение исходных количеств не
  подтверждает визуальную сводку PDF.
- Для самовывоза нет доступного уникального маркера; требуется эксклюзивное
  создание одного самовывоза между prepare/verify. При неоднозначности — отказ.
- Неизменность journal при повторном PASS относится к файлу результатов;
  HTTP login может добавить EmployeeLoginEvent в БД.
- Журнал привязан к локальному компьютеру и постоянной QA; его потеря не
  восстанавливается поиском по сумме/дате и не лечится удалением документов.
- QA-001/004 имеют фиксированные плановые даты. Текущая дата сервера создания
  остаётся реальной, исторические даты не подделываются.
- Новый цикл с NewCycle явно оставляет прежние незавершённые сценарии
  архивными, не объявляет их успешно пройденными.

Первоначальная инструкция была выполнена владельцем: QA-001 → QA-002 → QA-003
на одном маршруте и независимый QA-004. Последующее состояние и приёмка
зафиксированы ниже. Этап 4 не начинался.
