# Контракт отчёта по продажам

Статус: контракт реализован в backend и Flutter. Модель
хранения снимка способа оплаты описана также в
`docs/contracts/delivery_document.md`.

## Назначение и правила отчёта

Отчёт показывает оборот по товарным строкам активных документов доставки и
самовывоза за выбранный период, сгруппированный по историческому способу оплаты.
Это отчёт по суммам документов, а не реестр фактически полученных платежей:
отдельные платёжные транзакции в текущей модели не хранятся.

- Период фильтруется по `plannedDate`, а не по `createdAt`.
- `date_from` и `date_to` включаются в период целиком. `date_from` не может быть
  позже `date_to`.
- Учитываются активные (`isActive: true`) документы обоих типов: доставки и
  самовывоза. Отменённые документы исключаются; восстановленные снова входят
  в отчёт.
- В оборот входят сохранённые товарные строки. Пустые документы и точки без
  товаров не добавляют количества или суммы.
- Количество товара — сумма `quantity` строк. Сумма строки — `quantity × price`,
  округлённая до двух знаков по правилу `ROUND_HALF_UP`; суммы отчёта складывают
  уже округлённые строки. Общий оборот равен сумме оборотов всех способов оплаты,
  включая группу «Не указан».
- Товар группируется по `productId` внутри способа оплаты. Для одного UUID, если
  в сохранённых строках встречаются разные исторические имена, `productName`
  содержит уникальные имена через ` / `, как в карточках дней доставки.
- Способ оплаты группируется по сохранённому в точке `paymentMethodId`, никогда
  не по текущему `Client.defaultPaymentMethodId`.
- В список `paymentMethods` включаются все способы из справочника, в том числе
  деактивированные и не использованные в выбранном периоде. Для них возвращаются
  нулевые показатели и пустой `products`.
- Строки с `paymentMethodId: null` объединяются в отдельную группу
  «Не указан». Группа включается, когда в периоде есть подходящие продажи без
  сохранённого способа оплаты. В неё попадут старые документы, созданные до
  миграции, а также новые точки клиента без заданного способа по умолчанию.
- Деактивированные способы не удаляются физически. Отчёт группирует по их UUID;
  `paymentMethodName` разрешается по текущему имени записи справочника.

## Снимок способа оплаты в документе

В БД у `points` появляется nullable `payment_method_id` с внешним ключом на
`payment_methods.payment_method_id`. Для точек до миграции выполняется только
добавление nullable-колонки: существующие строки не backfill-ятся из текущего
значения клиента, их способ оплаты остаётся неизвестен (`null`).

При создании новой точки backend копирует текущий способ оплаты по умолчанию
клиента. Точка с `pointId` при PATCH сохраняет сохранённый снимок, в том числе
`null`; новая точка, добавленная через PATCH, получает текущий способ по
умолчанию своего клиента. Изменение способа оплаты клиента влияет только на
точки, создаваемые после изменения.

Поле `paymentMethodId` и его отображаемое nullable-поле `paymentMethodName`
добавляются в ответы точки. Существующие `defaultPaymentMethodId` и
`defaultPaymentMethodName` остаются текущими значениями клиента и нужны для
его карточки/новых документов; использовать их в отчётах запрещено.

## HTTP-интерфейс

Новый endpoint защищён авторизацией по правилам приложения и использует
`StdResponse` с результатом в `data`. Поля JSON ответа — `camelCase`.

### Получить отчёт

`GET /protected/sales-report?date_from=2026-10-01&date_to=2026-10-31`

Оба query-параметра обязательны и принимают ISO date `YYYY-MM-DD`. При
отсутствии параметра, неверной дате или `date_from > date_to` сервер возвращает
стандартный ответ валидации `422`.

Отчёт возвращается целиком, без пагинации. Агрегацию выполняет backend в
PostgreSQL за один read-only SQL-запрос, чтобы общие показатели и карточки были
согласованы в одном снимке данных. В запросе используются границы плановых дат,
признак активности документа и сохранённый `points.payment_method_id`.

Денежные поля возвращаются десятичными строками с двумя знаками после запятой,
чтобы клиент не терял точность при преобразовании JSON-чисел.

```json
{
  "data": {
    "dateFrom": "2026-10-01",
    "dateTo": "2026-10-31",
    "totalQuantity": 17,
    "totalAmount": "4250.50",
    "paymentMethods": [
      {
        "paymentMethodId": "019a0000-0000-7000-8000-000000000001",
        "paymentMethodName": "Карта",
        "isActive": true,
        "totalQuantity": 12,
        "totalAmount": "3000.50",
        "products": [
          {
            "productId": "019a0000-0000-7000-8000-000000000010",
            "productName": "Вода",
            "quantity": 10,
            "amount": "2500.50"
          },
          {
            "productId": "019a0000-0000-7000-8000-000000000011",
            "productName": "Стаканы",
            "quantity": 2,
            "amount": "500.00"
          }
        ]
      },
      {
        "paymentMethodId": "019a0000-0000-7000-8000-000000000002",
        "paymentMethodName": "Перевод",
        "isActive": false,
        "totalQuantity": 0,
        "totalAmount": "0.00",
        "products": []
      },
      {
        "paymentMethodId": null,
        "paymentMethodName": "Не указан",
        "isActive": null,
        "totalQuantity": 5,
        "totalAmount": "1250.00",
        "products": [
          {
            "productId": "019a0000-0000-7000-8000-000000000010",
            "productName": "Вода",
            "quantity": 5,
            "amount": "1250.00"
          }
        ]
      }
    ]
  }
}
```

`totalQuantity` и `totalAmount` являются общими итогами всех групп, включая
«Не указан». Для каждой группы её итоги равны сумме значений `products`.
`isActive` равен текущему признаку способа оплаты и равен `null` только для
группы «Не указан».

Если за период нет товарных строк, endpoint возвращает `totalQuantity: 0`,
`totalAmount: "0.00"`; каждый заведённый способ оплаты всё равно присутствует
с нулевыми итогами, а `paymentMethods` не содержит группу «Не указан».

## Реализация и интеграция

- Изменение схемы БД оформляется новой Alembic-миграцией, совместимой с уже
  запущенным приложением. Колонка nullable, чтобы сохранить старые документы
  без выдуманного исторического способа оплаты.
- Изменение API документов добавляет снимок оплаты в модель/домен точки,
  ответы документов, события изменений и обработку создания/PATCH.
- Отчёт является read-only фичей. Он не меняет документы, справочники или
  события аудита.
- При создании документа с `creationRequestId` снимок оплаты определяется
  только при фактическом первом создании. Повтор идемпотентного запроса
  возвращает уже сохранённый документ и не пересчитывает снимки по текущим
  карточкам клиентов.
