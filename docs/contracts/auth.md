# Контракт входа и авторизации Mountain Fairytale

Статус: бизнес-контракт входа, учётных записей и работы JWT согласован. Дата: 10.10.2026.
Рекомендуемое место в Git: mountain_fairytale_backend/docs/contracts/auth.md.
Flutter ссылается на этот файл; независимую копию правил не ведём.

## 1. Назначение и источники требований

Общий контракт описывает взаимодействие Windows-приложения Flutter и FastAPI:
вход, восстановление сессии, обновление токенов, выход и смену пароля.
Приложение предназначено для работы сотрудников в локальной сети.

Роутеры, Pydantic-схемы, карта исключений и OpenAPI описывают HTTP-интерфейс.
Этот документ дополняет их правилами поведения клиента и сквозными сценариями.
В документе не следует вручную дублировать все поля OpenAPI.
Несоответствие кода и согласованных правил — задача на исправление, а не повод
молча изменить контракт.

Проверенные исходники в master:
- Backend: src/feat/auth/api/auth_routers.py, auth_schemas.py;
  src/feat/me/me_routers.py; src/common/api/routers.py, schemas.py, deps.py,
  excs_handlers.py.
- Flutter: lib/infra/repos/auth/sources/api_data_source.dart;
  lib/infra/repos/auth/models/auth_tokens_model.dart;
  lib/infra/auth/auth_service_impl.dart;
  lib/infra/http/api_client.dart;
  lib/presentation/providers/auth_provider.dart;
  lib/presentation/screens/login/login_screen.dart.

Это анализ исходников, а не результат запуска приложения или API-тестов.

## Согласованный бизнес-контракт: вход и учётные записи

Следующие правила утверждены пользователем 10.10.2026 и являются требованиями
для Flutter и FastAPI. Они определяют целевое поведение приложения.

### Экран входа и проверка пароля

1. Экран входа содержит dropdown активных сотрудников, поле пароля и кнопку «Войти».
2. Список активных сотрудников доступен до авторизации; dropdown показывает username.
   Деактивированные сотрудники в список не попадают.
3. username служит одновременно логином и отображаемым именем.
   Отдельное поле имени для этого сценария не требуется.
   Пустой username и username из одних пробельных символов запрещены
   при создании и переименовании сотрудника.
4. Пользователь выбирает свою учётную запись и вводит её пароль.
5. Пустой пароль разрешён. Вход с пустым полем успешен только для учётной записи,
   которой установлен именно пустой пароль.
6. Если пароль непустой, пустое поле не позволяет войти. Обход проверки пароля
   из-за локального размещения приложения не предусмотрен.
7. При входе сервер проверяет существование, активность сотрудника и пароль.
   Наличие сотрудника в ранее загруженном dropdown не заменяет серверную проверку.
8. Публичной самостоятельной регистрации нет. Кнопку «Зарегистрировать»
   и клиентский сценарий публичной регистрации необходимо убрать.
9. Публичный список активных username является разрешённой частью интерфейса.
   Прежнее правило о нераскрытии существования учётных записей следует уточнить:
   список логинов доступен, а ошибки входа не должны дополнительно раскрывать
   причину отказа или конфиденциальные данные сотрудника.

### Единственный bootstrap-администратор

1. В системе один администратор: bootstrap-администратор.
2. При первоначальном создании его username и пароль берутся из ENV.
3. Bootstrap создаёт администратора, если его ещё нет. При последующих запусках
   существующие username и пароль автоматически не перезаписываются из ENV.
4. Через приложение нельзя деактивировать bootstrap-администратора.
   Запрет должен действовать на сервере, а не только скрывать кнопку во Flutter.
5. Создание дополнительных администраторов через приложение не допускается.
6. Если пароль администратора забыт, доступ восстанавливают отдельной CLI-командой
   на сервере. Изменение ENV и перезапуск не являются неявным сбросом пароля.

### Управление сотрудниками и паролями

1. Только администратор создаёт сотрудников.
2. При создании администратор задаёт username и первоначальный пароль,
   включая пустой.
3. Администратор может изменять username сотрудника, деактивировать и восстанавливать
   его, а также задавать новый пароль, включая пустой.
4. Деактивация сохраняет сотрудника и историю его действий.
5. Каждый авторизованный сотрудник может самостоятельно изменить собственный пароль
   на выбранный им пароль, включая пустой. Это относится и к администратору.
6. При смене собственного пароля сотрудник определяется из проверенного access token;
   клиент не выбирает чужую учётную запись через employee_id.
7. Пароль и его hash не возвращаются ни в dropdown, ни в остальных ответах API.
8. Смена пароля не отзывает ранее выданные JWT. Деактивация запрещает новый вход
   и refresh, но уже выданный access token действует до своего exp (не более 15 минут).

### Критерии приёмки согласованного блока

- В dropdown присутствуют активные сотрудники и отсутствуют деактивированные.
- Сотрудник с пустым паролем входит с пустым полем.
- Сотрудник с непустым паролем не входит с пустым или неверным паролем.
- Деактивированный после загрузки списка сотрудник не может войти.
- Обычный сотрудник не может создавать сотрудников или выполнять административные операции.
- Администратор может менять username, пароль и активность обычного сотрудника.
- Сотрудник может изменить свой пароль с непустого на пустой и обратно.
- Смена собственного пароля не позволяет изменить пароль другого сотрудника.
- Повторный bootstrap не перезаписывает существующий пароль администратора.
- Деактивация bootstrap-администратора и создание второго администратора через API запрещены.
- CLI позволяет восстановить доступ администратора с забытым паролем.

## 2. HTTP-интерфейс: существующие endpoints и согласованные дополнения

Пути ниже относительно адреса сервера, без дополнительного /public в base URL.

| Действие | Метод и путь | Запрос | Успешный ответ |
| --- | --- | --- | --- |
| Список для входа — добавить | GET /public/auth/users | Без токенов и тела | 200, data.usernames: список username |
| Вход | POST /public/auth/login | username, password | 200, токены внутри data |
| Обновление | POST /public/auth/refresh | refreshToken | 200, токены внутри data |
| Выход | POST /protected/me/logout | Bearer access token, тело не требуется | 200, data: null |
| Смена пароля | PUT /protected/me/change-password | Bearer access token, password | 200, data: null |
| Текущий пользователь — добавить | GET /protected/me | Bearer access token | 200, data с employeeId, username, role |

Пример запроса входа:

```json
{"username": "manager", "password": ""}
```

Пример ответа входа и обновления:

```json
{
  "offset": null,
  "limit": null,
  "total": null,
  "message": null,
  "data": {
    "accessToken": "<access token>",
    "refreshToken": "<refresh token>"
  }
}
```

Пример запроса обновления для Flutter:

```json
{"refreshToken": "<refresh token>"}
```

Схемы backend используют camelCase. Входные snake_case имена также принимаются
благодаря populate_by_name, но клиенту предлагается использовать camelCase.
Flutter передаёт access token через Authorization: Bearer <token>.
Cookies поддерживаются сервером для браузерного клиента и документации;
работа Windows-клиента не должна зависеть от них.

Ошибки бизнес-логики текущий обработчик возвращает как {"detail": "..."}.
Точную таблицу статусов и сообщений необходимо сверить с APP_EXCEPTION_MAP.
Ошибки валидации 422 нужно разбирать отдельно: detail может быть списком.
Успешная оболочка StdResponse не означает, что ошибки имеют ту же оболочку.

Публичных /auth/users и /auth/register в проверенной сборке роутеров нет.
GET /protected/me также пока не объявлен и должен быть добавлен. Он возвращает
актуальные employeeId (UUID в виде строки), username и role внутри StdResponse.data.
Flutter использует эти данные для отображения текущего сотрудника и доступных
действий; права доступа всегда проверяются сервером.

### Публичный список сотрудников для входа

Endpoint: GET /public/auth/users. Доступен без авторизации, access и refresh tokens.
Предназначен для заполнения dropdown на экране входа.

1. Возвращает всех активных сотрудников, включая bootstrap-администратора.
2. Деактивированные сотрудники исключаются сервером.
3. Возвращает только имена пользователей: data — объект с полем usernames (массив строк username).
   Идентификаторы, роли, даты создания, пароли и password hash не возвращаются.
4. Сортировка на сервере: created_at ASC — самые старые сотрудники сверху.
   При одинаковом created_at используется employee_id ASC для стабильного порядка.
5. Переименование не меняет место сотрудника в порядке по дате добавления.
6. Возвращается полный список без пагинации; при отсутствии активных сотрудников
   HTTP 200 и data: {"usernames": []}, а не null.
7. Flutter сохраняет порядок массива data.usernames и использует выбранный username для login.
8. Наличие username в списке не заменяет проверку активности и пароля при login.

Пример успешного ответа:

```json
{
  "offset": null,
  "limit": null,
  "total": null,
  "message": null,
  "data": {"usernames": ["admin", "manager", "dispatcher"]}
}
```

HTTP-модель: StdResponse[AuthUsersResp] (usernames: list[str]). Имена в примере расположены по дате
добавления сотрудников, а не по алфавиту.

## 3. Правила клиента

Правила ниже описывают согласованное поведение входа и JWT и необходимые
действия клиента для его реализации.

### Запуск

1. До завершения восстановления показывать состояние загрузки.
2. Если сохранённого refresh token нет, открыть экран входа.
3. Если refresh token есть, попытаться получить новую пару токенов.
4. При успехе сохранить пару и открыть рабочую часть приложения.
5. При окончательном отказе в обновлении очистить токены и открыть вход.
6. При таймауте, отсутствии сети или 5xx сохранить refresh token,
   показать недоступность сервера и действие «Повторить».
   Рабочие операции без подтверждённой сессии не выполнять.

### Вход

1. Пользователь выбирает username из списка активных сотрудников и вводит пароль.
   Пустое поле допустимо только при установленном пустом пароле.
2. На время запроса повторное нажатие «Войти» блокируется.
3. При успехе клиент извлекает data, сохраняет токены и открывает приложение.
4. При неверных данных показывает понятное сообщение.
5. Пароль не сохраняется как способ восстановления сессии.
6. Ошибка сохранения токенов не должна оставлять приложение в частично
   авторизованном состоянии.

### Защищённые запросы

1. Передавать access token в Bearer-заголовке.
2. При 401 защищённого запроса выполнить refresh и повторить запрос один раз.
3. Одновременные запросы должны ожидать одну общую операцию refresh.
4. Повторный 401 после успешного refresh завершает локальную сессию.
5. Login и refresh не запускают автоматический refresh сами для себя.
6. 403 означает отсутствие прав; обновление токенов само по себе его не исправляет.
7. Сетевой сбой refresh не равен отказу в авторизации.
8. Завершение сессии в сервисе должно менять AuthProvider и возвращать экран входа.

### Выход

1. Пользователь всегда может выйти локально, даже при недоступном сервере.
2. При возможности клиент вызывает серверный logout с access token.
3. Токены и пользовательское состояние очищаются независимо от результата запроса.
4. После выхода отложенный refresh не должен снова восстановить сессию.
5. Данные предыдущего пользователя не должны оставаться доступны следующему.

Logout выполняет локальный выход на текущем компьютере и удаляет app cookies
при обращении к серверу. Серверного отзыва access или refresh tokens нет.
Другие компьютеры продолжают работать. Скопированный JWT остаётся валиден
до exp при выполнении соответствующих проверок сервера.

### Смена пароля

Идентификатор сотрудника определяется сервером из проверенного access token.
Клиент передаёт только новый password. Сотрудник может установить любой
допустимый пароль, включая пустой; это правило согласовано.
Текущая сессия и вход на других компьютерах сохраняются. Ранее выданные
access и refresh tokens продолжают действовать до своего exp. Новый пароль
используется при последующем входе по username и password.

## 4. Обнаруженные расхождения и места проверки

| Место | Текущее состояние | Необходимая работа |
| --- | --- | --- |
| Пути Flutter | /auth/login, /auth/refresh, /auth/logout | Согласовать полные пути с backend и настройкой base URL |
| Ответ с токенами | Flutter читает корень и snake_case | Читать data.accessToken и data.refreshToken |
| Logout Flutter | Передаёт refresh token через transport | Передавать Bearer access token на /protected/me/logout |
| Dropdown пользователей | Flutter вызывает /auth/users | Добавить GET /public/auth/users: data.usernames со строками username, created_at ASC |
| Регистрация | Flutter вызывает /auth/register | Убрать публичную регистрацию и кнопку; сотрудников создаёт администратор |
| Сбой refresh | Flutter ловит любую ошибку и удаляет токены | Разделить отказ в авторизации и временный сбой |
| Изменение состояния | ApiClient вызывает refresh через сервис | Проверить уведомление AuthProvider об окончании сессии |
| Общая защита backend | verify_access_token извлекает строку токена | Гарантировать валидацию JWT на каждом защищённом роуте |

В backend JWT разбирается через AccessTokenPayloadDep. Общая зависимость
protected сейчас использует verify_access_token, который лишь извлекает токен.
Наличие строки в заголовке не должно давать доступ к защищённому API.

## 5. Согласованные правила JWT и сохранения входа

1. Access token действует 15 минут с момента выдачи.
2. Refresh token действует три месяца. Для однозначной настройки TTL в реализации
   принимается 90 дней с момента выдачи каждого refresh token.
3. После закрытия и перезапуска приложения вход восстанавливается автоматически
   по сохранённому refresh token. Перерыв в работе на месяц сам по себе
   не должен требовать повторного ввода пароля.
4. Успешный refresh выдаёт новую пару JWT с новым сроком действия:
   access — 15 минут, refresh — 90 дней от новой выдачи. Клиент сохраняет новую пару.
5. Сессии, реестр refresh tokens, blacklist и признаки отзыва в базе не создаются.
   Авторизация работает на JWT с проверкой подписи, типа и exp.
6. Один сотрудник может входить на любом числе компьютеров и получать любое число
   токенов. Ограничений числа одновременных входов и учёта устройств нет.
7. Выдача новой пары не отзывает старую. Старые access и refresh tokens сохраняют
   свои исходные сроки действия; их exp не продлевается самим фактом refresh.
8. Повторное использование старого refresh token допустимо до его exp, если
   сотрудник существует и активен. Одноразовой ротации refresh tokens нет.
9. Смена пароля сотрудником, администратором или через CLI не отзывает JWT.
10. Logout очищает только локальное состояние текущего клиента и app cookies.
    Серверный отзыв JWT и выход со всех компьютеров не выполняются.
11. Деактивированный сотрудник не может войти или выполнить refresh, даже
    с ещё не истёкшим refresh token. Проверка активности выполняется при входе
    и refresh. Для существующего access token немедленная проверка активности
    на каждом защищённом запросе не требуется: доступ сохраняется до exp,
    максимум 15 минут после выдачи последнего access token.
12. GET /protected/me предназначен для чтения данных текущего сотрудника;
    его вызов не создаёт серверную сессию и не вводит немедленный отзыв JWT.
13. При истечении refresh token и отсутствии другой сохранённой валидной пары
    потребуется повторный вход. Таймаут, потеря сети и 5xx не являются основанием
    для удаления сохранённого refresh token.

Открытых бизнес-вопросов в согласованном объёме авторизации не осталось.
Точные HTTP-схемы новых endpoints, настройки и обработка ошибок должны быть
приведены к этим требованиям при реализации.

## 6. План соединения приложений

1. Использовать согласованный контракт как требования для реализации.
2. Уточнить описания роутеров, схемы и ошибки; исправить общую проверку JWT.
3. Добавить список активных username и GET /protected/me; довести остальные
   auth endpoints, TTL JWT и API-тесты по согласованным правилам.
4. Подключить вход Flutter: адрес сервера, пути, StdResponse, camelCase, ошибки.
5. Довести восстановление, общий refresh, уведомление UI и локальный выход.
6. Проверить на реальном FastAPI/PostgreSQL полный цикл авторизации.
7. Подключить один простой справочник, например автомобили, чтобы проверить
   Bearer-доступ, UUID, оболочку ответа и CRUD через существующие слои Flutter.
8. Затем переносить остальные справочники и документы по одной фиче.

Критерий готовности первого этапа: вход с обычным и пустым паролем,
отказ при неверных данных, восстановление после перезапуска,
обновление истёкшего access token, окончательный отказ refresh,
временная недоступность сервера без потери сохранённого входа,
выход без сети, отсутствие доступа с поддельным JWT.

Дополнительные критерии приёмки:

- GET /public/auth/users работает без токенов, возвращает только активные username.
- Список отсортирован по created_at ASC; при равных датах — по employee_id ASC.
- Ответ списка содержит data.usernames со строками и не раскрывает другие поля сотрудника.
- Пустой список возвращается как HTTP 200 с data: {"usernames": []}.

- Пустой username и username из одних пробелов отклоняются при создании и изменении.
- GET /protected/me возвращает employeeId, username и role текущего сотрудника.
- Сроки JWT соответствуют 15 минутам и 90 дням.
- После месяца без использования приложения действующий refresh восстанавливает вход.
- После refresh старая пара остаётся действительной до собственного exp.
- Смена пароля не прекращает вход на текущем и остальных компьютерах.
- Logout на одном компьютере не прекращает вход на другом.
- Деактивация блокирует login и refresh, но не отзывает действующий access token.
- Авторизация не требует таблицы сессий или серверного реестра JWT.
