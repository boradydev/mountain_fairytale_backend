# Контракт журнала событий API ↔ Flutter

Статус: API и интеграция Flutter реализованы. Проверены HTTP-сценарии на реальном
PostgreSQL, курсорная пагинация, безопасность payload, модели/провайдеры и UI Flutter.
Исходная миграция events изменена без добавления новых ревизий.

Источники текущего устройства:

- backend: `src/common/domain/event_record.py`, `src/common/infra/services/event_pud_service.py`,
  `src/common/infra/db/postgres/repos/events/` и доменные модули событий `src/feat/*/domain/*_events.py`;
- Flutter: `lib/features/audit_event/` и подключение `ApiAuditLogDataSource` в `lib/main.dart`.

## Исходное состояние до реализации

### Backend

- Общая таблица `events`: `event_id` UUID, `event_type` строка с именем класса,
  `actor_id` UUID, `created_at` timestamp, `payload` JSONB.
- Publisher сохраняет события в той же транзакции, что и изменение сущности.
- Список репозитория отсортирован по `created_at DESC, event_id DESC` и принимает
  `offset` / `limit`.
- События создаются для сотрудников (создание, изменение, вход), товаров,
  клиентов, водителей, автомобилей, способов оплаты и представителей продаж.
  Для документов доставки также сохраняются события документа, точек и товарных
  позиций, включая создание, изменение, отмену, восстановление и удаление вложенных
  сущностей.
- Публичный защищённый API подключает фичи под `/protected`, требует access token,
  использует JSON `camelCase` и `StdResponse` с полезной нагрузкой в `data`.
- Чтение журнала доступно всем сотрудникам. Создание сотрудников остаётся
  административной операцией; это отдельное правило доступа, не часть контракта
  событий.

### Flutter

- Есть экран аудита с поиском, бесконечной прокруткой страниц по 50 записей и
  отображением времени, пользователя, действия, сущности и изменений.
- Источник данных сейчас — `DemoAuditLogDataSource`; HTTP-источника для журнала нет.
- Текущая модель Flutter предполагает числовые `id` / `userId` / `entityId`,
  действия `created | updated | deleted` и изменения-строки `oldValue` / `newValue`.
  Эти ожидания не соответствуют backend UUID и его разнородным доменным событиям.

## Целевой HTTP-контракт

### Авторизация и формат

- Метод и путь: `GET /protected/events`.
- Требуется `Authorization: Bearer <accessToken>`.
- Журнал доступен любому авторизованному сотруднику; отдельная роль для чтения
  не требуется.
- Поля JSON ответа используют `camelCase`; ID передаются строками UUID.
- Успешный ответ обёрнут в `StdResponse`; список и курсор следующей страницы
  находятся в `data`.
- У endpoint нет операций создания, изменения или удаления: журнал доступен
  только для чтения.

### Запрос

| Параметр | Тип | Обязательный | Правило |
| --- | --- | --- | --- |
| `limit` | integer | нет | По умолчанию `50`, диапазон `1..100` |
| `cursor` | string | нет | Непрозрачный курсор из предыдущего ответа; отсутствует при запросе первой страницы |
| `after` | string | нет | Курсор обновлений `latestCursor`; загрузка событий строго новее этой позиции |
| `search` | string | нет | Необязательная строка поиска; пустая после trim трактуется как отсутствие фильтра |
| `action` | enum string | нет | Одно действие из `action` события; отсутствие означает все действия |
| `date_from` | ISO 8601 timestamp | нет | Время события от указанной границы включительно; часовой пояс обязателен |
| `date_to` | ISO 8601 timestamp | нет | Время события до указанной границы исключительно; часовой пояс обязателен |

Длина `search` ограничена 500 символами, `cursor` и `after` — 2048 символами.
`cursor` и `after` нельзя передавать одновременно. Неиспользуемые
метаданные стандартной обёртки (`offset`, `total`, `message`) могут быть `null`;
Flutter определяет продолжение списка только по `data.nextCursor`.
Фильтры применяются совместно до пагинации. Если обе границы заданы,
`date_from` должен быть меньше `date_to`; неверное действие, дата без часового
пояса или неверный диапазон дают HTTP 422. Фильтр относится к `createdAt`
события, а не к плановой дате документа.

Пример:

```http
GET /protected/events?limit=50&search=Иванов
Authorization: Bearer <accessToken>
```

`search` фильтрует по имени пользователя, типу/названию сущности и отображаемым
старым/новым значениям изменений без учёта регистра. Фильтрация должна
применяться на backend до cursor pagination. Поиск не должен возвращать скрытые
служебные значения, например хеш пароля.

### Поля события

| Поле | Тип | Правило |
| --- | --- | --- |
| `eventId` | UUID string | Идентификатор записи журнала; уникален и пригоден для ключа списка |
| `operationId` | UUID string | Общий идентификатор одной бизнес-операции/API-команды; все события от одного сохранения имеют один `operationId` |
| `eventType` | string | Исходный тип доменного события, например `CreateProductEvent`; клиент использует для диагностики/неизвестных типов, а не для текста UI |
| `createdAt` | ISO 8601 timestamp | API нормализует время в UTC с суффиксом `Z`; Flutter отображает локальное время устройства |
| `actor.actorId` | UUID string | Автор события; текущая таблица требует UUID автора для каждой записи |
| `actor.displayName` | string или `null` | Текущее имя автора, разрешённое по `actorId`; переименование сотрудника обновляет имя во всех старых событиях. Если сотрудник недоступен, вернуть `null` |
| `action` | enum string | `created`, `updated`, `activated`, `deactivated`, `cancelled`, `restored`, `deleted`, `password_changed`, `login`, `other` |
| `subject.type` | string | Стабильный ключ типа сущности в `snake_case`: `product`, `client`, `driver`, `car`, `payment_method`, `sales_representative`, `employee`, `delivery_document`, `delivery_point`, `delivery_item` |
| `subject.id` | UUID string | ID сущности, к которой относится событие |
| `subject.displayName` | string или `null` | Имя сущности в состоянии на момент события; для новых событий создания обязательно фиксируется, последующие имена выводятся из цепочки изменений |
| `subject.documentType` | string или `null` | Необязательный неизменяемый тип документа: `delivery_route_sheet` или `pickup_sheet`; используется для нейтральной подписи документа во Flutter |
| `data` | object | Начальные бизнес-значения для события создания, включая исходное имя сущности; не содержит секретов |
| `changes` | object | Изменения по ключу поля; `{}` если значимых изменений нет |

При создании событие обязательно сохраняет начальное имя сущности в `data`
(поле `displayName` или исходные поля, однозначно формирующие это имя) и начальные
значения остальных бизнес-полей. Flutter использует сохранённое имя при показе
создания; название на более позднем событии восстанавливается по цепочке изменений.
Для изменения каждое поле `changes` содержит `oldValue` и
`newValue` как JSON-значения любого типа или `null`. Значение `null` означает
отсутствие/пустое значение, а не отсутствие ключа. Ключи — стабильные camelCase
имена полей API;
Flutter переводит их в подписи для пользователя. Даты и UUID в значениях также
передаются строками. Это публичное представление: внутренний сериализатор сейчас
хранит `FieldChange` как `old` / `new`, а API преобразует их в `oldValue` /
`newValue`. Составные изменения (например, точки и позиции документа)
могут быть массивами/объектами; UI должен уметь показать краткое сводное
значение и не считать произвольную JSON-структуру строкой ошибки. Изменения
секретных полей не содержат старого или нового значения: смена пароля отражается
как `password_changed` без hash или пароля.

### Названия связанных сущностей

При записи события backend сохраняет ссылочное бизнес-значение как объект
`{ "id": "UUID", "displayName": "Название на момент действия" }`.
Это относится к `salesRepresentativeId`, `defaultPaymentMethodId`, `driverId`,
`carId`, `clientId` и `productId`, включая ссылки внутри `points` и `items`.
Для автомобиля название складывается из модели и номера.

При создании и удалении вложенной сущности объект находится в `data`.
При изменении ссылки оба значения в `changes` сохраняются отдельно:

```json
{
  "salesRepresentativeId": {
    "oldValue": { "id": "0192f0b0-1234-7000-8000-000000000004", "displayName": "Иван Петров" },
    "newValue": { "id": "0192f0b0-1234-7000-8000-000000000005", "displayName": "Анна Иванова" }
  },
  "defaultPaymentMethodId": {
    "oldValue": null,
    "newValue": { "id": "0192f0b0-1234-7000-8000-000000000006", "displayName": "Наличные" }
  }
}
```

`null` сохраняет значение отсутствующей связи. Если связанную запись невозможно
найти, объект сохраняет ID и `displayName: null`; Flutter показывает ID.
Название берётся в транзакции бизнес-операции и сохраняется в JSON события.
Переименование или деактивация справочника позднее не меняет этот снимок.
Это правило действует и для старого значения: имя фиксируется на момент изменения
связи. Ранее записанные события не дополняются текущими названиями.

Flutter показывает сохранённый `displayName` без дополнительной загрузки
справочника по ID. Старые события с UUID-строкой остаются читаемыми и показывают ID.
Идентификаторы самого события, субъекта, точки и `actorId` остаются строками UUID.
Для автора сохраняется согласованное правило: `actor.displayName` — текущее имя
сотрудника, разрешённое по `actorId` при чтении журнала.

### Типы действий

`action` — стабильный тип бизнес-действия в API. Flutter выбирает по нему
глагол, иконку и контекст строки; определять действие по `eventType` или разбирать
внутренний payload не нужно. `eventType` остаётся технической меткой для
диагностики и поддержки неизвестных типов.

Flutter разбирает общую оболочку события (`eventId`, `operationId`, `createdAt`,
`actor`, `action`, `subject`, `data`, `changes`) и не создаёт отдельную модель для
каждого `eventType`. `data` и `changes` — динамические JSON-объекты: ключи — имена
полей API в `camelCase`, значения могут быть строками, числами, boolean, `null`,
массивами или вложенными объектами. Для подписи поля Flutter может использовать
словарь по `subject.type` + имени поля; незнакомое поле отображается по имени ключа,
а незнакомое значение — в безопасном общем JSON-формате. Добавление нового поля или
нового внутреннего класса события не должно ломать разбор уже известных полей.

Backend не отдаёт внутренний `payload` как публичный формат: он преобразует разные
доменные события в общую оболочку и стабильные `action`, `subject`, `data` и `changes`.

| `action` | Смысл для Flutter |
| --- | --- |
| `created` | Сущность создана; начальные поля и имя доступны в `data` |
| `updated` | Данные сущности изменены; `changes` содержит старые и новые значения |
| `activated` / `deactivated` | Сущность включена / выключена |
| `cancelled` / `restored` | Документ отменён / восстановлен |
| `deleted` | Вложенная точка или позиция удалена при редактировании документа |
| `password_changed` | Пароль сотрудника изменён; секретные значения отсутствуют |
| `login` | Сотрудник успешно вошёл по логину и паролю |
| `other` | Незнакомое действие; Flutter показывает нейтральный вариант по `eventType` |

### Правила отображения действий

- `Create*Event` → `created`.
- `Update*Event` → `updated`, кроме изменения только `isActive`: переход `false → true`
  отображается как `activated`, `true → false` — как `deactivated`.
- `CancelDeliveryDocumentEvent` → `cancelled`; `RestoreDeliveryDocumentEvent` → `restored`.
- `DeletePointEvent` / `DeleteItemEvent` → `deleted`.
- Успешный вход по логину и паролю (`EmployeeLoginEvent`) → `login`; сотрудник
  является и автором, и subject события. Неуспешный вход не записывается.
- Обновление refresh token и выход не записываются.
- Изменение пароля сотрудника → `password_changed`, без значений `password_hash`.
- Блокировка, продление и снятие edit lock документа не являются бизнес-изменением
  документа и в журнал не входят.
- Неизвестный тип события остаётся в выдаче с `action: "other"`; Flutter показывает
  нейтральный текст по `eventType`. Новые типы нельзя молча отбрасывать.

## Пагинация и порядок

- Сортировка: `createdAt DESC`, при одинаковом времени — `eventId DESC`.
  Для запроса `after` используется обратное направление: `createdAt ASC, eventId ASC`,
  чтобы последовательно дочитывать все новые записи без пропусков при превышении лимита.
- События с одинаковым `operationId` возникли из одной команды сохранения. Flutter
  отображает одну строку операции; отдельные события и их `eventId` сохраняются в подробностях.
  Страница может закончиться посреди группы; при загрузке следующих страниц Flutter
  добавляет события в уже открытую группу с тем же `operationId`.
- Первая страница запрашивается без `cursor`. Следующие запросы передают `nextCursor`
  предыдущего ответа как `cursor`.
- Курсор непрозрачен для Flutter: клиент не декодирует его и не создаёт самостоятельно.
  Он указывает на последнюю запись страницы по паре `createdAt` / `eventId` и привязан
  к поиску, действию и диапазону дат. Backend возвращает курсор только если есть более старые записи;
  `nextCursor: null` означает конец списка.
- Для следующей страницы backend выбирает события строго старше позиции курсора,
  включая tie-break по `eventId`. Новые события, добавленные в начало журнала после
  загрузки первой страницы, не сдвигают эту границу и не вызывают повторов/пропусков.
- Смена поиска, действия или диапазона дат сбрасывает выдачу и оба курсора.
  Новые события загружаются отдельно через `after` с теми же фильтрами.
- Некорректный курсор или курсор, выпущенный для другого фильтра поиска, приводит
  к HTTP 422; Flutter сбрасывает курсор и перечитывает список с начала.

### Загрузка новых событий

- `data.latestCursor` — непрозрачный курсор обновлений, привязанный ко всем фильтрам и
  направлению «новее». На первой странице он указывает на её самое новое событие.
  Для пустой выдачи возвращается начальная позиция, пригодная для последующих проверок.
- Flutter проверяет обновления через `GET /protected/events?after=<latestCursor>&limit=50`
  с теми же `search`, `action`, `date_from`, `date_to`. Полученные события объединяются по `eventId` и сортируются
  для отображения в обычном порядке DESC.
- При `after` поле `nextCursor` служит продолжением загрузки новых записей: его
  нужно передать снова как `after`. Если оно `null`, новые записи дочитаны.
  `latestCursor` указывает на последнюю прочитанную новую запись; при пустом
  ответе сохраняет переданную позицию.
- Курсоры направлений несовместимы; неправильное направление, фильтр или
  одновременная передача `cursor` и `after` дают HTTP 422.
- Курсор старой истории хранится отдельно и не заменяется курсором обновлений.
  Одна проверка загружает не более пяти порций по 50 событий; оставшиеся записи
  дочитываются при следующей проверке с сохранённой позиции.
- Проверка выполняется каждые 15 секунд, только когда вкладка журнала видима
  и приложение находится в состоянии resumed. При открытии вкладки и возвращении
  приложения выполняется немедленная проверка. При уходе таймер отключается;
  уже отправленный запрос может завершиться, но следующие порции не запрашиваются.
- При просмотре верхней части списка дочитанные обновления показываются автоматически.
  При чтении истории они накапливаются отдельно, а кнопка «Есть новые события — показать»
  добавляет их и переводит к началу журнала. Загруженные старые страницы сохраняются.
- Ручное обновление после начальной загрузки также добавляет новые записи с
  сохранением истории. Поиск начинает новую выдачу и сбрасывает оба курсора.
- Ошибка проверки не очищает журнал и накопленные обновления; следующая проверка
  продолжает чтение с последней успешно полученной позиции. Открытые строки
  сохраняют состояние при добавлении записей и прокрутке.

### Ошибки

- `401` — токен отсутствует или недействителен; используется общий механизм обновления
  токена Flutter и общая обработка `ApiException`.
- `422` — некорректные `cursor` / `limit` или параметры запроса.
- Схема ошибки и остальные статусы следуют общим обработчикам backend. Flutter
  показывает сообщение запроса и действие повтора, не разбирая внутренний traceback.

## Реализация

- Endpoint: `src/feat/audit_event/api/audit_routers.py`, схемы `audit_schemas.py`.
  Use case и UOW собраны через `AuditUseCaseFactory` и `AppContext`.
- История имён и поиск до пагинации: `src/common/infra/db/postgres/repos/events/sql/get_page.sql`.
  Курсор содержит версию, время, UUID последней записи и отпечаток нормализованного поиска.
- Каждый publisher-вызов в UOW создаёт один `operationId` для всего набора событий.
  Исходная миграция events включает `operation_id`, `TIMESTAMPTZ` и индексы курсора,
  операций и истории имени. Новых миграций нет.
- `BaseEntity._add_event` проверяет поля по `_EVENT_FIELDS`, сохраняет безопасные
  начальные значения и идентичность сущности. Неожиданное поле вызывает ошибку;
  транзакция изменения сущности откатывается вместе с записью аудита.
- Смена пароля — отдельное `EmployeePasswordChangedEvent` без значений пароля/хеша.
  Publisher дополнительно отклоняет секреты во вложенных JSON-значениях.
- `EmployeeLoginEvent` создаётся только после успешной проверки логина/пароля.
  Refresh, logout и операции edit lock событий не создают.
- Имя автора разрешается по текущей записи сотрудника. Для системного bootstrap
  используется `actorId: 00000000-0000-0000-0000-000000000000`; Flutter показывает «Система».
- `delivery_item` имеет составной доменный ключ pointId/productId. Его публичный
  `subject.id` — стабильный UUID5 от этой пары; он служит идентификатором аудита,
  а не адресом отдельного CRUD endpoint.
- Flutter использует `ApiAuditLogDataSource` и `AuditLogRepositoryImpl`.
  В интерфейсе поиск и ручное обновление заменены меню фильтров действия и периода;
  параметр `search` API сохранён. Ответы устаревших фильтров игнорируются. Ошибка следующей
  страницы сохраняет уже загруженные строки и курсор. Некорректный курсор истории вызывает
  повторное чтение с первой страницы. Обновления загружаются отдельно через `after`.
- Действия, сущности и названия известных полей подписываются во Flutter на русском.
  Неизвестное поле/вложенный JSON имеют общий формат отображения.
- Использованы общие `AppIconButton` и `AppSecondaryButton`. Карточки в журнале
  заменены компактными раскрывающимися строками `AuditOperationRow`.
- Проверки: `tests/integration/api/test_audit_events.py`, `tests/unit/test_audit_fields.py`,
  `tests/integration/infra/repos/test_events_repo.py`; во Flutter — `test/audit_event/`,
  `test/app/app_shell_test.dart`, отдельный opt-in live-тест `test/live/audit_events_live_test.dart`.
- 14.10.2026 выполнена совместная проверка настоящего Flutter с запущенным backend:
  создание, переименование, изменение цены, деактивация товара, переход между
  страницами истории и отображение настоящих данных в журнале прошли успешно.

### Компактное отображение Flutter

- Над списком постоянно выделена панель высотой 76 px. В ней расположено popup-меню
  фильтров: одно действие либо «Все действия», диапазон дат, «Все даты» и сброс.
  Действие и период применяются совместно. На широком экране текущие фильтры видны
  рядом с меню, на узком доступны в меню и подсказке.
- Диапазон выбирается календарём. Обе выбранные даты включены целиком по локальному
  времени устройства: Flutter передаёт начало первого дня и начало дня после
  последнего в UTC. Это позволяет корректно учесть часовой пояс и смену длительности дня.
- Кнопка «Есть новые события — показать» появляется внутри этой же панели;
  её место зарезервировано. Индикатор загрузки также имеет постоянное место.
  Появление уведомления или индикатора не меняет высоту панели и положение списка.
  Ошибки доступны через значок с подсказкой и повтором запроса в панели.
- Закрытая строка: иконка действия → дата/время → название действия → автор →
  тип сущности и её название → шеврон. Действие занимает колонку фиксированной
  ширины, чтобы авторы начинались на одной вертикали, например:
  «Создание   manager → Товар: Вода талая». Длинное название действия сокращается
  и доступно целиком в подсказке. При узкой ширине автор и сущность переносятся
  на вторую строку с одинаковым отступом для всех операций.
- Основная строка, названия действий, клиентов и товаров, подписи полей и значения
  используют размер 14 px; дата — 13 px. Минимальная высота корневой строки — 48 px.
  Масштабирование текста по настройкам устройства сохраняется.
- Вход отображается отдельной фразой «admin — вошёл в систему»; системный автор
  с нулевым UUID отображается как «Система».
- Создание обозначено зелёным плюсом, изменение — синим карандашом, деактивация —
  красным выключенным тумблером (`toggle_off_outlined`); активация — зелёным
  включённым тумблером (`toggle_on_outlined`). Корзина используется для реального удаления вложенных записей.
  Остальные действия имеют отдельные иконки/подсказки; цвета адаптируются к теме.
- У иконок есть подсказка о действии, у даты — полное время с секундами, у текста —
  полные имена. Длинные имена сокращаются в строке и доступны полностью в подробностях.
- Вся строка раскрывается по нажатию или с клавиатуры. Начальные поля показаны как
  «Поле: значение», изменённые — «Поле: было → стало». Цвет сущности/сотрудника не назначается.
- На всех уровнях заголовок раскрывающейся строки не повторяется внутри
  раскрытого блока: действие, автор, тип и название остаются в заголовке,
  ниже показаны только бизнес-поля, изменения и вложенные списки.
  Связанные события без общего снимка также имеют собственную раскрывающуюся
  строку без повторения заголовка в подробностях.
- Без подробностей шеврон отсутствует (например, вход или смена пароля без значений).
- Для одного сохранения документа основной строкой выбирается событие самого документа.
  Изменения точек и позиций помещаются в подробности этой строки. Если группа разделена
  курсором, новые события добавляются в неё с сохранением раскрытого состояния.
- Документ получает подпись «Маршрутный лист: 15.10.2026» или «Лист самовывоза: 15.10.2026»;
  без `documentType` используется совместимый вариант «Документ: 15.10.2026».
- Подробности документа упорядочены: плановая дата, водитель, автомобиль,
  начальный и конечный пробег, остальные бизнес-поля, раскрывающийся раздел «Клиенты».
  Тип документа повторно не выводится. Для самовывоза поля водителя, автомобиля
  и пробега скрыты как неприменимые.
- «Клиенты» раскрывает строки клиентов с количеством товарных позиций. Каждая
  строка клиента раскрывает товары: название, количество и цену. Имена берутся
  из снимков события; запросы к текущим справочникам не выполняются.
  Все вложенные раскрывающиеся строки подсвечиваются при наведении и фокусе,
  показывают курсор ссылки и вращающийся шеврон, как корневая строка операции.
- Точки упорядочены по сохранённой позиции в документе. При редактировании
  удалённые точки добавляются после оставшихся, в своём прежнем порядке.
  Счётчики включают все показанные позиции, в том числе удалённые.
- Старые и новые снимки точек сопоставляются по `pointId`, товаров — по ID товара.
  Иконка действия отображается только в верхней строке операции. Во вложенных
  подробностях изменение и удаление обозначены текстом, а шевроны
  раскрытия сохранены. Изменения количества,
  цены и порядка показываются как «было → стало». Порядок показывается с единицы.
  Пустые списки имеют явные подписи «Нет клиентов» / «Нет товаров».
  У новых клиентов документа и новых товаров подпись «Создание» не выводится:
  добавление вложенных записей в уже существующий документ относится к общей
  операции «Изменение». Доменные типы событий и JSON-ключи `points` / `pointId`
  сохраняются; это правило отображения Flutter.
- Когда снимок документа содержит точки, вложенные события точек и товаров
  представлены в этой структуре и не повторяются в «Связанных изменениях».
  Для событий без снимка и незнакомых типов сохраняется общее отображение подробностей.
- Раскрытые значения можно выделять и копировать; тёмная/светлая темы и узкая ширина
  проверены виджетными тестами. Opt-in preview-тест с `AUDIT_PREVIEW=true` сохраняет
  изображения в `build/audit-events/` Flutter-проекта.

### Поля, разрешённые в событиях

`_EVENT_FIELDS` задаётся отдельно от `_ALLOWED_UPDATE_FIELDS` и включает все
бизнес-поля каждой сущности. Пароли, хеши, токены и другие секреты аутентификации
не входят в него. Служебные timestamps и edit lock также исключены.

| Сущность | Поля события (в JSON ответа) |
| --- | --- |
| Товар | name, basePrice, isActive |
| Водитель | name, isActive |
| Автомобиль | model, number, currentMileage, isActive |
| Способ оплаты | name, isActive |
| Представитель | name, phone, commissionPercent, isActive |
| Сотрудник | username, role, commissionPercent, isActive |
| Клиент | name, phone, address, lastDeliveryDate, lastDeliveryQuantity, cooldownUntil, sleepingThresholdDays, salesRepresentativeId, defaultPaymentMethodId, isActive |
| Документ | documentType, plannedDate, isActive, driverId, carId, startMileage, endMileage, points |
| Точка | pointId, clientId, position, items |
| Позиция | productId, productName, quantity, price |

При создании данные включают также `displayName`. Для документа это плановая дата,
для точки — название клиента при создании, для позиции — сохранённое название товара,
для автомобиля — модель и номер, для остальных справочников — name/username.
В обновлении остаются только реально изменившиеся поля.

## Зафиксированные границы

- Этот API показывает аудит изменений, а не поток для синхронизации состояния Flutter.
  Flutter не применяет `payload` как команды и не восстанавливает состояние сущности
  из событий.
- Запись событий остаётся внутренней ответственностью backend и входит в транзакцию
  изменения сущности.
- Событие не создаётся для запроса, который не изменил состояние сущности.
- В событие попадают только поля из явного `_EVENT_FIELDS` сущности; поле,
  разрешённое для изменения, не обязательно разрешено для записи в аудит.
- Все сотрудники могут читать журнал. Создавать сотрудников могут только
  администраторы; это единственное указанное здесь отличие администратора.
- Все бизнес-поля из `_EVENT_FIELDS` одинаково видны всем сотрудникам; отдельного
  разграничения полей по ролям нет. Секретные данные не записываются в аудит.
- События, уже существующие в таблице, не переписываются ради нового формата ответа;
  преобразование выполняется на чтении.
- Для старых create-событий, где сохранён только ID, исходное имя восстановить
  нельзя. Новые create-события обязательно сохраняют его при записи.
- Срок хранения событий не ограничен: события хранятся бессрочно, автоматическая
  очистка, TTL и удаление записей журнала не предусмотрены.
- Контракт включает фильтры действия и периода, но не realtime/push-обновления.
  Новые события загружаются периодическими HTTP-запросами.
