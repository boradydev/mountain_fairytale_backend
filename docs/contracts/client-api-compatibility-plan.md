# Совместимость Flutter и backend: контракт и план внедрения

Статус: реализовано в рабочих ветках backend и Flutter; выпуск не выполнен.
Дата: 28 октября 2026 года.

Документ описывает согласованный контракт и его реализацию. Наличие изменений
в исходниках не означает установку на сервере или публикацию Flutter.
Демонстрационные номера в примерах не являются номерами подготовленных выпусков.
Итоговые решения приведены в разделе 10, эксплуатация — в разделе 11.

## 1. Цель и исходные условия

Backend сообщает, какая минимальная версия Flutter требуется для работы.
Неподдерживаемый клиент получает понятный экран обновления, а сервер отклоняет
его рабочие запросы до выполнения операций.

Приложение находится в разработке и не введено в эксплуатацию. По уточнению
владельца нет старых установленных клиентских версий, которые необходимо
поддерживать. Механизм можно внедрить сразу в обеих частях без переходного режима
для клиентов, не передающих версию. Наличие ранее подготовленных выпусков
и инфраструктуры доставки не означает наличие поддерживаемых рабочих установок.

Версии backend и Flutter независимы. Совпадение номеров не требуется.
Повышение версии backend само по себе не меняет минимальную версию Flutter.

Работает один обновляемый API. Параллельные поколения API, маршруты `/v2`
и согласование нескольких контрактов не предусматриваются. Обычно API
обновляется вне рабочего времени, когда пользователи не работают во Flutter.
При обновлении во время работы клиент также должен корректно обработать
серверное требование обновления; установка API без перерыва в доступности
не является целью этой задачи.

## 2. Исходное состояние до этой задачи

| Механизм | Фактическое поведение |
| --- | --- |
| Версия backend | Читается из `[tool.poetry].version` в `pyproject.toml`; используется в OpenAPI, health и диагностике |
| Идентичность backend-сборки | Полный commit SHA и digest образа; несколько сборок могут иметь одинаковую публичную версию |
| Версия Flutter | `version` в `pubspec.yaml`; CI сверяет публичную версию с тегом `vX.Y.Z` |
| Номер Flutter-сборки | При выпуске CI подставляет `github.run_number` вместо исходной части после `+` |
| Доставка Flutter | GitHub Releases, `update.json`, appcast и подписанный установщик через WinSparkle |
| Проверка обновлений | При запуске механизма обновлений и затем раз в четыре часа; установка по решению пользователя |
| Адрес API | Начальный `API_BASE_URL` и сохранённая настройка сервера; URL без дополнительных путей |
| Рабочие запросы | UI/provider → repository → data source → общий `ApiClient` → `HttpTransport` |
| Авторизация | `AuthApiDataSource` обращается к `HttpTransport` напрямую, включая login, refresh и `/protected/me` |
| Проверка соединения | `/health/ready`, показ версии сервера; совместимость не проверяется |
| Версия в запросах | Фиксированный `User-Agent: MountainFairytale/1.0 Windows`; фактическая версия не передаётся |

В backend `ROOT_PATH = /app/v1` сейчас является настройкой FastAPI.
Само наличие этой строки не реализует согласование версий или поддержку
нескольких контрактов. Flutter использует пути `/public`, `/protected`, `/admin`.
В рамках этой задачи адреса существующих методов не меняются.

Основание: [контракт эксплуатации и выпусков](operations-deployment-updates.md),
разделы 9–10; код `src/core/build_info.py`, `src/common/api/health_routers.py`
и Flutter `lib/core/network/`, `lib/features/app_updates/`.

## 3. Источники версий

| Значение | Единственный источник | Когда меняется |
| --- | --- | --- |
| Версия Flutter | `pubspec.yaml` | При подготовке клиентского выпуска |
| Номер установленной Flutter-сборки | Метаданные собранного Windows-приложения | При сборке в CI |
| Версия backend | `pyproject.toml` | При подготовке серверного выпуска |
| Минимальный Flutter | Новый `client_compatibility.toml` в корне backend | Когда прекращается поддержка старого клиента |

Содержимое нового файла (номер приведён для примера):

```toml
[flutter]
min_version = "1.2.0"
```

Это правило поставляется внутри того же образа backend и проходит обычный PR.
Не дублируем его в ENV, БД, GitHub Variables или вручную в Flutter.
Новые ENV-переменные для механизма не нужны. Существующие настройки адреса API
и доставки обновлений сохраняются.
Проверяем корректность при старте backend и в CI; ошибочная конфигурация
не должна незаметно отключать проверку.

Номера выпусков хранятся как `MAJOR.MINOR.PATCH`. Минимум сравнивается по трём
целым компонентам, а не как строка: `1.10.0` новее `1.9.0`.
В первой реализации не нужны prerelease-версии, диапазоны SemVer и ограничения
на отдельные build-номера. Номер сборки сохраняется для диагностики.

## 4. Согласованный HTTP-контракт

### 4.1. Заголовки клиента

Каждый запрос Flutter к выбранному API содержит:

```http
X-Client-Version: 1.2.0
X-Client-Build: 42
```

Версия и build читаются из метаданных установленного приложения один раз
при запуске. Для этого можно использовать уже подключённый `package_info_plus`.
Запрещено подставлять в release фиктивную версию при ошибке чтения метаданных.
Debug-сборки также передают реальную версию; скрытый обход серверной проверки
не предусматривается. Локальные API-инструменты явно задают заголовок версии.

Добавление заголовков выполняется в общем `HttpTransport`, чтобы охватить
login, refresh, обычные запросы и long polling. Обновление через GitHub
использует отдельный транспорт и не зависит от доступности рабочего API.
Версию также подставляем в `User-Agent` для диагностики; сервер проверяет
выделенный заголовок, а не разбирает `User-Agent`.

### 4.2. Информация о совместимости

Публичный метод: `GET /public/app-info`.
Не требует токена и доступен также неподдерживаемому клиенту.

```json
{
  "data": {
    "backendVersion": "1.5.0",
    "minClientVersion": "1.2.0"
  }
}
```

Ответ использует существующий `StdResponse`; дополнительные стандартные поля
могут присутствовать. Правило не зависит от пользователя и возвращается
с запретом кеширования (`Cache-Control: no-store`).

Последнюю доступную Flutter-версию, описание и установщик приложение получает
из существующего GitHub feed. Не создаём вторую систему доставки внутри API.

### 4.3. Отказ несовместимому клиенту

Возвращается HTTP `409` и машинный код ошибки:

```json
{
  "code": "CLIENT_UPDATE_REQUIRED",
  "detail": "Для работы требуется обновить приложение до версии 1.2.0 или новее.",
  "minClientVersion": "1.2.0",
  "backendVersion": "1.5.0"
}
```

Flutter распознаёт комбинацию согласованного статуса и `code`, а не текст
сообщения и не любой ответ `409`. Существующий `X-Request-ID` сохраняется.
Эта ошибка не является истечением сессии и не запускает refresh/logout.

Версия ниже минимума отклоняется до обработчика операции и изменений в БД.
Отсутствующий или некорректный заголовок на проверяемом методе также отклоняется;
возвращается `400` с отдельным `code: CLIENT_VERSION_INVALID` и полем
`minClientVersion`. Flutter показывает ошибку метаданных сборки и доступ к
обновлению; не маскирует её под сетевой сбой.

Проверка применяется к `/public/auth/*`, `/protected/*`, `/admin/*`.
Health и `/public/app-info` остаются доступны без версии. Не следует глобально
закрывать все публичные методы: bootstrap мониторинга и эксплуатационные
инструменты нужно явно учесть при выборе границ проверки. Запросы из Swagger,
тестов и служебных скриптов к проверяемым методам также передают заголовки.

Это контроль совместимости штатного клиента, а не механизм авторизации:
значение заголовка может быть подставлено вручную. Проверки токенов, прав
и входных данных продолжают действовать независимо.

## 5. Поведение Flutter

Перед загрузкой рабочих данных приложение получает метаданные своей сборки
и `/public/app-info`. Проверка выполняется при запуске и после смены сервера;
вход и восстановление сессии начинаются после успешной проверки.

| Состояние | Поведение |
| --- | --- |
| Версия подходит | Вход и работа доступны; обычное обновление добровольное |
| Версия ниже минимума | Глобальный экран требования обновления; рабочие действия недоступны |
| Сеть/сервер недоступны при запуске или восстановлении входа | Остаётся экран входа с ошибкой соединения и повтором; не сообщаем о несовместимости без ответа сервера |
| Новый метод отсутствует или ответ повреждён | Ошибка проверки на экране входа; автоматического допуска к работе нет |
| Не удалось прочитать версию сборки | Ошибка метаданных на экране входа; доступны меню настроек и обновлений |

На блокирующем экране доступны обновление, повторная проверка, настройки
сервера и выход из приложения. Отмена обновления оставляет блокировку.
Ошибка feed/скачивания не снимает её. Приложение не завершается принудительно.
Существующие проверки подписи и подтверждение установки сохраняются.

Во время работы каждый ответ API может сообщить `CLIENT_UPDATE_REQUIRED`.
Обработка централизована и охватывает также auth и long polling: приложение
останавливает новые рабочие действия и фоновые запросы, показывает один экран,
не создаёт повторяющиеся диалоги и не запускает бесконечные повторы запросов.
Событие от прежнего сервера после смены адреса не должно блокировать новую сессию.

При обязательном обновлении несохранённые данные форм отбрасываются.
Сохранение редакторов, черновики, экспорт и восстановление введённых данных
не реализуются. После обновления пользователь заново создаёт несохранённые
документы. Это согласованное упрощение владельца; сохранённые на сервере
документы не удаляются. Установка по-прежнему требует действия пользователя.

Текущую обработку недоступного API сохраняем. Новые алгоритмы повторов,
отдельный режим обслуживания и переработка сетевого UX в задачу не входят.
После возвращения API приложение должно продолжить работу без перезапуска:
совместимый клиент работает дальше, устаревший получает требование обновления.
Это проверяется при приёмке, а не считается уже подтверждённым тестом.

Уже выполняющийся запрос мог пройти проверку до смены серверной версии.
Блокировка не отменяет и не откатывает ранее принятые операции. При неопределённом
результате записи нельзя автоматически повторять её после обновления.

## 6. Ограничения минимальной версии

Условие `clientVersion >= minClientVersion` защищает от слишком старого клиента.
Оно само по себе не доказывает, что любой будущий клиент работает со старым API.

Визуальные и другие независимые от API обновления Flutter работают с текущим
сервером и выпускаются самостоятельно. Flutter с новой серверной функцией
публикуется только после установки и проверки API, необходимого для этой функции.
Совместимость такого Flutter с предыдущим API специально не добавляется.

Новый функционал backend по возможности сохраняет старые запросы: старый Flutter
может продолжать работу без доступа к новой функции. Само добавление функции
не является основанием требовать обновления всех клиентов.

`apiContractVersion`, список поддерживаемых поколений, максимальная версия
клиента и механизм определения «сервер слишком старый» в задачу не входят.
Порядок выпуска обеспечивает наличие нужного API к моменту публикации Flutter.

## 7. Git, теги и выпуск

### Flutter

1. В PR изменить публичную версию `pubspec.yaml` и описание выпуска.
2. После слияния поставить тег `vX.Y.Z`, совпадающий с версией файла.
3. Существующий CI проверяет тег, подставляет build, собирает и подписывает пакет.
4. Опубликовать готовый выпуск штатным процессом, обновить feed.
5. Проверить, что приложение видит и может установить опубликованную версию.

### Backend

1. В PR изменить версию `pyproject.toml` по характеру изменения.
2. При необходимости изменить `client_compatibility.toml`; объяснить причину
   прекращения поддержки старого Flutter в описании изменения.
3. CI проверяет код и правило совместимости, создаёт образ с SHA/digest.
4. Установить выбранную сборку существующим процессом доставки.
5. Проверить health и фактический минимум через `/public/app-info`.

Тег backend `vX.Y.Z` и GitHub Release можно использовать для обозначения
публичного выпуска, но они не обязательны для текущей доставки по SHA/digest.
Введение обязательных backend-тегов или новых workflows не входит в эту задачу.

### Координация двух частей

| Изменение | Пример | Минимальный Flutter |
| --- | --- | --- |
| Исправление backend без изменения контракта | backend `1.5.0 → 1.5.1` | Не меняется |
| Новая возможность с сохранением старых запросов | backend `1.5.1 → 1.6.0` | Обычно не меняется |
| Прекращение поддержки старого поведения клиента | Новый контракт и Flutter `1.3.0` | Явно повышается до `1.3.0` |
| Исправление только Flutter | Flutter `1.3.0 → 1.3.1` | Backend менять не требуется, если нет отдельной причины запретить старый клиент |

Повышение MAJOR и повышение минимума — отдельные решения. Для определения
SemVer сохраняются правила существующего контракта выпусков.

Порядок выпуска новой серверной функции: сначала установить и проверить API,
затем опубликовать Flutter. Если старые запросы сохранены, минимум не меняется
и старый Flutter продолжает работу без новой функции.

Если изменение несовместимо и минимум повышается сразу, выпуск проводится
вне рабочего времени. Клиентский установщик заранее собран и проверен;
после готовности API его публикуют и проверяют доступность через updater.
До публикации подходящего Flutter старые клиенты могут быть заблокированы;
рабочее использование возобновляют после завершения обоих шагов. Это намеренное
окно обслуживания, а не требование публиковать новый Flutter раньше API.
До первого рабочего ввода обе части можно обновить вместе в среде разработки.

Откат backend возвращает правило из его образа. Это не гарантирует, что уже
обновлённый Flutter совместим с возвращённым API. Проверка клиентской совместимости
добавляется к существующим условиям отката по данным и схеме БД; автоматическое
понижение версии клиента не предусматривается.

## 8. Наблюдаемость и сопровождение

В технической информации Flutter показываем установленную версию и build,
версию выбранного backend и требуемый минимум, полученные от этого сервера.
После смены сервера старые значения очищаются. При недоступности сервера
не выдаём прошлые сведения за результат текущей проверки.

В диагностике отказа полезны client version/build, backend version/SHA,
минимум и request ID. Не записываем токены или тела рабочих запросов.
Версия из заголовка проверяется по формату до использования в логах.
Ожидаемый отказ старому клиенту не должен создавать поток одинаковых аварийных
событий мониторинга.

В описание backend-выпуска добавляем: «Минимальный Flutter: X.Y.Z;
без изменений» или причину повышения. Совместимость определяет разработчик
по контракту, CI проверяет явно заданное правило и сценарии его применения.
CI не пытается самостоятельно определить несовместимость по произвольному diff.

## 9. Этапы реализации и приёмка

1. Владелец разрешил реализацию в отдельных ветках, без коммитов агента.
2. Backend: файл правила, загрузка/валидация, endpoint, проверка заголовков,
   структурированные ошибки, исключения для эксплуатационных методов.
3. Flutter: метаданные сборки, заголовки общего транспорта, предварительная
   проверка, общее состояние совместимости и блокирующий экран.
4. Интегрировать существующий updater и настройки сервера; учесть auth,
   long polling, редакторы и смену адреса.
5. Дополнить CI и инструкции выпуска, проверить обе части вместе.
6. После реализации обновить описания текущего поведения в документации.

Необходимая проверка:

- Версия равна минимуму и выше него проходит; ниже — отклоняется.
- Численное сравнение `1.10.0 > 1.9.0`; плохая конфигурация не принимается.
- Отсутствующий/испорченный заголовок отклоняется на рабочих и auth-методах.
- Отклонённая операция не меняет БД; доступ к health/app-info сохранён.
- Все пути транспорта, включая refresh и long polling, передают метаданные.
- Серверное требование обновления во время работы вызывает одну блокировку,
  прекращает повторы и не стирает токены как при logout.
- Настройки, повтор, обновление и выход доступны из блокировки.
- Смена сервера сбрасывает состояние и игнорирует запоздалые старые ответы.
- Сеть, `404`, повреждённый ответ и ошибка feed различаются с устаревшей версией.
- При обязательном обновлении несохранённые формы отбрасываются без попыток
  восстановления; сохранённые серверные данные остаются целыми. Отмена
  установки не снимает блокировку и не приводит к самопроизвольному закрытию.
- В release-сборке версия заголовка совпадает с установленным приложением;
  опубликованный подходящий установщик действительно доступен.
- Временное отключение и возвращение API переживается без перезапуска Flutter
  с текущей обработкой сетевых ошибок; при новом минимуме появляется блокировка.
- Новый Flutter с серверной функцией публикуется после готовности нужного API;
  отдельно проверен допустимый сценарий отката backend.

## 10. Согласованные решения

| Вопрос | Решение владельца |
| --- | --- |
| Имя файла/метода/заголовков | `client_compatibility.toml`, `/public/app-info`, `X-Client-Version`, `X-Client-Build` |
| Ошибка старого клиента | `409`, `CLIENT_UPDATE_REQUIRED`, поля из раздела 4 |
| Ошибка заголовка | `400`, `CLIENT_VERSION_INVALID`; build — только диагностический |
| Неуспешная предварительная проверка | Рабочие данные не загружать; дать повтор, настройки и обновление |
| Совместимый Flutter | Продолжает работать; новый выпуск предлагается добровольно |
| Flutter ниже минимума | Рабочие действия блокируются; требуется обновление |
| Несохранённые формы | Данные отбрасываются; пользователь заново создаёт документы после обновления |
| Недоступность API | Существующая обработка сохраняется; после возвращения сервера работа возобновляется без перезапуска |
| Количество API | Один обновляемый API, без параллельных версий |
| Время обновления API | Обычно вне рабочего времени; обработка требования обновления во время работы также обязательна |
| Новый Flutter с серверной функцией | Публикуется только после готовности соответствующего API |
| Независимое обновление Flutter | Визуальные и другие изменения без новых требований к API выпускаются самостоятельно |
| Debug и локальные API-инструменты | Передавать настоящую версию; без скрытого обхода; инструменты задают заголовок явно |
| Новые ENV | Не требуются; минимум хранится в файле backend |
| Начальный минимум | `1.1.0` для Flutter `1.1.0` и backend `1.0.0` |

Дополнительных вопросов к владельцу для реализации нет. Владелец разрешил
изменения исходников и проверки; коммиты выполняет самостоятельно после просмотра
diff. Установка на сервер, теги и публикация выпусков в эту задачу не входят.

## 11. Реализация и эксплуатация

- Backend загружает `client_compatibility.toml` при создании приложения.
  Минимум для выпуска backend `1.0.0` — Flutter `1.1.0`.
  Файл включён в test/runtime Docker-образы и разрешён в `.dockerignore`.
- Проверка подключена зависимостью к auth, protected и admin. Поле
  `X-Client-Version` отображается в OpenAPI; health, app-info и конфигурация
  мониторинга доступны без него. Эти эксплуатационные запросы допускаются
  без клиентских метаданных, в том числе из отдельных проверочных транспортов.
- Flutter читает метаданные через `package_info_plus` перед входом, задаёт
  заголовки в общем транспорте и проверяет `/public/app-info`. Ошибка чтения
  метаданных не подменяется фиктивной версией.
- Ответ с согласованной комбинацией статуса и кода включает глобальную
  блокировку, пересоздаёт Navigator и удаляет рабочие providers и формы.
  Токены не очищаются; фоновые запросы рабочего экрана прекращаются при его
  удалении. Новые рабочие запросы блокируются также локально в транспорте.
- Доступны существующие updater, меню настроек, повтор проверки и закрытие.
  Нативная установка и проверка подписи сохраняют существующее поведение.
- Версия приложения, backend и минимум видны в меню приложения и на экране
  блокировки. Серверные сведения относятся к выбранному адресу.
- Смена адреса создаёт новый транспорт и состояние проверки; ответы прежнего
  транспорта больше не меняют состояние приложения.
- Обычные сетевые сбои и бизнес-ошибки `400`/`409` без согласованного кода
  не включают блокировку совместимости. Существующее восстановление связи
  во время работы сохраняется. При запуске и восстановлении сессии ошибка
  соединения и повтор показываются внутри существующего экрана входа.
  Повторная проверка уже работающего совместимого клиента при сетевой ошибке
  не меняет его статус и не закрывает формы.

### Как изменить минимум

1. В PR backend изменить `[flutter].min_version` в `client_compatibility.toml`.
2. Указать причину и проверить наличие подходящего клиентского установщика
   для согласованного порядка публикации из раздела 7.
3. Пройти CI, собрать и установить новый образ штатным процессом.
4. Прочитать `/public/app-info` и проверить значение `data.minClientVersion`.

Редактирование файла на диске без перезапуска приложения не меняет действующее
правило. ENV, изменение БД и новые миграции не требуются. Для выпуска выставлены
backend `1.0.0`, Flutter `1.1.0+1` и минимум `1.1.0`; подготовлены Flutter
release notes. Тег Flutter — `v1.1.0`, номер сборки подставляет CI.
Коммиты, теги, push, установка API и публикация выполняются владельцем.

Backend `1.0.0` обозначает первый законченный выпуск до ввода в эксплуатацию.
Добавление механизма совместимости на этапе разработки не требует `2.0.0`:
старых рабочих установок нет. После ввода в эксплуатацию несовместимые изменения
оцениваются по обычным правилам MAJOR и согласованному порядку обновления.

### Swagger и служебные запросы

При вызове auth, protected и admin передавайте `X-Client-Version`, например
`1.1.0` при текущем минимуме, и при необходимости диагностический
`X-Client-Build`. В Swagger заголовок задаётся в параметрах метода. Сохранение
формального необязательного типа параметра позволяет вернуть согласованный
`400 CLIENT_VERSION_INVALID` при его отсутствии вместо стандартного `422`.
Сервер фактически требует версию на этих методах.

### Проверки

Backend: `tests/unit/test_client_compatibility.py` и
`tests/integration/api/test_client_compatibility.py`. Интеграционный тест
проверяет отсутствие записи после отказа и читает обратно успешно созданную
запись поддерживаемого клиента. Остальные API-тесты передают версию через
общую fixture. Существующий CI автоматически запускает эти тесты.

Flutter: `test/app_compatibility/`. Проверяются реальные запросы к локальному
HTTP-серверу, заголовки всех методов и auth, блокировка во время работы,
сохранение токенов, восстановление после недоступности, отказы bootstrap,
запоздалые ответы старого сервера, сброс модальной формы и доступ к updater
и настройкам. Существующий Flutter CI запускает их вместе с остальными тестами.
