# Оптимизация порядка доставок: проверка Geoapify и проект контракта

Статус: исторический план и результаты исследования. Реализация завершена 19.10.2026;
действующий контракт — [route_optimization.md](route_optimization.md).

## Согласованный сценарий

- Один склад: Россия, Ставропольский край, Михайловск, Локомотивная улица, 147.
- До 30 доставок в листе, до трёх листов в день. Каждый лист рассчитывается отдельно для одной машины.
- Начало и конец расчёта — склад. В список доставок склад не добавляется.
- Результат — рекомендуемый порядок адресов, без карты и навигации.
- Диспетчер сохраняет возможность ручной перестановки; водитель может отклоняться от порядка.
- Расчёт выполняется через backend с ключом GEOAPIFY_API_KEY из окружения.
- Оптимизация не сохраняет документ. Применение в редакторе и обычное сохранение разделены.

## Фактические результаты проверки

Проверка выполнена из локального окружения разработки, с разрешённым сетевым доступом.
Доступность с будущего сервера развёртывания ещё не проверена.

1. Ключ найден в .env; его значение не выводилось и не сохранялось в отчёты.
2. Геокодирование склада: HTTP 200, 0,85 с, один результат типа building,
   housenumber=147, match_type=full_match, confidence=1.
3. Найденные координаты: latitude=45.1373445, longitude=41.9974531.
   Это кандидат, а не подтверждённая точка въезда на склад.
4. Route Planner: HTTP 200, 0,92 с, одна машина, 30 искусственных заданий вокруг склада.
   Все 30 job_id присутствуют ровно один раз; начало и конец содержат координаты склада.
   Использованы mode=drive, type=balanced, traffic=free_flow.
5. Результат содержит actions типа start/job/end и job_id; соседние действия могут
   объединяться в один waypoint. Порядок нужно извлекать по действиям job,
   а не считать каждый waypoint отдельной доставкой.
6. Возвращённая точка на дороге немного отличается от исходных координат склада
   из-за привязки к дорожной сети. Для проверки въезда это различие важно.
7. В локальной тестовой БД один клиент, его адрес — «Рыбная 5» без населённого пункта.
   Данные БД не изменялись. Пользователь затем предоставил отдельную выборку 10 адресов.
8. В выборке 9 результатов с confidence=1, один с confidence=0.75 (Выставочная, 18).
   Добрый заезд, 17 потребовал структурированного запроса. Для всех 10 API вернул
   здания с совпадающими городом, улицей и номером дома; это не проверка фактического въезда.
9. Расчёт 10 доставок занял 0,97 с, все задания вернулись по одному разу.
   Одинаковая модель Routing API оценила исходную последовательность в 175,139 км / 10481,503 с,
   новую — в 62,093 км / 4256,309 с. Исходная последовательность — порядок сообщения пользователя,
   не эталон опытного диспетчера; пробки и время разгрузки не включены.

Искусственный тест подтверждает техническую возможность расчёта на 30 точках.
Он не доказывает точность геокодирования, качество подъездов, оптимальность
реальных маршрутов или устойчивость сервиса при длительной эксплуатации.

## Условия сервиса и ограничения

- Бесплатный план: 3000 кредитов/день, до 5 запросов/с; коммерческое использование разрешено
  при соблюдении лимитов и атрибуции. SLA для бесплатного плана не заявлен.
- Хранить результаты геокодирования разрешено с сохранением указания источников.
- На бесплатном плане требуется Geoapify attribution рядом с предоставляемой информацией;
  также требуется атрибуция OpenStreetMap и иных источников, указанных в ответе.
  Предлагаемое размещение: рядом с результатом проверки адреса и оптимизации;
  на печатном листе с результатами сервиса — в подвале с читаемыми ссылками.
- free_flow не учитывает пробки. approximated — приблизительная модель загруженности,
  а не текущие пробки в реальном времени.
- Документация о стоимости на разных страницах расходится в подсчёте повторяющихся
  координат старта/финиша. Для бюджета до уточнения используем консервативную оценку:
  (30 + 2) * 10 = 320 кредитов/расчёт, до 960/день для трёх листов без повторов.
  Фактический расход необходимо сверить в кабинете. Проверка склада — ещё один запрос геокодирования.

## Предлагаемый контракт (ещё не реализован)

### Координаты клиентов

- Существующий address остаётся строкой.
- Добавляются nullable latitude/longitude, статус unlocated/unconfirmed/confirmed,
  источник, найденный адрес и сведения об атрибуции.
- Координаты сохраняются парой с проверкой диапазонов.
- Ответ геокодера не равен подтверждению пользователем. Центр улицы/города
  нельзя автоматически принимать как точное местоположение доставки.
- При смене address прежние координаты и подтверждение перестают быть актуальными.
- Предусмотреть ручные координаты, когда геокодер не находит нужное здание.
- Координаты склада задаются на сервере отдельно, после подтверждения местоположения.

### POST /protected/delivery-route-sheets/optimize-order

Это предварительное имя нового endpoint, не существующий API.

Запрос: текущий orderedClientIds из редактора, от 2 до 30 уникальных UUID.
Не требуется сохранённый documentId: поддерживается новый документ и новые точки.
Клиенты к этому моменту существуют в справочнике, их координаты подтверждены.
Backend самостоятельно получает координаты, не доверяет координатам из Flutter.

Ответ StdResponse.data: orderedClientIds, расчётные durationSeconds/distanceMeters,
provider, trafficModel, attribution. Ответ не содержит клиентских телефонов или товаров.
Во внешний сервис передаются координаты и временные технические job_id.

Backend проверяет точную перестановку исходных ID, одну машину, начало/конец на складе,
отсутствие пропущенных и повторяющихся заданий, корректность структуры и чисел ответа.
Частичный результат отклоняется. Порядок определяется по job actions, а не waypoint count.
Ключ и полный URL с apiKey запрещено включать в логи и тексты исключений.
Ошибки авторизации провайдера, таймаута, квоты, сети и повреждённого ответа различаются
внутри backend; наружу выдаётся понятная ошибка без секретов.
Новые коды ошибок и HTTP-статусы уточняются при реализации по общим правилам проекта.

### Flutter

- Сохраняет исходный список для отмены одной автоматической перестановки.
- На запросе фиксирует ревизию состава/порядка списка. Если список изменился,
  ответ не применяется; пользователь может запустить расчёт заново.
- Переставляет существующие объекты точек без потери pointId/items.
- Повторное нажатие во время запроса блокируется.
- Ошибка оставляет список без изменений. Сохранение использует существующий API документа.
