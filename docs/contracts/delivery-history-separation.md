# Разделение истории клиентов и документов — согласованный контракт

Дата согласования: 04.11.2026.
Статус: бизнес-правила и UX согласованы; реализация ещё не начата.
Репозитории: boradydev/mountain_fairytale и boradydev/mountain_fairytale_backend.
Целевая ветка в обоих репозиториях: codex/delivery-history.

## 1. Назначение и границы

В разделе приложения «История доставок» есть два верхнеуровневых сегмента:

- **Клиенты** — найти конкретные доставки клиентов за период, увидеть исторические товары, суммы, условия и исполнителя, открыть исходный маршрут.
- **Документы** — просмотреть целые маршруты и документы самовывоза за период, открыть документ и при необходимости повторно распечатать.

Это два представления уже существующих документов и точек, а не новые продажи. Не менять правила начисления комиссий, расчётов, отмены документов, редактирования, блокировки и журналирования без явно описанных ниже оснований. Не создавать отдельные таблицы истории.

Основные связанные контракты: delivery-history.md, delivery-history-plan.md, delivery_document.md, commissions.md, anonymous-pickup.md, failed-delivery.md, free-price-items.md.

## 2. Общие правила UI

- Основная вкладка в AppShell по-прежнему называется **«История доставок»**.
- Верхняя панель по образцу CommissionsToolbar: слева SegmentedButton «Клиенты / Документы», справа выбор периода; между ними при режиме «Документы» чекбокс «Отменённые». В режиме «Клиенты» чекбокс не показывать.
- Под панелью в одной **постоянной по занимаемому месту области**: для «Клиентов» поле поиска, для «Документов» фильтр «Все / Доставки / Самовывозы». Переключение не должно сдвигать вниз список карточек. Поиск ограничен по ширине, не растягивается на всё окно. Использовать существующие Material 3 и общие компоненты.
- Состояние выбранного периода общее для двух режимов и не сбрасывается при переключении. По умолчанию последние 30 календарных дней, включая сегодняшний; обязательный период не длиннее 12 календарных месяцев, границы включительны, високосные годы учтены.
- Повторно использовать showAppDateRangePicker / AppDateRangeDialog. В самом диалоге добавить **необязательную для других экранов** кнопку «Сбросить», выровненную слева отдельно от правых «Отмена» и «Подтвердить» (в BaseFormDialog уже есть leadingAction). Кнопка восстанавливает последние 30 дней **в черновике диалога**, не закрывает его и не применяет изменения до подтверждения. Она не сбрасывает поиск, тип документа или чекбокс.
- Режимы независимо запоминают свои фильтры при переключении; выбранный период один. Поиск клиентов имеет обычное действие очистки поля. Для документов «Все» — вариант по умолчанию, отменённые по умолчанию скрыты.
- Сортировка обоих списков: plannedDate DESC, createdAt DESC, далее детерминированные идентификаторы для стабильной пагинации.
- Загрузка по **50 записей** с автоматическим подгружением следующих 50 при приближении к концу прокрутки (оба режима); без кнопки «Показать ещё». Не делать параллельных запросов одной страницы, не применять запоздавшие ответы после изменения фильтра, не дублировать строки, показывать индикатор и возможность повторить ошибочную подгрузку, не стирая уже загруженное. Предусмотреть пустое состояние и повтор первичной загрузки.
- Интерфейс Desktop-first, но сохранять адаптивность при уменьшении окна и масштабировании текста; избегать overflow и скачков высоты панели.

## 3. Режим «Клиенты»

### 3.1. Данные

- Одна строка списка = **одна точка доставки конкретному клиенту** из delivery_route_sheet, а не документ целиком. Один маршрут с десятью клиентами даёт десять записей.
- Самовывозы и анонимные покупки **не входят** в историю клиентов.
- Отменённые маршруты **не входят** в историю клиентов; отдельного фильтра для их включения здесь нет. Деактивированные клиенты **входят** всегда, без чекбокса.
- Включать недоставленные точки с причиной и товарами. Сумма заказа видна как исходная, перечёркнута и не прибавляется к обороту документа; использовать уже согласованные правила недоставки. Не считать недоставку фактически совершённой продажей.
- Список показывать даже при пустом поиске (все подходящие доставки периода). Период ограничивает plannedDate документа.
- У каждой записи один pointId и её исходный deliveryDocumentId; порядок — plannedDate DESC, createdAt DESC, deliveryDocumentId DESC, затем стабильный порядок точек (position и pointId).

### 3.2. Поиск

Одна строка поиска по имени, адресу, дополнительной информации доставки и телефону. Ищем **конкретные точки доставки** за период:

1. Если запрос совпал с *актуальными* данными связанной карточки клиента (clients), показать **все его точки доставки** в выбранном периоде.
2. Если запрос совпал с *историческими* полями конкретной точки, показать **именно эту точку** (не остальные доставки данного клиента только из-за исторического совпадения).
3. Если одновременно выполнены оба условия, точку вывести **один раз**.
4. Показывать в результатах **только сохранённые исторические поля** точки, независимо от того, чем найдено совпадение.
5. Подстрочный поиск имени, адреса, уточнения — без учёта регистра; телефон — по нормализованным цифрам. Символы %, _ и обратная косая черта должны интерпретироваться буквально, а не как SQL-wildcard. Ограничение длины поиска согласовать с текущим API (до 500 символов); debounce как в действующем экране.

Пример: текущая карточка клиента называется «Вектор», а в январской точке исторически «Иванов», адрес «Ленина, 10». Поиск «Вектор» находит все доставки этого clientId; поиск «Ленина, 10» по историческому значению находит январскую точку, но не другие доставки с другим историческим адресом. При поиске отображается «Иванов, Ленина, 10».

### 3.3. Компоновка одной записи

Слева — **компактная кликабельная миникарточка маршрута**, справа — знакомая **раскрывающаяся карточка доставки клиента**, максимально похожая на свёрнутую точку из RoutePointsList в режиме просмотра.

- Слева: **плановая дата**, водитель, машина, **общая сумма маршрута**. Без отдельной кнопки «Открыть»; нажатие на любую свободную область миникарточки открывает исходный маршрут целиком в существующем режиме просмотра.
- Справа: историческое имя, адрес и памятка/причина, сумма **этой точки** и краткая информация о позициях/оплате, как в карточке точки маршрута. Шеврон раскрывает подробности: «Задание для водителя», все товарные строки с сохранёнными названиями, количеством, ценами, уточнениями, суммами, телефон, способ оплаты и исторический торговый представитель.
- Не показывать номер точки маршрута и drag handle; не показывать кнопки редактирования, удаления или изменяемые формы. В истории оплату и представителя показывать **простым текстом**, не disabled dropdown.
- Переиспользовать визуальные и форматирующие части RoutePointsList / TaskItemRow, но **не подключать логику редактирования OrderPointsProvider или reorder** к истории. При необходимости выделить небольшой повторно используемый read-only компонент, не создавать большой второй конструктор.
- Размер: свернутая карточка клиента задаёт естественную высоту, миникарточка — компактна и подстраивается под высоту строки, без искусственного увеличения всего списка. Начальные верхние границы выровнены. При раскрытии правой карточки **левая остаётся компактной** и не растягивается на высоту товаров. Длинные тексты обрезать с подсказкой; при узком окне допустим адаптивный переход на вертикальную компоновку.
- Миникарточка не показывает дату создания, только плановую дату. Это **не отменяет** отображения обеих дат в полной истории документов.

## 4. Режим «Документы»

- Один элемент = **целый документ**: delivery_route_sheet или pickup_sheet. Не группировать по дням, не создавать сводные карточки дня.
- В области под верхней панелью фильтр типа **«Все / Доставки / Самовывозы»**; текстового поиска клиентов здесь нет. «Все» включает оба типа.
- Чекбокс «Отменённые»: выключен по умолчанию; при включении показывает и действующие, и отменённые документы, визуально обозначая статус.
- Сортировка: plannedDate DESC, createdAt DESC, deliveryDocumentId DESC. Период выбирает по plannedDate.
- Использовать имеющиеся карточки HistoryDocumentCard: тип документа, **подписанные плановая дата и дата создания**, общий итог, количество клиентов (маршрут) или покупок (самовывоз), водитель и машина только у доставки. Сумма — всего документа, по текущим правилам исключая недоставленные точки.
- Нажатие на карточку открывает соответствующий сохранённый документ целиком в уже существующем режиме просмотра, доступна действующая печать. В общем списке нет встроенных блоков поиска и matchedClients.
- **Отдельная задача существующего плана:** показывать обе даты и в карточках диалога документов дня. Сейчас там указана дата создания, а плановая — лишь в заголовке дня.

## 5. Исторические снимки клиента в точках маршрута

### 5.1. Новые данные

Точка доставки хранит следующие данные на момент сохранения новой точки:

- неизменная связь с клиентом через client_id;
- сохранённое имя клиента;
- сохранённый телефон;
- сохранённый адрес;
- сохранённое уточнение доставки (delivery_details);
- nullable **ID представителя**, закреплённого за клиентом.

Названия колонок выбрать в согласии с текущим snake_case-кодом (например, snapshot_client_name, snapshot_phone, snapshot_client_address, snapshot_delivery_details, snapshot_sales_representative_id). Снимок хранится **в points**, не в справочнике клиентов и не в комиссии. Идентификаторы точек/документов и имеющиеся товары сохраняются.

При чтении старого маршрута (просмотр, редактирование, история, PDF) имя, телефон, адрес и уточнение берутся **из снимка точки**, а не из текущей карточки клиента. Не подменять его при повторных GET, загрузке справочников, повторном сохранении или смене актуальных клиентских реквизитов. Это необходимо для воспроизводимости печатной формы.

Связь по client_id сохраняется, чтобы искать историю по актуальным данным клиента. Имя торгового представителя **не снимок**: хранится ID, отображаемое имя разрешается через справочник представителей при чтении (включая деактивированных). При отсутствии ID показывать «Не указан». Имя может обновляться при переименовании одного и того же представителя — это согласовано.

Не смешивать **исторически назначенного представителя точки** с **получателем комиссии** из point_commissions: это разные поля с потенциально разными значениями. Правила существующих начислений не меняются.

### 5.2. Выбор и редактирование представителя

- **Новая точка доставки**: представитель доступен для выбора и при создании нового маршрута, и при **добавлении новой точки в режиме редактирования существующего маршрута**. Новизна определяется отсутствием сохранённого `pointId`, а не общим режимом документа. Первоначально предложен представитель из актуальной карточки клиента.
- **При выборе представителя для новой точки** применить существующую семантику: сразу обновить назначение **в карточке клиента**, синхронизировать локальную новую точку, а **при сохранении документа** зафиксировать выбранный ID в историческом снимке новой точки. Отмена несохранённого документа не откатывает уже выполненный PATCH карточки клиента (как у способа оплаты).
- **При просмотре маршрута и для каждой уже сохранённой точки (`pointId` существует) в режиме редактирования** dropdown представителя **выключен**; он показывает исторический ID точки и текущее имя из справочника. Изменить представителя сохранённой точки через этот control нельзя.
- **При добавлении новой точки в существующий маршрут** её исторические сведения клиента и выбранный представитель фиксируются при первом успешном сохранении этой точки. Комиссия новой точки рассчитывается по действующим правилам для новой точки. Уже сохранённые точки, их исторические представители и комиссии не изменяются.
- Сохранение документа **без изменения набора точек** не переписывает снимки и не перерассчитывает комиссию. Функцию изменения исторического представителя существующей точки и перенос прошлых комиссий **не реализовывать** в этой задаче.

### 5.3. Миграция существующих данных

Рабочая база уже эксплуатируется. Добавить **новую последовательную Alembic-ревизию** после актуального head, не переписывать прошедшие миграции.

Для **всех существующих точек доставки** (включая отменённые документы) один раз заполнить новые поля из **текущего состояния связанной записи clients** на момент миграции, включая текущий sales_representative_id. Это сознательно принятое приближение: старые достоверные значения могут быть недоступны. Не пытаться восстанавливать представителя из commission recipient; не менять его снимок комиссии.

Для самовывозов без клиента исторические клиентские поля и ID представителя должны оставаться отсутствующими/nullable; не придумывать клиента. Не удалять/пересоздавать документы, точки, товары, суммы, комиссии или аудиторские события. В миграции предусмотреть безопасное поведение при большом объёме, целостность FK и повторяемость применения в обычном Alembic workflow.

Далее новые точки получают снимок при создании, исторические не обновляются автоматически. Определить nullable/ограничения так, чтобы старые анонимные самовывозы и пустые разрешённые значения не ломались.

## 6. Backend и API

### 6.1. Выдача истории клиентов

Предпочтительная архитектура: **новый защищённый GET /protected/client-delivery-history** с обязательными date_from/date_to, search (необязательный), offset/limit (по умолчанию 50, максимум API 100). Одна запись ответа — точка доставки. Формат стандартного StdResponse с total, offset, limit и data.deliveries.

Для записи вернуть минимум:

- pointId, clientId, deliveryDocumentId;
- исторические clientName, phone, clientAddress, deliveryDetails, составной адрес для карточки;
- исторический salesRepresentativeId, разрешённый salesRepresentativeName;
- plannedDate и createdAt исходного документа; driverName, carModelAndNumber, **documentTotalAmount** (всего маршрута);
- isDelivered, nonDeliveryReason, memo, paymentMethodId/Name, **totalAmount** исходного заказа, items;
- items с имеющимися историческими productName, itemId, productId, quantity, price, amount, isFreePrice, driverNote.

Денежные значения отдавать decimal-строками и округлять строки перед суммированием согласно действующим контрактам. Не сериализовать денежные суммы через float на сервере. Не загружать целый документ для каждого элемента истории (избегать N+1).

Считать total по **точкам после фильтров**, не по документам. Поиск: OR между актуальным совпадением по client_id и **совпадением исторических полей именно этой точки**; без дублирования. SQL-параметры безопасны, экранировать спецсимволы шаблона. Проверять права через действующую схему protected API.

### 6.2. Выдача истории документов

Сохранить работающий **GET /protected/delivery-history**, текущий envelope, сортировку, правила итогов и доступность старых клиентов API. Добавить фильтр типа документа (например, document_type со значениями all/delivery_route_sheet/pickup_sheet), по умолчанию оба типа. Новый Flutter не передаёт search и не использует matchedClients.

До согласованного обновления API не ломать прежний параметр search и matchedClients, если существующие клиенты на него рассчитывают. Отдельно обеспечить сериализацию createdAt в Flutter: сейчас сервер уже отдаёт его, но HistoryDocument его не читает. Клиентский поиск не должен фильтровать результаты режима «Документы».

### 6.3. Совместимость и изменение API документа

- Расширить доменную модель Point, слой репозитория, схемы и сериализацию/чтение полного документа так, чтобы **текущие поля** clientName/phone/address/clientAddress/deliveryDetails/salesRepresentativeId отражали сохранённое состояние точки, а не новые реквизиты из clients. Справочник по-прежнему нужен для поиска и управления клиентами.
- Учитывать аудит, create/update idempotency, revision/edit-lock и документные снимки в events; не превращать обычную загрузку данных в запись событий. Сохранить прежние UUID itemId/pointId.
- Так как backend и Flutter должны согласованно читать новые снимки, проверить действующий механизм client_compatibility.toml и версионирования. Выпускать совместно, без продакшен-миграции в рамках одной реализации контракта.

## 7. Flutter и печать

- Изменить DeliveryHistoryScreen/Provider/Repository, добавив два независимых режима, фиксированную область фильтров, переключатель документов и бесконечную подгрузку. Отдельные модели ответа для клиентских точек и документов. Сохранять фильтры при переключении.
- Выделить повторно используемый read-only визуальный участок карточки RoutePointsList: по возможности без дублирования форматирования товаров/памятки/недоставки. В истории клиентов не создавать искусственный OrderPointsProvider ради просмотра.
- В конструкторе dropdown представителя **доступен для новых точек**: как при создании маршрута, так и для только что добавленной точки при редактировании существующего маршрута (`pointId == null`). Для сохранённых точек (`pointId != null`) и в режиме просмотра dropdown отключён. В истории — обычный текст. При деактивации представителя исторический ID по-прежнему отображается.
- Полный маршрут, повторное открытие и PDF **всегда используют снимок** имени, телефона, адреса, уточнения доставки; название представителя — по сохранённому ID. Печатная форма не должна меняться из-за изменения реквизитов клиента в справочнике.
- Для истории документов показать обе даты; то же исправить в DayDocumentsDialog (плановая и создана с явными подписями). Полноценная печать остается в текущем документном экране, новую систему печати не создавать.

## 8. Проверки и критерии готовности

Нужны backend unit/integration и Flutter widget/provider/API тесты, а также ручная проверка печати.

1. Клиент найден по текущему новому имени после полной смены данных; показаны **все** доставки периода, каждая со **старыми** сведениями.
2. Поиск по старому адресу/телефону/имени/уточнению находит **только совпавшие исторические точки**, если актуальные сведения не совпадают. Несколько совпадений не дублируют точки.
3. Пустой поиск показывает точки, включая деактивированных клиентов. Самовывозы и отменённые документы скрыты в истории клиентов. Недоставленные точки видны с причиной и перечёркнутой суммой, но не учитываются в сумме маршрута.
4. Маршрут с несколькими клиентами даёт несколько клиентских строк и **одну** документную строку. Итоги документа не пересчитываются по поисковому совпадению.
5. Из миникарточки открывается правильный полный маршрут. Раскрытие правой карточки не вызывает навигацию и не растягивает левую. Без drag handles, disabled dropdown, лишних кнопок. Длинный текст и узкие окна не ломают разметку.
6. В режиме «Документы» фильтры «Все / Доставки / Самовывозы», отменённые, оба типа и сортировка работают; обе даты видны; самовывоз открывается и печатается.
7. Период общий, лимит 12 месяцев, сброс внутри диалога действует только после «Подтвердить», отмена не применяет черновик.
8. Автоподгрузка по 50, правильные total/offset, отсутствие дубликатов, работа с ошибкой страницы и с устаревшими конкурентными ответами; проверка пустых и длинных историй.
9. Создание маршрута и добавление **новой** точки при редактировании фиксируют данные клиента и выбранного представителя в этой точке при сохранении; выбор новой точки сразу обновляет карточку клиента. Изменение карточки клиента впоследствии **не меняет** просмотр, PDF и сохранённые точки. При редактировании сохранённой точки представитель недоступен для изменения; её снимок и комиссия не переписываются. Проверить отдельно новую и уже сохранённую точки внутри одного редактируемого маршрута.
10. Миграция на копии существующей БД: backfill из актуальных clients, целостность старых маршрутов/самовывозов, сохранность pointId, itemId, процентов, получателей и сумм комиссий. Регрессия сохранения новых товаров со свободной ценой.
11. Полная проверка связанных существующих тестов документов, комиссий, печати и совместимости; визуальная ручная проверка нескольких состояний карточек и PDF.

## 9. Порядок работ и выпуск

1. Реализовать SQL-снимки и миграцию, модели и API; тесты backend.
2. Подключить Flutter-модели полного документа, историю клиентов, историю документов, карточки и переключатели; widget-тесты.
3. Перевести PDF и существующий просмотр на снимки, добавить обе даты; регрессионные проверки.
4. Проверить diff в обоих репозиториях, обновить старый delivery-history.md и общий план клиентских этапов: пометить разделение и снимки реализованными **только после фактического завершения**.
5. Не развёртывать рабочую базу, не применять миграцию на production, не выпускать Flutter релиз без отдельного решения владельца. Коммиты реализации и релиз — после ревью владельцем.

**Важно:** контракт фиксирует согласованные решения. Не расширять задачу отчётностью, новым поиском для документов, сменой комиссионных получателей, редактированием исторических представителей или отдельным интерфейсом ручной коррекции снимков без нового согласования.
