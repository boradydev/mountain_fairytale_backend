# Контракт API сотрудников

Статус: реализовано в backend и Flutter. Ставка комиссии необязательна;
участие любой роли определяется наличием ставки и активностью.
Правила начислений определены в `commissions.md`.

Основные источники текущего API:
- `src/feat/employees/api/employee_routers.py`
- `src/feat/employees/api/employee_schemas.py`
- `src/common/api/routers.py`
- `src/common/api/deps.py`
- `src/common/api/exc_map.py`

Общее поведение диалогов Flutter — «ОК / Сохранить», поиск дубликатов через
600 мс, выборочный PATCH и индикаторы — описано в
[контракте форм справочников](entity_forms.md).

## Назначение и термины

- Сотрудник — учётная запись, через которую пользователь входит в приложение.
- `role` (`admin` или `employee`) задаёт права учётной записи. В текущем API
  создавать и изменять сотрудников может только администратор.
- Торговый представитель — отдельная сущность с собственным UUID, ставкой
  комиссии и выборочным назначением клиентам через `salesRepresentativeId`.
- Менеджер офиса — сотрудник, которому бизнес хочет начислять комиссию за
  офисные продажи. Правила исторических начислений со всего оборота, прекращения
  новых начислений после деактивации и месячного отчёта определены в
  `docs/contracts/commissions.md`.

## API

### Общие правила

- Все маршруты имеют префикс `/admin/employees` и требуют access token с ролью
  `admin`. Для обычного сотрудника ответ — `403`; без действительного токена —
  `401`.
- Токен передаётся в `Authorization: Bearer <token>` или cookie
  `access-token`.
- Успешные ответы обёрнуты в `StdResponse`; полезная нагрузка находится в
  `data`.
- Поля request/response используют `camelCase`. Исключение — query-параметр
  `include_deactivated`, имя которого задано так в router.
- `employeeId` — UUID. Пароль и его хеш никогда не возвращаются.
- Физического удаления нет. Сотрудника деактивируют через `PATCH isActive`;
  запись и история сохраняются.
- `username` уникален среди всех сотрудников, в том числе деактивированных.
- Создание через API создаёт сотрудника с ролью `employee`; назначение роли
  `admin` телом запроса не поддерживается.
- `commissionPercent` входит в ответ для всех учётных записей, в том числе
  `admin`; значение — число от 0 до 100 включительно либо `null`.
  При создании поле необязательно: отсутствие поля и явный `null` означают
  отсутствие комиссии. `0` — заданная нулевая ставка, а не отсутствие комиссии.

Форма объекта сотрудника в ответах:

```json
{
  "employeeId": "uuid",
  "username": "manager",
  "role": "employee",
  "commissionPercent": 5.0,
  "isActive": true,
  "createdAt": "2026-10-12T10:00:00"
}
```

### `GET /admin/employees`

Возвращает `data.employees` — массив объектов сотрудника.

- `include_deactivated` — необязательный boolean, по умолчанию `false`.
- При `false` включены только активные сотрудники; при `true` — также
  деактивированные.
- Пароль и `passwordHash` отсутствуют в ответе.
- Текущая сортировка — `createdAt` по убыванию. Для одинаковых дат стабильный
  порядок не гарантирован контрактом реализации.

### `GET /admin/employees/{employee_id}`

Возвращает объект сотрудника в `data`, независимо от активности.

- `200` — сотрудник найден.
- `401` — нет действительной авторизации.
- `403` — роль не `admin`.
- `404` — сотрудник не найден.
- Некорректный UUID в пути отклоняется валидацией FastAPI.

### `GET /admin/employees/check-duplicate?username={username}`

- Доступен только администратору. Обязательный `username` — строка 1–50 символов.
- Ищет точное совпадение логина среди активных и деактивированных сотрудников.
- `200`: `data` содержит сотрудника либо `null`, если совпадений нет.
- Flutter проверяет изменённый логин после паузы 600 мс; при сохранении
  использует актуальный результат либо дожидается выполняющегося поиска. Результат
  показывает статус записи и предлагает открыть её либо «Активировать и выбрать».
- Восстановление выполняет `PATCH isActive=true` для найденного UUID, сохраняя
  логин, пароль и ставку комиссии, включая `null`. После успеха список карточек
  обновляется; dropdown на экране сотрудников не используется.
- Поиск не заменяет проверку уникальности на сохранении: `POST`/`PATCH` всё
  равно отправляются на сервер; `409` отображается внутри поля локальным текстом
  «Такой логин уже существует». Серверные сообщения в UI не выводятся.

### `POST /admin/employees/create`

Создаёт активного сотрудника. Пример тела:

```json
{
  "username": "manager",
  "password": "secret",
  "commissionPercent": 5.0
}
```

- `username`: обязательная строка длиной 1–50 символов; строка только из
  пробелов недопустима.
- `password`: обязательная строка длиной 0–50 символов; пустой пароль
  допускается текущей схемой.
- `commissionPercent`: необязательное число от 0 до 100 включительно либо
  `null`; по умолчанию `null`. В ответе поле присутствует всегда.
  Например, `{ "username": "director", "password": "secret" }` создаёт
  сотрудника без комиссии; ответ содержит `"commissionPercent": null`.
- Сервер назначает `employeeId`, `createdAt`, `role=employee` и
  `isActive=true`.
- `201` — созданный объект возвращается в `data`.
- `401` / `403` — нет авторизации / роль не `admin`.
- `409` — такой `username` уже занят, включая имя деактивированного сотрудника.
- `422` — обязательное поле отсутствует или значение не проходит валидацию.

### `PATCH /admin/employees/{employee_id}`

Частично изменяет сотрудника. Допустимые поля: `username`,
`commissionPercent`, `isActive`. Нужно передать хотя бы одно поле. Примеры:

```json
{ "commissionPercent": 7.5 }
```

```json
{ "commissionPercent": null }
```

Последний пример отключает комиссию для новых документов. Отсутствие
`commissionPercent` в PATCH сохраняет текущую ставку; `0` устанавливает
нулевую ставку. Очистка ставки не удаляет исторические начисления.

```json
{ "isActive": false }
```

- `200` — актуальный объект сотрудника возвращается в `data`.
- `401` / `403` — нет авторизации / роль не `admin`.
- `403` — запрещена деактивация учётной записи `admin`.
- `404` — сотрудник не найден.
- `409` — новый `username` занят другим сотрудником.
- `422` — пустое тело, `null` для `username` или `isActive`, пустое имя или
  процент вне диапазона 0–100. Явный `null` для `commissionPercent` допустим.
- `role` этим маршрутом не меняется.

### `PUT /admin/employees/{employee_id}/change-password`

Устанавливает пароль сотрудника; тело — `{ "password": "новый пароль" }`.
Строка длиной 0–50 символов, включая пустую, допускается текущей схемой.

- `200` — `data` равен `null`, `message` — `"Пароль сотрудника изменён."`.
- `401` / `403` — нет авторизации / роль не `admin`.
- `404` — сотрудник не найден.
- `422` — некорректное или отсутствующее поле.
- Пароль не отражается в ответе; прочие атрибуты сотрудника не должны
  изменяться.

## Сценарии управления учётными записями

1. Администратор открывает список: получает только активных сотрудников.
2. Чтобы найти уволенного или отключённого сотрудника, администратор передаёт
   `include_deactivated=true`; сохранённого сотрудника можно открыть по UUID.
3. Администратор создаёт сотрудника, указывая логин, пароль и при необходимости
   процент; клиент
   сохраняет возвращённый UUID, не пытается назначать роль.
4. Администратор меняет ставку или логин через `PATCH`; после ответа клиент
   обновляет состояние из тела ответа либо повторным `GET`.
5. Администратор отключает/восстанавливает учётную запись через `isActive`.
   Операция не удаляет запись. Отключённый сотрудник исключается из списка по
   умолчанию.
6. Администратор меняет пароль по отдельному маршруту. Клиент не получает и не
   сохраняет пароль из ответа.
7. Клиент обрабатывает `401`, `403`, `404`, `409` и `422` как разные случаи;
   при `409` показывает конфликт логина, а при `422` — ошибку поля/запроса.

## Комиссионный процент сотрудника

- `commissionPercent=null` — комиссия не назначена. Активность и права входа
  сотрудника от этого не меняются.
- Число от 0 до 100 включительно — назначенная ставка. `0` является
  самостоятельным значением: сотрудник участвует в начислениях с нулевой ставкой.
- Роль (`admin` или `employee`) определяет права, но не участие в комиссии.
  Активная учётная запись любой роли с заданной ставкой включается в снимки
  новых документов. Деактивированная учётная запись новые начисления не получает.
- Администратор может назначить, изменить или очистить ставку, в том числе
  собственной учётной записи. Запрет деактивации `admin` сохраняется.
- Каждый участвующий сотрудник получает свой процент от полного оборота
  документа; проценты нескольких сотрудников складываются, а не делятся между ними.
- Назначение, изменение и очистка ставки действуют на новые документы.
  Получатели и ставки существующих документов сохраняются; при редактировании
  их суммы пересчитываются по сохранённым ставкам. Назначение комиссии не
  добавляет сотрудника в старые документы задним числом.
- Сотрудник с очищенной ставкой остаётся в отчёте за месяц с сохранёнными
  начислениями, включая нулевые. Подробные условия состава отчёта — в
  `commissions.md`.

## Отображение управления сотрудниками во Flutter

- Экран «Сотрудники» доступен отдельной вкладкой только администратору;
  backend дополнительно защищает `/admin/employees`.
- Сотрудники отображаются прокручиваемым списком карточек `AppBaseCard`.
  Первым элементом используется `AddActionButton` «Добавить сотрудника».
- `LabeledCheckboxToggle` «Деактивированные» добавляет к активным сотрудникам
  деактивированных. Это фильтр справочника, независимо от участия в комиссии.
- В карточке показываются логин, статус, роль администратора при наличии и
  «Комиссия: N%» либо «Без комиссии» при `null`.
- Нажатие открывает существующий `EmployeeDialog`; создание открывает его без
  сотрудника. Смена пароля доступна из диалога редактирования через
  `EmployeePasswordDialog`.
- Поле «Комиссия» необязательно, без звёздочки; подсказка поясняет:
  «Пусто — без комиссии. 0% — участие с нулевой ставкой».
- При редактировании `null` отображается пустым полем. Очистка поля отправляет
  явный `commissionPercent: null`; отсутствие поля в PATCH не очищает ставку.
- Для непустого поля сохраняются проверка числа и диапазон 0–100. Пустое поле
  проходит валидацию; ошибки поля показываются стандартным состоянием поля.

## Миграция базы разработки

- Изменяется существующая миграция, задающая колонку
  `employees.commission_percent`: колонка nullable, без подстановки
  нуля вместо отсутствующей ставки. Проверить исходное создание и последующее
  изменение этой колонки в цепочке миграций.
- База разработки/тестирования будет пересоздаваться штатным процессом проекта;
  перенос и сохранение существующих данных не требуются. Для новой схемы
  bootstrap-администратор создаётся без комиссии (`null`); ставку можно
  назначить позднее через API или форму.
- Ставки в исторических снимках начислений остаются обязательными числами:
  отсутствие комиссии означает отсутствие снимка для этого сотрудника.

## Ссылки на связанные сущности

- Торговый представитель управляется через `/protected/sales-representatives`;
  клиент получает необязательный `salesRepresentativeId` через API клиентов.
- Поле комиссии и UUID торгового представителя не являются полем/UUID
  `Employee`; эти сущности нельзя смешивать.

## Проверка API-контракта

- Проверять только публичные HTTP-маршруты, статус и тело ответа.
- Проверять создание без `commissionPercent`, с явным `null` и с числом;
  ответ всегда содержит поле, пароль отсутствует. Проверять запись чтением
  через `GET`.
- Проверять `commissionPercent` на границах 0 и 100, а также отказ для
  отрицательного значения и значения больше 100.
- Проверять список с параметром по умолчанию и с
  `include_deactivated=true`, а также получение деактивированного сотрудника по
  UUID.
- Проверять обновление username/процента/активности и чтение сохранённого
  состояния после `PATCH`. Отдельно проверять назначение ставки, очистку
  явным `null`, сохранение ставки при отсутствии поля и отличие `0` от `null`.
- Проверять назначение и очистку ставки у `admin` с сохранением запрета его
  деактивации. Во Flutter проверять пустое поле и подпись «Без комиссии».
- Проверять `401` без токена, `403` от обычного сотрудника, `409` на дублирующий
  username, `404` для неизвестного UUID и `422` для некорректных тел.
- Проверять смену пароля без раскрытия пароля и без побочных изменений прочих
  полей.
- Проверять создание и редактирование `commissionPercent` как поля сотрудника;
  вычисление начислений этим API не проверяется и не определяется.
