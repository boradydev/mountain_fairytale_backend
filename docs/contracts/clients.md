## Общие правила

- Все endpoints находятся под `/protected/clients` и требуют действительный
  access token. Токен передаётся как `Authorization: Bearer <token>` или cookie
  `access-token`.
- Доступ разрешён любому аутентифицированному пользователю; отдельная роль
  администратора для клиентов не требуется.
- Идентификаторы клиента, торгового представителя и способа оплаты — UUID,
  передаваемые в JSON как строки.
- JSON-поля используют `camelCase`.
- Успешные ответы обёрнуты в `StdResponse`; полезная нагрузка находится в
  `data`. В ответе списка `offset`, `limit` и `total` находятся на верхнем
  уровне.
- Клиенты физически не удаляются. Запись выключается через `isActive: false`
  и может быть включена повторно. История и UUID при этом сохраняются.
- Телефон уникален. Создание или смена телефона на уже занятый возвращает
  `409`.
- Ответ `ClientResp` содержит:

```json
{
  "clientId": "uuid",
  "name": "ООО Пример",
  "phone": "+70000000000",
  "address": "Москва, улица Пример, 1",
  "sleepingThresholdDays": 30,
  "lastDeliveryDate": null,
  "lastDeliveryQuantity": null,
  "cooldownUntil": null,
  "salesRepresentativeId": null,
  "salesRepresentativeName": null,
  "defaultPaymentMethodId": null,
  "defaultPaymentMethodName": null,
  "createdAt": "2026-10-12T10:00:00",
  "isActive": true
}
```

  Это пример формы ответа, а не фиксированные значения. `lastDeliveryDate` и
  `lastDeliveryQuantity` возвращаются, но клиент не может менять их через
  API клиентов. Названия связей в ответе доступны только для чтения; при
  отправке передаются ID.

## Получение списка

### `GET /protected/clients`

Query-параметры:

- `include_deactivated` — boolean, по умолчанию `false`. При `false` выдаются
  только активные клиенты; при `true` — активные и деактивированные.
- `offset` — число пропускаемых записей, по умолчанию `0`, минимум `0`.
- `limit` — размер страницы, по умолчанию `100`, минимум `1`.
- `search` — необязательная строка поиска по имени, телефону и адресу;
  правила приведены ниже. Передаётся как query-параметр GET в соответствии
  с общим подходом приложения.

Список отсортирован по `createdAt` по убыванию, затем по `clientId` по
убыванию. `total` — число записей после фильтра по активности, но до
применения `offset` и `limit`.

Пример:

```json
{
  "offset": 0,
  "limit": 100,
  "total": 1,
  "data": {
    "clients": [
      {
        "clientId": "uuid",
        "name": "ООО Пример",
        "phone": "+70000000000",
        "address": "Москва, улица Пример, 1",
        "sleepingThresholdDays": 30,
        "lastDeliveryDate": null,
        "lastDeliveryQuantity": null,
        "cooldownUntil": null,
        "salesRepresentativeId": null,
        "salesRepresentativeName": null,
        "defaultPaymentMethodId": null,
        "defaultPaymentMethodName": null,
        "createdAt": "2026-10-12T10:00:00",
        "isActive": true
      }
    ]
  }
}
```

Пустой список — `data.clients: []`, `total: 0`. Недопустимые `offset` и
`limit` дают `422`.

## Получение одного клиента

### `GET /protected/clients/{client_id}`

Принимает UUID в пути. Клиент возвращается независимо от `isActive`.

- `200` — клиент найден, объект `ClientResp` находится в `data`.
- `401` — нет действительной авторизации.
- `404` — UUID не найден.
- `422` — некорректный UUID.

## Создание

### `POST /protected/clients/create`

Обязательные поля тела:

- `name`: строка длиной 1–120 символов;
- `phone`: строка длиной 1–32 символа;
- `address`: строка длиной 1–500 символов;
- `sleepingThresholdDays`: целое число от 0 до 3650 включительно.

Необязательные nullable-поля:

- `cooldownUntil`: дата и время либо `null`;
- `salesRepresentativeId`: UUID либо `null`;
- `defaultPaymentMethodId`: UUID либо `null`.

При указании ID связанная запись должна существовать. Её активность не
проверяется: существующую деактивированную запись можно назначить.
Списки справочников по умолчанию возвращают активные записи. Если у клиента
уже сохранена деактивированная связь, API клиента всё равно возвращает её ID и
имя; клиентская форма должна сохранить/показать текущее значение, хотя его
нельзя выбрать как новое из активного списка.

- `201` — созданный клиент находится в `data`; он активен, а
  `lastDeliveryDate` и `lastDeliveryQuantity` равны `null`.
- `401` — нет действительной авторизации.
- `409` — телефон уже занят.
- `422` — ошибка валидации либо передан несуществующий ID связи.

`clientId`, `createdAt`, `isActive` и поля последней доставки назначаются
сервером и не передаются при создании.
Неизвестные поля и поля только для чтения в POST/PATCH отклоняются с `422`.

## Даты и время

Принятое для приложения правило: сервер и приложение работают с локальным
временем сервера; клиент не переводит эти значения между часовыми поясами.
Сериализованный `datetime` передаётся как ISO 8601 без timezone offset, например
`2026-10-12T10:00:00`, без суффикса `Z`. Значения с `Z` или timezone offset
в POST/PATCH отклоняются с `422`. При отправке `cooldownUntil` клиент
формирует такое же локальное время. Контракт исходит из того, что приложение
используется рядом с сервером и не обслуживает удалённых пользователей в иных
часовых поясах.

## Частичное обновление

### `PATCH /protected/clients/{client_id}`

Можно передать любое непустое подмножество следующих полей:

- `name`: строка 1–120 символов, `null` запрещён;
- `phone`: строка 1–32 символа, `null` запрещён;
- `address`: строка 1–500 символов, `null` запрещён;
- `sleepingThresholdDays`: целое число 0–3650, `null` запрещён;
- `cooldownUntil`: дата и время или `null` (явный `null` очищает значение);
- `salesRepresentativeId`: UUID или `null` (явный `null` снимает связь);
- `defaultPaymentMethodId`: UUID или `null` (явный `null` снимает связь);
- `isActive`: boolean; `false` деактивирует клиента, `true` повторно
  активирует его.

Отсутствующее поле не меняется. `{}` отклоняется с `422`. Поля
`lastDeliveryDate` и `lastDeliveryQuantity` через этот endpoint не обновляются.
Связанные ID проверяются на существование; деактивированные связи допустимы.

- `200` — актуальный `ClientResp` находится в `data`.
- `401` — нет действительной авторизации.
- `404` — клиент не найден.
- `409` — телефон занят другим клиентом; существующее значение клиента
  остаётся прежним.
- `422` — валидация, ошибка доменного обновления или несуществующая связь.

## Проверка похожего клиента

### `GET /protected/clients/check-duplicate`

Обязательны query-параметры `name`, `phone`, `address` с ограничениями длины,
как при создании. Ищутся активные и деактивированные клиенты.

- `200` и объект `ClientResp` в `data`, если найдено совпадение;
- `200` и `data: null`, если совпадений нет;
- `401` — нет действительной авторизации;
- `422` — параметр отсутствует или не проходит валидацию.

Проверка дублей остаётся GET-запросом с query-параметрами, как и другие
функции приложения.

Фактическое поведение текущей реализации поиска:

- применяется PostgreSQL `pg_trgm` `similarity` к переданным строкам имени,
  телефона и адреса;
- пороги включительные: имя `>= 0.35`, телефон `>= 0.50`, адрес `>= 0.25`;
- совпадение есть, если порог пройден минимум по двум из трёх полей;
- явного предварительного форматирования/нормализации входных строк в коде
  поиска нет;
- рассматриваются активные и деактивированные записи;
- если кандидатов несколько, выбирается запись с максимальной суммой трёх
  similarity score; при равенстве — с более поздним `createdAt`, затем с
  большим `clientId`.

Это поведение относится к отдельной проверке дублей при создании. Оно не
задаёт автоматически поведение нового поиска по списку.

## Поиск в списке

`search` реализован в `GET /protected/clients`.

```text
GET /protected/clients?search=иван&include_deactivated=false&offset=0&limit=100
```

- `search` — необязательная строка длиной до 500 символов; после trim пустое
  значение означает поиск без фильтра.
- По имени и адресу — нечувствительное к регистру частичное вхождение
  (`%строка%`), чтобы результат находился по началу или середине слова.
- По телефону — частичное совпадение по цифрам после удаления всех символов,
  кроме цифр, и из запроса, и из сохранённого номера.
- Условия имени, телефона и адреса объединяются через OR: достаточно
  совпадения по одному полю.
- Поиск применяется до пагинации; `total` считает найденные строки после
  фильтра активности и поиска. Существующая сортировка сохраняется.
- Частичное вхождение используется без typo-tolerant fuzzy-подбора. Это
  предсказуемо и покрывает запрос «найти с полуслова». Исправление опечаток
  контрактом не предусмотрено.
- Поиск списка остаётся GET-запросом с query-параметрами, как и другие функции
  приложения.

Причина серверного поиска: список уже имеет пагинацию, поэтому поиск только по
загруженной странице не найдёт клиента на другой странице. Flutter выполняет поиск на сервере по имени, адресу и телефону,
включая страницы, которые ещё не загружены клиентом.

## Интеграция Flutter

- Клиенты используют UUID-строки и серверные `createdAt` / `isActive`.
- Справочники формы клиента загружаются через защищённые API; передаются
  только ID. Названия связей читаются из ответа сервера.
- Сохранённая деактивированная связь отображается как текущее значение;
  её можно сохранить или снять. Новые значения берутся из активного списка.
- Деактивация и активация используют PATCH `isActive`. Физического удаления нет.
- Проверка похожего клиента запускается после ввода имени, телефона и адреса,
  повторяется перед созданием и показывает статус найденной записи.
  Совпадение требует подтверждения создания; уникальный телефон защищён HTTP 409.
  В раскрытом предупреждении доступны добавление существующего клиента и
  открытие его карточки; для неактивного — активация и добавление.
- Панель выбора подписана `Клиент *`. Кнопки общего `AppDropdown` расположены
  в порядке: показать неактивных, редактировать, создать. Такой же порядок
  используется у представителя и способа оплаты в форме клиента.
- Телефон в форме автоматически отображается как `+7 999 123 45 67`;
  поддерживается вставка номера с `8` или `+7`. Создание и редактирование
  отправляют полный номер без пробелов (`+79991234567`). Форматирование
  само по себе не меняет сохранённые номера остальных клиентов.
- Справочники в форме поддерживают создание и редактирование через API;
  используются существующие диалоги `SalesRepDialog` и `PaymentMethodDialog`.
  Выбранные связи сохраняются у клиента при отправке всей формы.
- PATCH различает пропуск поля и явный `null`: смена способа оплаты не меняет
  имя, телефон, адрес, представителя или отсрочку.
- Форма допускает `sleepingThresholdDays` от 0 до 3650; по умолчанию 7.
- Серверный поиск использует задержку после ввода и игнорирует устаревшие
  ответы. Список панели выбора может включать деактивированных клиентов;
  их можно открыть и активировать, но нельзя добавить в новый маршрут.
- Полный активный список для контроля засыпания загружается по страницам.
- Demo-аналитика представителей и demo-маршруты остаются отдельными модулями;
  они не являются источником данных API клиентов. Старые числовые clientId
  в demo-маршрутах читаются как строки для совместимости.

## Ошибки

У бизнес-ошибки тело имеет форму `{"detail": "..."}`. Известные ответы:

- `401` — `Unauthorized`;
- `404` — `Client not found`;
- `409` — `Client phone already exists`;
- `422` — доменная ошибка, несуществующая связанная запись или ошибка
  валидации FastAPI/Pydantic. Для ошибки валидации `detail` может быть
  массивом, а не строкой.

Клиенту следует ориентироваться на HTTP-код и не полагаться на текст
`detail` для бизнес-логики.

## Проверки

`tests/integration/api/test_client_routers.py` проверяет создание, получение,
PATCH, конфликт телефона и сохранение состояния после конфликта,
деактивацию/активацию, пагинацию, фильтр активности, проверку похожего клиента,
авторизацию, ошибочные и неизвестные UUID, границы полей, поиск по имени,
адресу и цифрам телефона, literal `%` / `_`, trim, пустой результат,
фильтрацию до пагинации и `total`. Проверяются деактивированные связи,
несуществующие ID связей, чтение названий, очистка nullable-полей и
сохранение остальных полей при PATCH.

Flutter-тесты клиентов проверяют HTTP-запросы, UUID, JSON-обёртки,
пагинацию, PATCH, проверку дублей, формы, конфликт телефона,
сохранение деактивированных связей и устойчивость к устаревшим ответам.
