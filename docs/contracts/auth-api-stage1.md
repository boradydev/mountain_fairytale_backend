# API авторизации: первый этап

Изменения от 11.10.2026 реализуют backend-часть требований auth.md.
Flutter ещё не изменён. Интеграционные тесты подготовлены, но не запускались:
по договорённости их запускает пользователь.

## HTTP-интерфейс

- GET /public/auth/users: без токенов, StdResponse[AuthUsersResp], data.usernames: list[str], только активные
  username, включая администратора. Полный список в порядке created_at ASC,
  employee_id ASC. Пустой список: data: {"usernames": []}.
- GET /protected/me: проверенный Bearer access token или access-token cookie.
  StdResponse.data содержит employeeId, username, role из БД. Отсутствующий
  сотрудник: 404; отсутствующий или невалидный токен: 401.
- POST /public/auth/login: неизвестный username, неверный пароль и деактивация
  дают одинаковый 401. Пустой пароль разрешён при установленном пустом пароле.
- POST /public/auth/refresh: деактивация даёт 403; невалидный, истёкший токен
  или токен неправильного типа — 401. Ранее выданные токены не отзываются.
- POST /protected/me/logout и PUT /protected/me/change-password сохраняют
  существующие пути. Logout удаляет cookies без серверного отзыва JWT.

Все /protected endpoints теперь проверяют JWT, а не только наличие строки.
Проверяются подпись, exp, тип токена и UUID сотрудника. Деактивация не вводит
немедленный отзыв access token: он действует до exp согласно контракту.

## Настройки и администратор

ACCESS_TOKEN_EXPIRE_MINUTES=15, REFRESH_TOKEN_EXPIRE_DAYS=90.
Эти значения используются по умолчанию и проверяются при запуске. Другие
значения в ENV вызовут понятную ошибку конфигурации. Явные секунды в JwtSettings
сохранены для специальных тестовых токенов. Локальный .env обновлён с 30 до 90 дней.

Bootstrap ищет администратора по роли независимо от актуального username,
не перезаписывает пароль и не создаёт нового администратора после переименования.
При существующих старых дубликатах выбирается самый ранний администратор;
автоматическое изменение существующих учётных записей не выполняется.
API создаёт только сотрудников с ролью employee; деактивация admin запрещена.
Пустые и состоящие из пробелов username отклоняются при создании и изменении.

Восстановление пароля работает и после переименования администратора:

```powershell
.venv\Scripts\python.exe -m src.common.cli.main admin change-password
```

## Проверка пользователем

```powershell
.venv\Scripts\python.exe -m pytest tests/integration/api
```

Новые проверки находятся в tests/integration/api/test_auth_contract.py.
Они охватывают список, порядок при равных датах, переименование, пустой результат,
вход с пустым паролем, одинаковые отказы входа, /me, недействительные JWT,
TTL, повторный refresh старым токеном, восстановление через месяц,
деактивацию после загрузки dropdown, смену собственного пароля, logout,
ограничения username и администратора, повторный bootstrap и CLI-восстановление.
В старом тесте входа деактивированного сотрудника ожидаемый статус изменён
с 403 на 401 согласно требованию об одинаковых ошибках входа.

Используется существующая отдельная API-тестовая PostgreSQL. Тест пустого списка
временно меняет флаги активности и восстанавливает их в finally; bootstrap/CLI
тест также восстанавливает исходные username и password hash администратора.
Не запускайте эти интеграционные тесты параллельно на одной тестовой БД.
