# История клиентов и документов

Реализация в `codex/delivery-history`. Согласованные бизнес-правила и UX:
[разделение истории](delivery-history-separation.md).

## Общие правила API

Оба GET защищены существующей авторизацией, не меняют документы, события,
revision или edit-lock. Обязательны `date_from` / `date_to`; границы включительны,
выборка по `plannedDate`, максимум 12 календарных месяцев с учётом високосных лет.
`offset >= 0`, `1 <= limit <= 100`. Денежные значения — decimal-строки;
сумма каждой товарной строки округляется до копеек до сложения.

## История клиентов

`GET /protected/client-delivery-history`, `limit=50` по умолчанию.
Ответ: стандартный StdResponse, `total`, `offset`, `limit`, `data.deliveries`.
Одна запись — точка маршрута, включая недоставленные точки и деактивированных
клиентов. Отменённые маршруты и все самовывозы исключены.
Сортировка: `plannedDate DESC, createdAt DESC, deliveryDocumentId DESC, position, pointId`.

Необязательный `search` до 500 символов ищет имя, адрес, уточнение доставки
без учёта регистра и телефон по цифрам. `%`, `_`, обратная косая черта буквальны.
Уточнение BUG-001 от 07.11.2026: телефонная ветка включается только для запроса,
который после `strip()` содержит хотя бы одну ASCII-цифру `0–9` и состоит только
из таких цифр и разделителей: обычный пробел, `+`, `-`, `(`, `)`, `.`.
Разделители удаляются, минимальной длины нет: `01` и `+7 (999) 123-45-67`
ищутся по текущему и историческому телефону. `QA-CORE-01`, `QA-TEST-0001`,
`Ленина, 10`, `12A34`, `+`, `---` телефонную ветку не включают.
Текстовая ветка всегда использует полную строку после `strip()`; пустая строка
сохраняет поиск без фильтра. Это правило не является валидацией номера клиента.
Совпадение актуальных реквизитов clients находит все точки данного клиента
за период. Совпадение снимка находит только конкретную историческую точку.
OR этих условий не дублирует точки. `total` считается после фильтров по точкам.

Запись содержит `pointId`, `clientId`, `deliveryDocumentId`, исторические
`clientName`, `phone`, `clientAddress`, `deliveryDetails`, составной `address`,
`salesRepresentativeId` и разрешённый из справочника `salesRepresentativeName`.
Контекст маршрута: `plannedDate`, `createdAt`, `driverName`, `carModelAndNumber`,
`documentTotalAmount`, `clientsCount`. Количество клиентов — все точки исходного
маршрута, включая недоставленные, независимо от поиска и пагинации. Поля точки: `isDelivered`, `nonDeliveryReason`, `memo`,
`paymentMethodId/Name`, исходная `totalAmount` и `items`. У товаров сохраняются
`itemId`, `productId`, `productName`, `quantity`, `price`, `amount`,
`isFreePrice`, `driverNote`. Общая сумма маршрута не ограничивается поиском
и исключает недоставленные точки; их собственная исходная сумма остаётся видна.

## История документов и совместимость

`GET /protected/delivery-history` сохраняет прежний envelope `data.documents`,
поля ответа и default `limit=25`. Flutter явно запрашивает по 50.
Новый `document_type`: `all` (по умолчанию), `delivery_route_sheet`, `pickup_sheet`.
`include_cancelled=false` по умолчанию; true добавляет отменённые документы.
Одна запись — целый документ, сортировка:
`plannedDate DESC, createdAt DESC, deliveryDocumentId DESC`.
Сумма и количество относятся ко всему документу, независимо от фильтра поиска.

Прежний `search` и `matchedClients` оставлены для старых API-клиентов.
Legacy-поиск использует то же правило включения телефонной ветки; параметры,
поля ответа, текстовые поля поиска и фильтры сохранены.
При пустом поиске `matchedClients=[]`; новый экран документов не передаёт поиск
и не показывает вложенные совпадения. Реквизиты совпавшей точки читаются из снимка.
`createdAt` читается Flutter-моделью и показывается с подписью рядом с плановой датой;
в диалоге документов дня и миникарточке маршрута истории клиентов показывается
только плановая дата с подписью «Дата».

## Снимки и интерфейс

Новая ревизия `1e8c3a5d907b` после `7d1f4e09ac32` добавляет в points
nullable-снимки имени, телефона, адреса, уточнения и ID представителя.
Backfill использует clients для всех прежних клиентских точек, включая отменённые.
Анонимные самовывозы остаются без клиента и снимка. Таблицы истории не создаются.
Новые точки фиксируют снимок один раз; сохранённые точки его не обновляют.
Полный GET, список документов дня, история и PDF используют эти сведения.
Представитель разрешается по историческому ID, включая деактивированного.
Получатель и ставки комиссии — отдельные данные; правила начисления не изменены.

Flutter: сегменты «Клиенты / Документы», общий период, независимые фильтры,
фиксированная область поиска/типов документов, ленивая автоподгрузка по 50.
Ошибку страницы можно повторить с сохранением предыдущих строк; запоздавшие
ответы отбрасываются, ID исключают дубликаты. Клиентская карточка раскрывает
read-only задание, миникарточка открывает исходный маршрут. Документная карточка
открывает существующий просмотр с печатью.

`showAppDateRangePicker` / `AppDateRangeDialog` получили необязательный `showReset`:
«Сбросить» слева возвращает последние 30 календарных дней только в черновике.
Отмена его не применяет. Сохранённая точка блокирует выбор представителя;
новая точка доступна для выбора и внутри редактируемого существующего маршрута.

Механизм `client_compatibility.toml` проверен: расширения API обратно совместимы,
существующий минимум 1.3.0 не повышен. Новый Flutter требует backend с этой
миграцией и endpoint; публикация обоих проектов должна быть согласована вместе.
Реализация находится в GitHub. Версии выпуска, фактическое применение миграций к
рабочей БД, сборка релиза и приёмка должны подтверждаться отдельно.
