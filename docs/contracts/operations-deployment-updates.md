# Эксплуатация, мониторинг, резервное копирование и обновления

Статус: актуальный контракт по реализованной схеме и оставшимся работам.
Согласован: 21 октября 2026 года. Обновлён по реализации: 23 октября 2026 года.
Область: FastAPI backend, PostgreSQL, Flutter Windows, GitHub Actions,
GitHub Releases, Timeweb S3, GlitchTip на собственном VPS.

Документ фиксирует действующую реализацию доставки backend, резервного
копирования и обновления Flutter. Статус проверок приведён в разделах 3 и 11.
Требования к GlitchTip и эксплуатационным алертам в разделах 4–5 согласованы,
но ещё не реализованы. Flutter v1.0.0 опубликован; ввод на всех рабочих ПК
и приёмка обновления с публичного feed остаются отдельными шагами. Изменения проходят через PR.
Подробные команды находятся в эксплуатационных инструкциях, а этот контракт
определяет поведение, границы автоматизации и ответственность владельца.

Подтверждённые решения:

- Локальный сервер: Windows → Hyper-V → Ubuntu Server → Docker Engine
  и Docker Compose. WSL для рабочего развёртывания не используется.
- Мониторинг: GlitchTip на собственном VPS, проекты backend, Flutter и operations.
  В приложениях используются совместимые Sentry SDK.
- Backend: один контейнер API и один worker Uvicorn. Второй процесс
  для отказоустойчивости на первом этапе не добавляется.
- Приложение и рабочая PostgreSQL остаются в локальной сети.
  VPS используется для мониторинга, а не для размещения рабочего API/БД.
- Локальный API: HTTP без домена и без Caddy, доступ только из разрешённой
  локальной подсети. Для публичного GlitchTip предусматривается HTTPS;
  VPS имеет отдельный домен и Caddy.
- Одновременно работают максимум три пользователя.
- Основная ветка обоих репозиториев — `master`. Отдельная ветка `deploy`
  в целевой схеме не используется. Изменения поступают через PR из коротких
  рабочих веток; merge в `master` сам по себе не выпускает production.
- Backend: автоматические проверки и сборка, production-деплой вручную.
- Flutter: автоматические проверки и сборка, версия по тегу `vX.Y.Z`,
  публикация вручную; установка обновления пользователем добровольная.
- Первые полноценные версии обеих частей — `1.0.0`. Версии ведутся независимо
  по `MAJOR.MINOR.PATCH`, источником служит файл проекта. Backend доставляется
  по полному commit SHA и digest без обязательного тега; Flutter — по тегу
  `vX.Y.Z`, совпадающему с версией `pubspec.yaml`.
- Плановый бэкап: один раз в сутки в 17:00. Хранение последних 30 успешно
  загруженных ежедневных копий по количеству; часовой график отменён.
- Часовой пояс бэкапов: `Europe/Moscow` (17:00 по Москве).
- Если плановый бэкап пропущен, при следующем запуске выполняется одна
  догоняющая копия после готовности БД; пропущенные дни не воспроизводятся.
- Windows-ПК может штатно выключаться на ночь, по выходным и в другие дни.
  Постоянная доступность приложения не требуется. Отсутствие сигналов,
  недоступность API и пропуск расписания из-за выключенного ПК не являются
  авариями. Отдельный uptime/heartbeat-мониторинг локального приложения не вводится.
- Сборка и разрешение деплоя просматриваются в GitHub. Результат фактической
  установки пока доступен на VM и через health endpoint. Диагностика приложения
  и критические эксплуатационные алерты будут централизованы в GlitchTip.
  Дальнейшую доставку уведомлений пользователь настраивает отдельно;
  Telegram — пожелание, конкретная интеграция пока не выбрана и не проверена.

## 1. Цель и границы

Сделать эксплуатацию приложения простой и предсказуемой:

- видеть ошибки backend и Flutter в одном сервисе;
- восстанавливать базу из внешнего резервного хранилища;
- выпускать backend через GitHub Actions;
- обновлять Windows-приложение по кнопке без ручной распаковки ZIP;
- сохранять понятный путь восстановления после неудачного обновления.

Стартовая конфигурация рассчитана на один сервер и один процесс FastAPI.
Kubernetes, кластер PostgreSQL, собственная установка Sentry, отдельный стек
сбора логов и аналитика пользовательского поведения в первый этап не входят.

Бизнес-журнал действий сохраняет существующее назначение и хранение в БД.
Техническая диагностика не заменяет этот журнал.

## 2. Целевая архитектура

| Компонент | Решение | Назначение |
| --- | --- | --- |
| Серверная среда | Hyper-V + Ubuntu Server на Windows-ПК | Локальная VM, работающая вместе с включённым ПК |
| Развёртывание | Docker Compose | Управление сервисами одного сервера |
| Backend | Контейнер FastAPI, один worker | API и существующие уведомления дашборда |
| База | Контейнер PostgreSQL с постоянным томом | Рабочие данные |
| Резервное копирование | Отдельный контейнер с расписанием | Создание дампов и загрузка в S3 |
| Внешнее хранение | Приватный бакет Timeweb S3 | Резервные копии |
| Ошибки и алерты | GlitchTip на собственном VPS, три проекта | Backend, Flutter и эксплуатационный контроль через Sentry SDK |
| Обычные серверные логи | Python logging → stdout/stderr → Docker | Локальная диагностика с ротацией |
| Сборка backend | GitHub Actions → GHCR | Версионированные Docker-образы |
| Деплой backend | Локальный Python-скрипт + systemd timer в Ubuntu VM | Получение разрешённого образа из `deployment/production.json` |
| Выпуски Flutter | GitHub Actions → GitHub Releases | Установщик и описание обновления |
| Обновление Flutter | WinSparkle 0.9.2 через Windows-мост, Inno Setup | Добровольная установка с проверкой Ed25519-подписи |
| HTTPS мониторинга | Caddy на VPS | Публичный HTTPS-доступ к GlitchTip |
| Локальный API | HTTP по закреплённому адресу VM | Без домена и без Caddy, только разрешённая локальная подсеть |

Для Flutter выбран прямой нативный мост к WinSparkle; пакет `auto_updater`
не используется. Установка A и обновление до B проверены на Windows.
GlitchTip/Caddy в таблице — согласованный следующий этап, а не запущенные сервисы.

### Потоки данных

```text
Flutter Windows ── API ──> FastAPI ──> PostgreSQL
       │                     │            │
       └── ошибки ──> GlitchTip на VPS <─┘  └── pg_dump ──> backup ──> Timeweb S3

GitHub Actions ──> публичный GHCR
Ручной backend workflow ──> deployment/production.json <── timer Ubuntu VM
Ubuntu VM ──> скачивание выбранного digest ──> бэкап/миграция ──> API в Compose
Flutter CI по тегу ──> подписанные Actions-артефакты
Ручная публикация ──> GitHub Releases ──> WinSparkle ──> установщик Flutter
```

Backend не раздаёт установщики Flutter и не проксирует их скачивание.
Сервис обновления клиента не зависит от работоспособности API.

## 4. Backend: логи и GlitchTip

**Статус:** stdout/stderr и ротация Docker реализованы. Отправка в GlitchTip,
обогащение событий окружением/версией и единый request ID — оставшаяся работа
этапа мониторинга; требования ниже не означают, что SDK уже подключён.

### Локальные логи

- Существующий Python logging остаётся основой логирования.
- Приложение пишет в stdout/stderr. Docker ограничивает размер и число
  файлов логов; диск не должен заполняться бесконечным выводом.
- Диагностика включает время, уровень, источник сообщения, окружение,
  версию backend и идентификатор запроса, когда он применим.
- Неожиданное исключение записывается со стеком вызовов.
- Клиент не получает внутренний traceback или секреты в ответе API.

### Отправка ошибок

- Используется отдельный проект GlitchTip для backend через `sentry-sdk`.
- В событиях указываются версия выпуска и окружение.
- Неожиданные ошибки, в том числе перехваченные общим обработчиком,
  должны попадать в GlitchTip без дублирования одного исключения.
- Ожидаемые бизнес-ошибки и обычные отказы авторизации не создают поток аварий.
- Для расследования ошибки API используется общий идентификатор запроса,
  доступный серверной диагностике и клиенту. Точное имя заголовка и способ
  передачи фиксируются при реализации в API-контракте.
- Сбой GlitchTip или отсутствие интернета не должны нарушать обработку запросов.

На старте приоритет — сбор ошибок. Полная трассировка всех запросов и
профилирование не обязательны. Logfire остаётся возможным следующим шагом,
если появится конкретная потребность в подробном анализе задержек.

## 5. Flutter: диагностика

**Статус:** следующий этап, отложенный до подготовки VPS. Централизованная
диагностика Flutter/backend/backup и события диска пока не подключены.

- Используется отдельный проект GlitchTip для Flutter через `sentry_flutter`.
- Перехватываются необработанные Dart/Flutter-ошибки.
- Неожиданные ошибки, которые приложение уже перехватило, отправляются явно
  в точке обработки: например, сбой печати или формирования документа.
- Ожидаемые ошибки валидации, неверный пароль, отмена пользователем и
  обработанная временная недоступность сети не считаются авариями автоматически.
- Событие содержит версию приложения, окружение, экран/операцию и при
  необходимости технический ID пользователя и идентификатор API-запроса.
- Одна ошибка не должна отправляться повторно на каждом слое приложения.
- Недоступность GlitchTip или интернета не блокирует запуск и работу приложения.

Firebase Analytics и Crashlytics в стартовое решение для Windows не входят.
Аналитика использования рассматривается отдельной задачей, если она понадобится.

### Данные и секреты

В обоих проектах GlitchTip исключаются пароли, access/refresh tokens,
заголовки авторизации, телефоны, адреса и содержимое документов. Проверяются
также URL/query-параметры, сообщения исключений и breadcrumbs.
Автоматические скриншоты и запись сессий не включаются на первом этапе.

Секреты не коммитятся и не выводятся в workflow. Серверные параметры остаются
в серверном окружении, CI-секреты — в GitHub Secrets. Клиентская конфигурация
SDK мониторинга не должна содержать административные токены.

Уведомления настраиваются для новых и значимых повторяющихся ошибок.
Сборка и деплой контролируются пользователем в GitHub. Остальные технические
события и критические алерты доступны в GlitchTip; дальнейший канал доставки
пользователь настраивает отдельно.

Под уведомлениями различаются:

- результаты CI, сборки и ручного выпуска — доступны в GitHub Actions;
- ошибки работающего приложения — доступны в GlitchTip независимо от CI;
- ошибки выполняемых операций: запущенный бэкап завершился неудачно,
  на работающей системе заканчивается диск — поступают в отдельный проект
  GlitchTip `operations`.
  Источники этих событий реализуются явно; сами по себе они не появляются
  ни в GitHub, ни от подключения Sentry SDK к FastAPI.

Административный блок дашборда приложения не обязателен для первого этапа.
GlitchTip является основным местом просмотра критических алертов.
Поддержка конкретного способа доставки в Telegram проверяется отдельно;
документ не предполагает наличие готовой встроенной интеграции.

### Источники критических алертов

- Backup сообщает об ошибке создания, загрузки или проверки копии.
- Отдельная проверка диска сообщает о нехватке места до полного заполнения.
  Контролируются диск Ubuntu VM, место на Windows-томе с VHDX и диск VPS.
  Проверка внутри VM не заменяет проверку свободного места на Windows-хосте.
- Проверки диска выполняются только при работающей системе. Отсутствие
  результатов проверок при выключенном ПК не создаёт события.
- Внешние проверки доступности API, heartbeat-сигналы и оповещения о пропуске
  расписания бэкапа не вводятся. Ночь, выходные и выключенный ПК — штатный режим.
- О полной недоступности приложения в рабочее время пользователь узнаёт
  от сотрудников. Не требуется автоматически отличать отказ от планового
  выключения ПК. Flutter показывает понятную ошибку соединения без потока
  одинаковых аварийных событий.
- API не публикуется в интернет; VPS не обращается к приватному IP офиса.
- Повторения группируются, применяются пороги/задержки против кратких сбоев
  и потока одинаковых сообщений. Восстановление состояния также фиксируется.
- Конкретные пороги диска и интервалы локальных проверок фиксируются
  при реализации. Проверки работают независимо от запуска CI.

GlitchTip на единственном VPS не может гарантированно сообщить о собственном
полном отказе. Второй независимый мониторинг для него не входит в первый этап;
это ограничение архитектуры. Доставка алертов из офиса зависит от связи.
Отсутствие событий само по себе не интерпретируется как сбой.

### GlitchTip на собственном VPS

- GlitchTip разворачивается отдельно от локального приложения через Docker
  Compose, с собственной PostgreSQL. База мониторинга не совмещается с рабочей БД.
- VPS выделен только под мониторинг и работает на Ubuntu Server.
  Рекомендуемая установка — один Docker Compose: Caddy, GlitchTip,
  его PostgreSQL и необходимые задания обслуживания.
  Отдельная установка Caddy/PostgreSQL пакетами ОС не требуется.
- На VPS используется отдельное доменное имя и HTTPS через Caddy.
  Порты GlitchTip и PostgreSQL доступны только во внутренней Docker-сети;
  наружу публикуются HTTP/HTTPS Caddy. Данные БД и сертификатов Caddy постоянные.
- Создаются отдельные проекты backend, Flutter и operations; адрес сервиса и DSN
  задаются конфигурацией приложений.
- Используются Sentry SDK, но не предполагается полное совпадение функций
  GlitchTip с Sentry. Неподдерживаемые возможности SDK отключаются;
  автоматическое отслеживание сессий не включается.
- До внедрения проверяются доставка ошибок из локальной сети, читаемые стеки,
  версии, окружения и уведомления на выбранных версиях SDK и GlitchTip.
- Обычные логи backend продолжают храниться локально с ротацией.
  На первом этапе GlitchTip принимает исключения, значимые диагностические
  события и критические алерты; отправка всего stdout/DEBUG-потока не включается.
  Если понадобится поиск по всем текстовым логам, подключение их приёма
  в GlitchTip рассматривается отдельно с ограничением объёма и срока хранения.
  При отсутствии интернета немедленная доставка ошибок на VPS не гарантируется;
  гарантированная долговременная очередь событий не входит в первый этап.
- Для VPS описываются обновления, ограничение срока хранения событий,
  контроль свободного места и резервное копирование данных/настроек GlitchTip.
- Отказ VPS не влияет на локальные API, PostgreSQL и работу Flutter.

Предлагаемый начальный размер VPS (оценка для небольшого потока ошибок,
не гарантия производительности и не официальный минимум GlitchTip):

| Вариант | CPU | RAM | SSD | Назначение |
| --- | --- | --- | --- | --- |
| Практический минимум | 1 vCPU | 1 ГБ + 1–2 ГБ swap | 20 ГБ | GlitchTip и PostgreSQL при малом числе событий, требуется контроль памяти |
| Рекомендуемый старт | 1–2 vCPU | 2 ГБ + 1–2 ГБ swap | 25–30 ГБ | Запас для ОС, PostgreSQL, прокси и обновлений |

На старте без тяжёлого профилирования и записи сессий; Valkey добавляется
только при необходимости. Предлагаемый срок хранения событий — 30 дней,
с контролем свободного места. Поток повторяющихся ошибок ограничивается,
иначе число пользователей само по себе не ограничивает расход ресурсов.
Точный тариф и срок хранения пока не утверждены.

## 6. PostgreSQL: резервное копирование

### Создание и хранение

Реализация — самостоятельный проект `postgres_s3_backup` со своим образом,
зависимостями, тестами и CI. Репозиторий
[`boradydev/postgres_s3_backup`](https://github.com/boradydev/postgres_s3_backup)
создан, образ `ghcr.io/boradydev/postgres_s3_backup:0.1.0` опубликован.
Backend подключает готовый образ через `compose.backup.yaml` с закреплённым
digest; обновление backup-образа выполняется отдельно от выпуска API.
Параметры Timeweb, ввод ключей и состояние проверки описаны в
[инструкции бэкапов](../operations/backups.md).

- Отдельный контейнер подключается к PostgreSQL по внутренней сети Compose.
- Создаётся логический дамп `pg_dump` в custom-формате для `pg_restore`.
- Версия клиента pg_dump согласуется с версией сервера PostgreSQL.
- Рабочая база не останавливается для обычного резервного копирования.
- Сначала успешно создаётся локальный временный файл, затем он загружается
  в приватный бакет Timeweb S3 по HTTPS.
- Каждая копия имеет уникальное имя с окружением и временем UTC.
- После загрузки проверяются наличие объекта, размер и контрольная сумма
  доступным для выбранного S3-клиента способом. ETag не считается универсальным
  эквивалентом контрольной суммы файла.
- Временные файлы очищаются после подтверждения загрузки; их объём ограничен.
  При ошибке загрузки предусматриваются повторы без бесконечного заполнения диска.
- Для S3 используются отдельные учётные данные с необходимыми правами
  на бакет резервных копий. Доступ к бакету не передаётся Flutter.
- Нужные для восстановления роли, расширения и параметры PostgreSQL
  описываются отдельно: дамп одной базы не является копией всего кластера.

Копирование файлов работающего Docker volume не заменяет штатный бэкап БД.
Бэкап обязан работать по локальному расписанию независимо от GitHub Actions.

### Базовое расписание и срок хранения

| Тип | Расписание | Хранение |
| --- | --- | --- |
| Ежедневная копия | Один раз в сутки в 17:00 | `BACKUP_KEEP`, по умолчанию 30 успешных копий |
| Ручная копия | По команде оператора | `BACKUP_MANUAL_KEEP`, по умолчанию 30 |
| Перед деплоем/откатом | Перед заменой API; для deploy до миграции | `BACKUP_PREDEPLOY_KEEP`, по умолчанию 30 |

Поведение задаётся ENV с документированными значениями по умолчанию.
`BACKUP_TIME=17:00`, `BACKUP_TIMEZONE=Europe/Moscow`, лимиты категорий
30/30/30 настраиваются независимо в серверном `.env`. Подключение к БД
и обязательные S3-параметры должны быть заполнены; ключи хранятся в серверном `.env`
и передаются только backup-контейнеру.
Контейнер постоянно работает с внутренним планировщиком, а не стартует
из cron на каждую копию. Разовые операции запускаются через `compose run --rm`.
Ежедневное расписание не зависит от GitHub и не требует ручного запуска.

Расписание подтверждено: ежедневно в 17:00 по `Europe/Moscow`.
Время в именах объектов всегда UTC. В 17:00 ожидается простой приложения,
но технически бэкап не зависит от отсутствия пользователей.
Задание выполняется, если Windows-ПК, VM и Docker запущены.
Пропуск из-за выключенного ПК допустим: алерта нет, старые копии не удаляются.
Возраст копии в календарных днях сам по себе не является аварией, поскольку
в нерабочие дни новые данные могут не появляться.

Порядок ротации: создать новую копию → загрузить и проверить её в S3 →
только после успеха удалить самые старые копии сверх настроенного лимита в той же
категории и окружении. При ошибке создания, загрузки или проверки ничего
не удаляется. Предмиграционные копии не вытесняют ежедневные.
Неудачное удаление старых объектов не отменяет успешный бэкап: сохраняются
лишние копии, фиксируется ошибка очистки, повтор выполняется позже.
Операции всех категорий сериализуются общей блокировкой состояния.
Сроковая lifecycle-очистка S3 не должна независимо удалять копии в обход
этой политики. Лимит означает число успешных копий, а не число дней.
Создание копий всех категорий сериализуется общей блокировкой тома состояния.

Подтверждено: при пропуске планового времени из-за выключенного ПК после
следующего запуска выполняется одна догоняющая копия, когда PostgreSQL готова.
За несколько пропущенных дней создаётся одна копия текущего состояния БД,
а не отдельные копии за прошлые дни.

- Состояние последнего успешно обработанного планового срока сохраняется
  постоянно и переживает перезапуск/пересоздание контейнера backup.
- При запуске проверяется последний наступивший срок 17:00 по Москве.
  Если он ещё не покрыт успешной ежедневной или догоняющей копией,
  выполняется догоняющее задание. В новой установке без истории — одна
  начальная копия после готовности БД.
- Успех фиксируется только после создания, загрузки и проверки копии в S3.
  После успеха повторный перезапуск не создаёт ещё одну копию за тот же срок.
- Догоняющая копия входит в общий лимит 30 ежедневных копий.
  Ручная и преддеплойная копии не заменяют выполнение планового задания.
- После догоняющей копии сохраняется обычное расписание: если следующий
  срок 17:00 ещё впереди, в это время создаётся следующая плановая копия.
- Догоняющее и плановое задания не выполняются параллельно. Повторы при
  ошибке ограничиваются задержками; неудача не отмечается как успешный бэкап
  и не запускает удаление старых копий. Сейчас ошибка доступна в логах/status;
  доставка в GlitchTip подключается на этапе мониторинга.

Суточное расписание допускает потерю примерно суток изменений при исправных
заданиях; при пропусках интервал может быть больше. При сбое до сегодняшних
17:00 изменения после вчерашнего снимка могут быть потеряны.
Допустимость такой потери и целевое время восстановления подтверждаются
до запуска. Если нужен меньший интервал, график пересматривается отдельно.

### Контроль и восстановление

- Фиксируются время последней подтверждённой внешней копии и результат задания.
- Ошибка запущенного копирования, загрузки или проверки видна в логах/status.
  Событие в GlitchTip — требование следующего этапа. Пропущенный запуск и
  возраст копии автоматически не оповещаются.
- При внедрении копия скачивается из S3 и восстанавливается в отдельную
  временную БД. Проверяются таблицы, миграционная версия и чтение данных.
- Предлагаемая периодичность повторного пробного восстановления — раз в месяц.
- Контейнер умеет безопасно скачать копию (`download`) и проверить SHA-256.
  Восстановление выполняется оператором через `pg_restore` в отдельно
  подготовленную БД/контейнер по инструкции; автоматического restore поверх
  рабочей БД нет. Обычный backup-сервис сам базу не восстанавливает.
- Команды восстановления, необходимые доступы и порядок возврата приложения
  в работу сохраняются в эксплуатационной инструкции.
- Клиентское шифрование дампа сейчас не реализовано: применяются HTTPS
  и приватный бакет. Это не равнозначно шифрованию файла отдельным ключом.
- Проверка никогда не перезаписывает рабочую или существующую локальную БД.
- Секреты и конфигурация, необходимые для восстановления на другом сервере,
  имеют отдельную безопасную резервную копию; одного дампа для них недостаточно.

## 7. Сервер и Docker Compose

Выбрано: обычный Windows-ПК с Hyper-V; внутри — Ubuntu Server
LTS без графического интерфейса, Docker Engine и Docker Compose.
Docker Desktop и WSL в рабочую цепочку не входят.
ПК включается по необходимости; круглосуточная работа не требуется.

- VM получает собственный адрес локальной сети через внешний виртуальный
  коммутатор Hyper-V. Адрес закрепляется, предпочтительно DHCP-резервацией.
- Docker и локальная проверка указаний деплоя работают как службы Ubuntu VM.
- PostgreSQL использует постоянный том в Linux-хранилище Docker.
- Версии PostgreSQL и остальных образов фиксируются. Обновление major-версии
  PostgreSQL выполняется отдельной процедурой, а не обычным деплоем API.
- PostgreSQL не публикуется в интернет; доступ API идёт по внутренней сети.
- Настраиваются healthcheck и перезапуск сервисов при падении процесса.
  Сам по себе unhealthy-статус Docker не считается механизмом перезапуска.
- Для API используется `restart: unless-stopped`. Отдельный watchdog зависаний
  и внешний контроль доступности в первый этап не входят.
- Проверяется запуск Windows → Hyper-V VM → Ubuntu → Docker → сервисов после перезагрузки
  без ручного входа пользователя. Автоматический сон во время обслуживания
  пользователей отключается; плановое выключение ПК допустимо.
- Доступ к API проверяется с реального клиентского компьютера.
- API использует HTTP по закреплённому адресу VM без домена и локального
  Caddy. Доступ ограничивается локальной подсетью. Пароли при входе, токены
  и данные передаются без TLS; это принятый компромисс локального размещения.
  Публикация API в интернет не допускается в рамках этой конфигурации.
- Диагностические проверки различают живой процесс и готовность API
  работать с БД: `GET /health/live` и `GET /health/ready` соответственно.
  Readiness возвращает 503 при недоступной БД; ответы содержат версию и commit SHA.
- Запускается один worker FastAPI согласно контракту обновлений дашборда.
- Один процесс может обслуживать несколько запросов асинхронно. Его выбор
  не означает гарантию безотказности. Два процесса на одной машине не устраняют
  отказ Windows, VM, диска или PostgreSQL; для них потребовалось бы также
  вынести уведомления дашборда из памяти процесса в общий механизм.
- Проверяется корректное завершение Ubuntu VM при выключении хоста.
  Снимки Hyper-V не заменяют резервное копирование PostgreSQL в S3.

Пользователь подбирает Windows-ПК под требования приложения. Характеристики
имеющейся машины не блокируют проектирование. При установке проверяются
поддержка Hyper-V/виртуализации, обновления Windows, ресурсы и автозапуск.

Предлагаемая начальная конфигурация для максимум трёх одновременных пользователей:
2 vCPU, 4 ГБ фиксированной RAM, виртуальный диск 60 ГБ на SSD.
Это инженерная оценка для текущего API, PostgreSQL, backup и локального deploy timer;
фактический объём данных и нагрузка проверяются при вводе в эксплуатацию.
При большом объёме данных/хранимых файлов диск увеличивается отдельно.
Сборка образов и тесты выполняются на GitHub, а не внутри этой VM.
Диск включает запас под ОС, Docker-образы, БД, WAL, временный дамп и обновления;
заполнение диска контролируется. Для увеличивающегося VHDX свободное место
контролируется также на Windows-хосте.
На Windows-ПК желательно 16 ГБ общей RAM, если он используется и как рабочая
станция; реальная конфигурация хоста пока неизвестна. Эти размеры — рекомендации,
а не утверждённые требования к закупке.

## 8. Workflow backend

### Сборка и ручное разрешение

1. PR в `master`: GitHub-hosted runner выполняет тесты с отдельной тестовой БД,
   Ruff для изменённых Python-файлов и проверку сборки. Доступа к production нет.
2. Push в `master`: CI проверяет итоговый коммит и публикует `linux/amd64` образ
   `ghcr.io/boradydev/mountain_fairytale_backend:sha-<полный SHA>`.
3. В ветке `deployment` создаётся `releases/<SHA>.json`: неизменяемый digest,
   версия из `pyproject.toml`, полный SHA, CI run ID, ревизия/контрольные суммы
   миграций. Повтор CI не подменяет существующую запись этого коммита.
4. Оператор запускает **Select production backend** из `master`, вводит
   `commit_sha` (полные 40 символов), выбирает `deploy` или `rollback`.
   Для rollback обязательно подтверждение `compatible_rollback`.
5. Workflow проверяет успешный Backend CI выбранного SHA и принадлежность
   истории `master`; записывает `production.json` в ветку `deployment`.
   `deploymentId` увеличивается при каждом новом указании, включая откат.

Тег `vX.Y.Z` не нужен для backend-деплоя. Поле версии описывает приложение,
а SHA/digest определяют конкретную сборку; `latest` для выбора не используется.
Зелёный workflow подтверждает запись указания, **а не установку на VM**.
Обратная отправка фактического результата в GitHub сейчас не реализована.

### Получение указания и применение на VM

На VM локально установлены проверенные скрипты `scripts/deploy/` и systemd-службы.
Timer начинает проверку через 90 секунд после загрузки, затем через 60 секунд
после завершения предыдущей проверки (`AccuracySec=5s`). Это не строгий SLA
установки за минуту: учитываются длительность проверки, загрузки и доступность сети.
Через `git ls-remote` определяется актуальный коммит `deployment`; JSON читается
по неизменяемому SHA, чтобы не зависеть от кеша raw-файла по имени ветки.
На VM нет GitHub-токена, runner, webhook, VPN или входящего доступа из GitHub.
В JSON находятся данные; shell-команды и deploy-скрипты из него не выполняются.

Применение сериализуется локальной блокировкой. Для нового целевого образа:

1. Проверить ID, разрешённый registry/repository, digest и обязательные поля.
2. Скачать образ и сверить его версию, полный SHA и миграции с каталогом выпуска.
3. Убедиться, что уже применённые миграции не удалены и не переписаны.
4. Создать `.deploy/maintenance` и остановить **только API**.
5. Получить подтверждённый S3-бэкап категории `predeploy`.
6. Для `deploy` выполнить отдельным контейнером `alembic upgrade head` новым
   образом; для совместимого `rollback` миграции не выполнять.
7. Заменить только `API_IMAGE` в серверном `.env`, сохранив прочие параметры
   и права файла. Пересоздать API и проверить readiness, версию и полный SHA.
8. Сохранить успешный выпуск/историю последних 20 успешных образов и снять
   маркер обслуживания. Повтор успешно обработанного ID не повторяет деплой.

Указание на уже установленный образ фиксируется без повторного обслуживания.
PostgreSQL, его том и постоянно работающий backup обычный deploy не пересоздаёт.
Небольшой перерыв API — штатная часть этой схемы. Zero-downtime не реализуется.
Во время выключения VM указание остаётся на GitHub; при запуске применяется
последнее, без обязательной установки каждого промежуточного выпуска.

### Ошибки и ограничения отката

- Ошибка получения/проверки образа до обслуживания не останавливает текущий API.
- Неудачный бэкап блокирует миграции; до их начала прежний API возвращается.
- После начала миграции ошибка или прерывание не приводят к автоматическому
  downgrade/restore. API остаётся остановлен, сохраняется maintenance-состояние.
  То же ограничение действует при неуспешном запуске нового API после миграции.
- Неудачный ID не повторяется каждую минуту. До миграции после исправления
  причины можно разрешить новый ID. После миграции/прерывания требуется
  проверка БД и осознанное восстановление/продолжение (`--recover` по инструкции).
- `rollback` допускается на ранее успешно установленный на этой VM образ,
  присутствующий в локальной истории, при совпадении ревизии и всех контрольных
  сумм миграций с текущим образом/БД. Перед откатом также выполняется бэкап.
- Совпадение схемы не доказывает совместимость логики с данными: её подтверждает
  оператор. При различной схеме нужен отдельный план восстановления или fix-forward.

### Конфигурация и обслуживание

Рабочий каталог VM — `/opt/mountain-fairytale`. `.env` содержит серверные
параметры и S3-секреты; файл имеет права 0600. Compose передаёт каждому контейнеру
только необходимые ему переменные.
Статус `.deploy/state.json` доступен root; журнал — в systemd/Docker.
Изменение ENV требует пересоздания соответствующего контейнера, а не только
его перезапуска. Смена пароля роли PostgreSQL требует отдельного изменения
самой роли: редактирование `POSTGRES_PASSWORD` не меняет существующую БД.

Доставка через файл обновляет только API-образ. Compose, systemd, скрипт
деплоя, ENV, PostgreSQL major и backup-образ обслуживаются отдельно.
Необходимые новые переменные/инфраструктурные изменения подготавливаются
до разрешения API-выпуска. Сборки и тесты на production не выполняются,
тома и рабочие данные обычным деплоем не удаляются.

Команды выпуска, диагностики и восстановления: [backend-deploy.md](../operations/backend-deploy.md).

## 9. Workflow Flutter и обновление Windows-приложения

### Проверка, подготовка и публикация

Реализованы два workflow в репозитории `boradydev/mountain_fairytale`:

- **Flutter Windows CI** (`flutter-build.yml`): PR/push в `master` и push тега
  `v*`. Зафиксированы Flutter 3.47.4 и Windows x64. Устанавливаются зависимости
  по lockfile, выполняются анализ, автономные Flutter-тесты, тесты release-скриптов,
  сборка приложения и per-user установщика. Анализ блокирует ошибки;
  существующие warning/info видны, но не блокируют pipeline.
- **Publish Flutter release** (`flutter-publish.yml`): только ручной запуск
  на `master` с `version_tag`, без пересборки готового установщика.

Для PR/master результат — Actions-артефакт `windows-preview-<run_number>`
с `MountainFairytale-X.Y.Z-windows-x64-Setup.exe`. Это проверочный установщик,
не публичный подписанный выпуск; он сам не появляется в GitHub Releases.

Подготовка выпуска:

1. В PR изменить `version` в `pubspec.yaml` и описание `release-notes.md`.
2. После merge выбрать коммит из истории `master` и отправить тег `vX.Y.Z`,
   точно совпадающий с публичной частью версии. Расхождение блокирует сборку.
3. CI по тегу повторяет проверки, включает публичный ключ, собирает установщик,
   подписывает его Ed25519, проверяет пару ключей и создаёт `appcast.xml`,
   `update.json`, `SHA256SUMS`. Артефакт — `windows-release-vX.Y.Z`.
4. Дождаться успешного CI тега, затем вручную запустить **Publish Flutter release**.
   Publisher проверяет тег/commit, успешную сборку, набор файлов, SHA-256,
   подпись, метаданные и увеличение публичной версии относительно latest.
5. Создаётся draft, в него загружается весь комплект; только после этого
   релиз становится публичным `latest`. Приложение не видит неполный выпуск.

Тег и merge сами не публикуют обновление. Actions-артефакты хранятся 30 дней.
Истёкший артефакт требует нового выпуска с новой версией; опубликованные
номера/теги не подменяются. При прерванной публикации остаётся draft: оператор
проверяет причину и удаляет незавершённый draft перед повтором, не перезаписывая
публичный релиз. Обычные клиенты используют только latest, без тестовых каналов.

Постоянные HTTPS-адреса:

```text
https://github.com/boradydev/mountain_fairytale/releases/latest/download/appcast.xml
https://github.com/boradydev/mountain_fairytale/releases/latest/download/update.json
```

GitHub Releases хранит установщик и feed. Backend не раздаёт их и не участвует
в обновлении клиента. Самостоятельный сервер доставки и клиентский GitHub-токен
не нужны, пока репозиторий и файлы выпуска публичные.

### Ключи, установщик и сохранение данных

- Используются WinSparkle 0.9.2 через C++/MethodChannel-мост и Inno Setup 6.7.3.
  SDK/компилятор загружаются с закреплёнными версиями и SHA-256.
  Callback-и WinSparkle передаются в главный поток Windows сообщениями окна.
- `UPDATE_PRIVATE_KEY` хранится в GitHub Actions Secrets; владелец создаёт ключ
  локальным скриптом и хранит отдельную резервную копию. В приложение входит
  только `UPDATE_PUBLIC_KEY` из Actions Variables. Переиздавать ключ для каждого
  релиза нельзя: установленные клиенты доверяют прежнему публичному ключу.
- `API_BASE_URL` — Actions Variable с адресом локального API; это параметр
  сборки, сейчас `http://192.168.0.25:8000`. Клиентского экрана смены адреса
  в рамках этой задачи нет. Все три настройки обязательны для выпуска по тегу.
- WinSparkle проверяет подпись скачанного файла до запуска установщика.
  Ошибка подписи запрещает установку. Это не Authenticode-подпись Windows;
  отсутствие предупреждений SmartScreen не обещается.
- Установка для текущего пользователя: `%LOCALAPPDATA%\Programs\MountainFairytale`,
  стабильный AppId, без UAC. В комплекте app-local VC++ runtime и WinSparkle DLL.
- Имя exe, CompanyName/ProductName в Runner.rc и хранилища токенов/preferences
  сохранены. Обновление не вызывает logout и не удаляет пользовательский профиль;
  uninstall также не очищает настройки и токены.
- Первый Setup.exe устанавливается вручную. При переходе с ZIP нужно закрыть
  старую копию и использовать новый ярлык; старый ZIP сам не обновляется.

### Поведение интерфейса и установки

1. После первого кадра, затем раз в четыре часа пассивно читается `update.json`.
   При новой версии появляется отметка на значке, без окна установки.
2. Кнопка в верхней панели основного экрана/входа, также при недоступном API,
   позволяет проверить обновления и посмотреть версию/описание.
3. Пока открыт редактор или модальная форма, обновление не запускается.
   Пользователь закрывает/сохраняет работу и может выбрать «Позже».
4. После подтверждения приложение блокирует редактирование на всё время
   нативного updater, включая загрузку. Продолжение работы во время загрузки
   в этой реализации не предусмотрено; отмена/закрытие WinSparkle снимает блокировку.
5. WinSparkle скачивает и проверяет установщик. После подтверждения установки
   приложение закрывается. При потере защитного модального состояния закрытие
   не выполняется; установщик отказывается менять файлы работающего приложения.
6. Установщик ждёт завершения процесса, показывает прогресс, обновляет файлы
   и запускает новую версию. Принудительного завершения приложения нет.

Сбой проверки/сети не блокирует вход и работу. До первого выпуска 404 feed —
нормальное состояние. Отмена/ошибка загрузки не запускает установку.
Dart не заменяет работающий exe. Проверка цифровой подписи защищает пакет;
после начала установки ошибки диска/ОС требуют диагностики и повторной установки.

Для локальной приёмки только debug-сборка допускает отдельный loopback HTTP-feed
и временный ключ. В Profile/Release принимается только штатный HTTPS appcast.
Тестовые файлы/ключи не публикуются как latest; сервер после проверки остановлен.

### Совместимость с API

Обновление добровольное, поэтому backend сохраняет совместимость с предыдущими
поддерживаемыми клиентами. Перед несовместимым изменением нужен отдельный план
перехода. Принудительные обновления, endpoint минимальной версии и поэтапные
каналы распространения в текущую реализацию не входят.

Полная инструкция: [Flutter Windows](https://github.com/boradydev/mountain_fairytale/blob/master/docs/windows-updates.md).

## 10. Версионирование backend и Flutter

### Старт и правила повышения

Задуманный функционал реализован; первый полноценный выпуск backend и Flutter
получает версию `1.0.0`. Backend этой версии уже установлен в VM;
первый подписанный Flutter v1.0.0 опубликован. Дальнейшие версии
проходят тот же tag CI и ручную публикацию.

Обе части используют `MAJOR.MINOR.PATCH` и выпускаются независимо:

| Часть номера | Когда повышается | Пример |
| --- | --- | --- |
| PATCH | Исправление ошибки без несовместимого изменения контракта | `1.0.0 → 1.0.1` |
| MINOR | Новая возможность с сохранением совместимости | `1.0.1 → 1.1.0` |
| MAJOR | Несовместимое изменение API либо существенное несовместимое изменение требований к клиенту/окружению | `1.1.0 → 2.0.0` |

При повышении MINOR обнуляется PATCH, при повышении MAJOR — MINOR и PATCH.
Изменение привычного поведения при исправлении бага само по себе не требует
MAJOR, если поддерживаемый контракт остаётся совместимым.

Например, исправление серверного расчёта выпускается как backend `1.0.1`,
а Flutter может остаться `1.0.0`. Совпадение номеров двух частей не требуется.

### Источники версии и теги

| Часть | Источник номера | Первый выпуск | Тег |
| --- | --- | --- | --- |
| Backend | `[tool.poetry].version` в `pyproject.toml` | `1.0.0` | Для доставки не нужен; выбор по полному SHA/digest |
| Flutter | `version` в `pubspec.yaml` | `1.0.0+1` как исходная запись | `v1.0.0` в репозитории Flutter |

- Версия меняется в PR и попадает в `master`. Владелец выбирает публичный
  SemVer по характеру изменения; номер CI не выбирает её автоматически.
- Backend CI публикует образ каждого успешного коммита `master`; установка
  выбирается по SHA/digest. Дополнительный git-тег может отмечать выпуск,
  но workflow не требует его и не проверяет соответствие тега версии.
- Технические backend-сборки могут иметь одинаковую версию приложения,
  различаясь SHA/digest. Содержимое существующей записи SHA не подменяется.
- Для Flutter тег `vX.Y.Z` обязателен и должен совпадать с `pubspec.yaml`.
  Часть после `+` заменяется на `github.run_number` workflow Flutter Windows CI.
  Номер не сбрасывается при смене версии и не требует ручного увеличения.
- Компоненты Windows-версии и build ограничены 65535; превышение блокирует
  выпуск без обнуления счётчика. Перед заменой/переименованием workflow нужно
  отдельно обеспечить сохранение возрастающей последовательности сборок.
- `1.0.0+42` соответствует тегу `v1.0.0`. WinSparkle сравнивает
  `MAJOR.MINOR.PATCH.BUILD`; интерфейс показывает версию и номер сборки.
- Публичные версии Flutter растут; исправление опубликованной версии получает
  новый PATCH. Артефакты, опубликованные теги и установщики не подменяются.
- Версия, полный commit SHA и миграции backend доступны в каталоге и health;
  `update.json` Flutter сохраняет версию, build и commit подготовленного выпуска.

### Совместимость и диагностика

Совместимость определяется контрактом API, а не равенством номеров.
Например, Flutter `1.2.0` может работать с backend `1.4.3`.
Поскольку обновление клиента добровольное, несовместимый backend требует
отдельного плана перехода; повышение MAJOR само по себе не разрешает
сломать установленные поддерживаемые клиенты.

Установленная версия и commit SHA backend доступны в технической диагностике;
версия и номер сборки Flutter — в информации о приложении.
После подключения GlitchTip события должны содержать версию части и окружение.

## 11. Статус этапов и оставшаяся приёмка

Распределение работ и порядок ввода: [план внедрения](operations-implementation-plan.md).
Отчёты и инструкции содержат детали проверок; исторические результаты не
являются непрерывным мониторингом текущего состояния VM или GitHub.

| Этап | Сделано | Осталось |
| --- | --- | --- |
| 1. Compose | API/PG запущены в Ubuntu VM; health, тома, ротация логов, один worker | Проверка полного Windows → VM → сервисы на выбранном рабочем ПК и реальных клиентских ПК |
| 2. Бэкапы | Публичный отдельный образ, расписание/catch-up/ротация, реальный Timeweb и изолированное восстановление 15 таблиц | Проверка копии уже рабочей БД, периодические restore-пробы; GlitchTip после этапа 3 |
| 3. Мониторинг | Архитектура и границы согласованы | VPS/домен, Compose/Caddy/GlitchTip, SDK, события backup и пороги дисков; этап отложен |
| 4. Доставка backend | GHCR, каталог/указание, timer, S3-бэкап, миграции, readiness и совместимый rollback проверены | Обычная эксплуатация по инструкции; обратный статус в GitHub не реализован и не требуется для первого ввода |
| 5. Flutter updater | Установщик без UAC, подпись/проверки, переход A → B подтверждён; подписанный v1.0.0 опубликован | Проверка обновления с публичного feed и сохранения профиля на рабочих ПК |
| 6. Рабочий ввод | Инструкции backend/backup/Flutter подготовлены | Выбрать рабочие ПК, пройти бизнес-сценарии, при необходимости отдельно спланировать перенос данных и проверить рабочий backup |

Владелец 22 октября подтвердил успешное обновление до `1.0.0+1`.
Сохранение токенов/темы/геометрии, обрыв нативной загрузки и переход со старой
пользовательской ZIP-копии отдельно проверяются в финальной приёмке на рабочих
ПК. Автоматические проверки и сохранённая идентичность хранилищ её дополняют.

Проверки отказов выполняются в тестовом окружении; рабочая БД не служит
площадкой для разрушительных тестов. Обычные деплои не сбрасывают данные.

## 12. Оставшиеся решения и работы

1. **Рабочая инфраструктура:** владелец выбирает Windows-ПК, закрепляет адрес
   VM и проверяет автозапуск/завершение Hyper-V. Установка Ubuntu и доступ
   к VM уже выполнены; WSL не входит в production-схему.
2. **Рабочие клиенты:** первая ручная установка опубликованного Flutter v1.0.0
   и проверка дальнейшего обновления с реального GitHub feed на рабочих ПК.
3. **Мониторинг:** VPS/домен, срок хранения событий, backup самого GlitchTip,
   пороги/интервалы дисков VM, Windows-тома VHDX и VPS. Уведомления владелец
   настраивает отдельно; Telegram не выбран и не проверен.
4. **Восстановление:** согласовать целевое время и приемлемость потери изменений
   после последней копии, периодичность restore-проб и отдельное резервирование
   секретов/конфигурации. Расписание, count-retention и категории уже выбраны;
   клиентское шифрование дампов сейчас отсутствует.
5. **Рабочие данные:** источник и процедура переноса, если перенос понадобится,
   определяются отдельно до запуска. Проверить бэкап после появления реальных данных.

Принятые решения повторно не открываются без причины: один worker, локальный
HTTP, отсутствие uptime/heartbeat, основной `master`, публичные образы,
pull-деплой без runner, добровольный WinSparkle updater и ENV-конфигурация.
Kubernetes, zero-downtime, автоматический downgrade/restore, принудительные
клиентские обновления и отдельный сервер раздачи установщиков не входят в объём.
