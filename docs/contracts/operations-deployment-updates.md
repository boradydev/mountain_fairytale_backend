# Эксплуатация, мониторинг, резервное копирование и обновления

Статус: проект контракта для совместного review перед реализацией.
Дата: 21 октября 2026 года.
Область: FastAPI backend, PostgreSQL, Flutter Windows, GitHub Actions,
GitHub Releases, Timeweb S3, Sentry.

Документ фиксирует согласованное направление. Он не означает, что описанные
механизмы уже реализованы. Изменения workflow и кода выполняются отдельными
задачами после review. Пункты раздела «Открытые решения» требуют уточнения;
остальные требования служат базой для реализации.

## 1. Цель и границы

Сделать эксплуатацию приложения простой и предсказуемой:

- видеть ошибки backend и Flutter в одном сервисе;
- восстанавливать базу из внешнего резервного хранилища;
- выпускать backend через GitHub Actions;
- обновлять Windows-приложение по кнопке без ручной распаковки ZIP;
- сохранять понятный путь восстановления после неудачного обновления.

Стартовая конфигурация рассчитана на один сервер и один процесс FastAPI.
Kubernetes, кластер PostgreSQL, собственная установка Sentry, отдельный стек
сбора логов и аналитика пользовательского поведения в первый этап не входят.

Бизнес-журнал действий сохраняет существующее назначение и хранение в БД.
Техническая диагностика не заменяет этот журнал.

## 2. Целевая архитектура

| Компонент | Решение | Назначение |
| --- | --- | --- |
| Развёртывание | Docker Compose | Управление сервисами одного сервера |
| Backend | Контейнер FastAPI, один worker | API и существующие уведомления дашборда |
| База | Контейнер PostgreSQL с постоянным томом | Рабочие данные |
| Резервное копирование | Отдельный контейнер с расписанием | Создание дампов и загрузка в S3 |
| Внешнее хранение | Приватный бакет Timeweb S3 | Резервные копии |
| Ошибки | Облачный Sentry, два проекта | Backend и Flutter Windows |
| Обычные серверные логи | Python logging → stdout/stderr → Docker | Локальная диагностика с ротацией |
| Сборка backend | GitHub Actions → GHCR | Версионированные Docker-образы |
| Деплой | Self-hosted runner на сервере в WSL | Обновление Compose из доверенного workflow |
| Выпуски Flutter | GitHub Actions → GitHub Releases | Установщик и описание обновления |
| Обновление Flutter | auto_updater / WinSparkle — кандидат | Проверка, загрузка и запуск установщика |
| HTTPS | Caddy при необходимости доменного доступа | Входящие подключения к API |

Пакет обновления Flutter считается выбранным окончательно только после
проверки полного цикла на двух тестовых версиях. Остальная архитектура
не зависит от конкретного пакета.

### Потоки данных

```text
Flutter Windows ── API ──> FastAPI ──> PostgreSQL
       │                     │            │
       └── ошибки ──> Sentry <─┘            └── pg_dump ──> backup ──> Timeweb S3

GitHub Actions ──> GHCR ──> deploy runner ──> Docker Compose
GitHub Actions ──> GitHub Releases ──> updater во Flutter
```

Backend не раздаёт установщики Flutter и не проксирует их скачивание.
Сервис обновления клиента не зависит от работоспособности API.

## 3. Текущее состояние, обнаруженное при планировании

- В backend есть стандартное Python-логирование и обработчики исключений.
- Миграции базы выполняются через Alembic.
- Контракт `docs/contracts/dashboard-updates.md` требует одного процесса
  backend: состояние уведомлений хранится в его памяти.
- В локальном backend пока нет Dockerfile, Compose и GitHub Actions workflow.
- Flutter ориентирован прежде всего на Windows Desktop.
- В локальном `pubspec.yaml` указана версия `1.0.0+1`.
- `.github/workflows/flutter-build.yml` собирает Windows-приложение,
  упаковывает его в ZIP и публикует GitHub Release.
- Workflow Flutter запускается для `push` и `pull_request` в ветку `deploy`.
  Шаг публикации релиза не имеет отдельного ограничения по событию.
- Тег релиза формируется как `v0.1.<github.run_number>` независимо от версии
  приложения. Комментарии workflow упоминают `main`, хотя триггер — `deploy`.
- На момент проверки репозиторий `boradydev/mountain_fairytale` публичный.

Это снимок на дату документа. Перед реализацией состояние сверяется повторно.

## 4. Backend: логи и Sentry

### Локальные логи

- Существующий Python logging остаётся основой логирования.
- Приложение пишет в stdout/stderr. Docker ограничивает размер и число
  файлов логов; диск не должен заполняться бесконечным выводом.
- Диагностика включает время, уровень, источник сообщения, окружение,
  версию backend и идентификатор запроса, когда он применим.
- Неожиданное исключение записывается со стеком вызовов.
- Клиент не получает внутренний traceback или секреты в ответе API.

### Отправка ошибок

- Используется отдельный проект Sentry для backend.
- В событиях указываются версия выпуска и окружение.
- Неожиданные ошибки, в том числе перехваченные общим обработчиком,
  должны попадать в Sentry без дублирования одного исключения.
- Ожидаемые бизнес-ошибки и обычные отказы авторизации не создают поток аварий.
- Для расследования ошибки API используется общий идентификатор запроса,
  доступный серверной диагностике и клиенту. Точное имя заголовка и способ
  передачи фиксируются при реализации в API-контракте.
- Сбой Sentry не должен нарушать обработку запросов.

На старте приоритет — сбор ошибок. Полная трассировка всех запросов и
профилирование не обязательны. Logfire остаётся возможным следующим шагом,
если появится конкретная потребность в подробном анализе задержек.

## 5. Flutter: диагностика

- Используется отдельный проект Sentry для Flutter через `sentry_flutter`.
- Перехватываются необработанные Dart/Flutter-ошибки.
- Неожиданные ошибки, которые приложение уже перехватило, отправляются явно
  в точке обработки: например, сбой печати или формирования документа.
- Ожидаемые ошибки валидации, неверный пароль, отмена пользователем и
  обработанная временная недоступность сети не считаются авариями автоматически.
- Событие содержит версию приложения, окружение, экран/операцию и при
  необходимости технический ID пользователя и идентификатор API-запроса.
- Одна ошибка не должна отправляться повторно на каждом слое приложения.
- Недоступность Sentry не блокирует запуск и работу приложения.

Firebase Analytics и Crashlytics в стартовое решение для Windows не входят.
Аналитика использования рассматривается отдельной задачей, если она понадобится.

### Данные и секреты

В обоих проектах Sentry исключаются пароли, access/refresh tokens,
заголовки авторизации, телефоны, адреса и содержимое документов. Проверяются
также URL/query-параметры, сообщения исключений и breadcrumbs.
Автоматические скриншоты и запись сессий не включаются на первом этапе.

Секреты не коммитятся и не выводятся в workflow. Серверные параметры остаются
в серверном окружении, CI-секреты — в GitHub Secrets. Клиентская конфигурация
Sentry не должна содержать административные токены.

Уведомления настраиваются для новых и значимых повторяющихся ошибок.
Канал доставки и пороги определяются до ввода в эксплуатацию.

## 6. PostgreSQL: резервное копирование

### Создание и хранение

- Отдельный контейнер подключается к PostgreSQL по внутренней сети Compose.
- Создаётся логический дамп `pg_dump` в custom-формате для `pg_restore`.
- Версия клиента pg_dump согласуется с версией сервера PostgreSQL.
- Рабочая база не останавливается для обычного резервного копирования.
- Сначала успешно создаётся локальный временный файл, затем он загружается
  в приватный бакет Timeweb S3 по HTTPS.
- Каждая копия имеет уникальное имя с окружением и временем UTC.
- После загрузки проверяются наличие объекта, размер и контрольная сумма
  доступным для выбранного S3-клиента способом. ETag не считается универсальным
  эквивалентом контрольной суммы файла.
- Временные файлы очищаются после подтверждения загрузки; их объём ограничен.
  При ошибке загрузки предусматриваются повторы без бесконечного заполнения диска.
- Для S3 используются отдельные учётные данные с необходимыми правами
  на бакет резервных копий. Доступ к бакету не передаётся Flutter.
- Нужные для восстановления роли, расширения и параметры PostgreSQL
  описываются отдельно: дамп одной базы не является копией всего кластера.

Копирование файлов работающего Docker volume не заменяет штатный бэкап БД.
Бэкап обязан работать по локальному расписанию независимо от GitHub Actions.

### Базовое расписание и срок хранения

| Тип | Расписание | Хранение |
| --- | --- | --- |
| Часовая копия | Каждый час в рабочее время | Последние 48 часов |
| Ежедневная копия | Один раз в сутки | 30 дней |
| Перед миграцией | Перед изменением схемы рабочей БД | Предлагается 30 дней; уточнить при review |

Рабочие часы, часовой пояс расписания и точное время ежедневной копии
фиксируются перед внедрением. Время в именах объектов всегда UTC.
Удаление просроченных копий выполняется по явным правилам; одна неудачная
загрузка не должна приводить к удалению последней пригодной копии.

Часовое расписание допускает потерю примерно часа изменений в рабочее время
при исправных заданиях. Вне рабочего времени и при сбоях интервал может быть
больше. Допустимый объём потери данных и время восстановления согласуются
до запуска. Если нужен меньший интервал потери, отдельно рассматриваются
WAL-архивирование и восстановление на момент времени.

### Контроль и восстановление

- Фиксируются время последней подтверждённой внешней копии и результат задания.
- Ошибка копирования и отсутствие свежих копий вызывают уведомление.
  Контроль пропущенных заданий должен обнаруживать также остановку самого
  контейнера/сервера; одного сообщения из успешно работающего backup недостаточно.
- При внедрении копия скачивается из S3 и восстанавливается в отдельную
  временную БД. Проверяются таблицы, миграционная версия и чтение данных.
- Предлагаемая периодичность повторного пробного восстановления — раз в месяц.
- Команды восстановления, необходимые доступы и порядок возврата приложения
  в работу сохраняются в эксплуатационной инструкции.
- Проверка никогда не перезаписывает рабочую или существующую локальную БД.
- Секреты и конфигурация, необходимые для восстановления на другом сервере,
  имеют отдельную безопасную резервную копию; одного дампа для них недостаточно.

## 7. Сервер и Docker Compose

Исходное условие: backend работает на Windows через WSL2 в Linux-контейнерах.
Если выбор ОС свободен, предпочтителен отдельный Ubuntu-сервер; переход на него
не должен требовать изменения архитектуры приложения.

- PostgreSQL использует постоянный том в Linux-хранилище Docker.
- Версии PostgreSQL и остальных образов фиксируются. Обновление major-версии
  PostgreSQL выполняется отдельной процедурой, а не обычным деплоем API.
- PostgreSQL не публикуется в интернет; доступ API идёт по внутренней сети.
- Настраиваются healthcheck и перезапуск сервисов при падении процесса.
  Сам по себе unhealthy-статус Docker не считается механизмом перезапуска.
- Проверяется запуск Windows → WSL → Docker → сервисов после перезагрузки
  без ручного входа пользователя. Сон сервера отключается.
- Доступ к API проверяется с реального клиентского компьютера.
- При доменном доступе используется HTTPS; при локальной работе отдельно
  фиксируются адресация, доступ и способ защиты соединения.
- Диагностические проверки различают живой процесс и готовность API
  работать с БД. Точные маршруты фиксируются при реализации.
- Запускается один worker FastAPI согласно контракту обновлений дашборда.

Редакция Windows, её обновления безопасности, вариант установки Docker и
способ автозапуска уточняются до настройки сервера.

## 8. Workflow backend

### Разделение проверки и выпуска

Проверка PR выполняется на GitHub-hosted runner: проверки качества,
тесты и проверка сборки по требованиям проекта. CI-тесты используют отдельную
тестовую БД; рабочая БД недоступна тестам.

После успешных проверок доверенного выпуска образ собирается на GitHub,
публикуется в GHCR и развёртывается self-hosted runner на сервере в WSL.
Runner сам устанавливает исходящее соединение с GitHub.

- Ветка/тег выпуска и автоматический либо ручной запуск — открытое решение.
- Деплой разрешён только из доверенных refs и событий.
- Self-hosted runner не исполняет код внешних PR. Доступ к Docker фактически
  даёт управление сервером, поэтому изоляция deploy-задания обязательна.
- Секреты production недоступны проверочным заданиям PR.
- Права `GITHUB_TOKEN` выдаются по заданиям в необходимом объёме.
- Одновременно выполняется не более одного деплоя одного окружения.
  Начавшаяся миграция не отменяется новым запуском workflow.
- Сервер получает готовый образ; исходный код не собирается на production.
- Образ идентифицируется неизменяемым digest/commit SHA. Понятный тег версии
  может добавляться дополнительно. Единственный тег `latest` недостаточен.

### Последовательность деплоя

1. Проверить доступность сервера, БД, образа и необходимых настроек.
2. Скачать целевой образ и сохранить идентификатор предыдущего выпуска.
3. Перед миграциями получить подтверждённую резервную копию в S3.
4. Один раз отдельным заданием выполнить `alembic upgrade head` новым образом.
5. При успехе обновить контейнер API, сохранив том PostgreSQL.
6. Дождаться готовности API и выполнить короткую проверку работы с БД.
7. Зафиксировать установленную версию и результат выпуска.

Миграции не запускаются одновременно в каждом worker/экземпляре API.
Рутинный деплой не удаляет тома, не сбрасывает базу и не запускает тесты
против production. Если миграции требуют отсутствия записей, применяется
заранее описанное окно обслуживания; один бэкап блокировку записей не заменяет.

### Ошибки и откат

- Неудачный бэкап блокирует миграцию и дальнейший выпуск.
- Неудачная миграция останавливает выпуск и вызывает уведомление.
  Возможность продолжать работу старого API оценивается по состоянию схемы.
- При неготовности нового API предыдущий образ можно вернуть только при
  совместимости с текущей схемой БД.
- Автоматические downgrade миграций и восстановление production из дампа
  при ошибке деплоя не выполняются: они могут уничтожить новые записи.
- Для штатных изменений используется совместимая последовательность:
  сначала добавление схемы, затем переход кода, удаление старого — позже.
- Допускается короткий перерыв при обновлении одного экземпляра API.
  Обновление без простоя не входит в первый этап.

## 9. Workflow Flutter и обновление Windows-приложения

### Проверка и публикация

- PR запускает проверки и Windows-сборку без публикации релиза.
- Публикация разрешена только для согласованного доверенного события выпуска.
- Версия задаётся в одном месте и согласованно передаётся в Flutter,
  Windows-ресурсы, установщик, GitHub Release и описание обновления.
- Версии растут монотонно, сравниваются как версии, а не как строки.
- Номер запуска CI может быть номером сборки, но не создаёт независимую
  от приложения версию релиза.
- Сборка использует зафиксированную версию Flutter SDK.
- Workflow создаёт установщик `Setup.exe`, подпись обновления и `appcast.xml`.
  ZIP при необходимости остаётся дополнительным артефактом.
- Сначала публикуется полностью готовый установщик, затем становится
  доступно описание обновления. Клиент не видит незавершённый выпуск.
- Выпуски доступны напрямую в GitHub Releases по HTTPS.
- `appcast.xml` доступен по постоянному URL; точный способ публикации
  выбирается при реализации. Ссылка должна переживать смену версии релиза.
- Тестовые/pre-release выпуски не предлагаются обычным пользователям.
- Устраняются расхождения комментариев workflow с фактическими триггерами.

### Проверка подлинности и установка

- Пакет проверяется механизмом подписи выбранного updater до установки.
- Приватный ключ подписи хранится в GitHub Secrets и имеет безопасную
  резервную копию. В приложение включается только публичный ключ.
- Подпись updater не равнозначна Windows Authenticode. Подписание установщика
  сертификатом Windows рассматривается отдельно; нельзя обещать отсутствие
  предупреждений SmartScreen только за счёт подписи обновления.
- Установка ориентирована на текущего пользователя, без повышения прав
  при штатном обновлении. Это подтверждается на целевой Windows.
- Настройки, токены и пользовательские файлы хранятся отдельно от каталога
  установленной программы и сохраняются при обновлении.
- Работающий exe не заменяется вручную из Dart: замену выполняет установщик
  после завершения приложения.
- В приложение не включается GitHub-токен. Если репозиторий станет приватным,
  схема доставки пересматривается отдельно.

### Поведение интерфейса

1. Приложение проверяет обновления при запуске без блокировки основной работы.
2. Пользователь также может вручную нажать «Проверить обновления».
3. При новой версии показываются номер, краткое описание и кнопка «Обновить».
4. После нажатия виден прогресс загрузки; пользователь продолжает работу,
   пока это безопасно для выбранного механизма установки.
5. Перед закрытием проверяются несохранённые изменения и активные операции.
   Пользователь может сохранить работу или отложить установку.
6. После подтверждения приложение закрывается, установщик обновляет файлы
   и запускает новую версию.

Сетевая ошибка, отсутствие релиза или ошибка подписи не повреждают текущую
установку. При ошибке подписи установка запрещена. Неудачная проверка
обновлений не блокирует вход и работу приложения.

Первый установщик с поддержкой обновлений ставится вручную один раз.
Переход с существующей ZIP-версии проверяется отдельно, включая сохранение
настроек и отсутствие двух случайно используемых копий приложения.

### Совместимость с API

Пользователь может отложить обновление Flutter, поэтому новый backend
сохраняет совместимость с предыдущими поддерживаемыми клиентами.
Конкретный диапазон поддержки фиксируется перед несовместимыми изменениями.
Endpoint минимальной версии клиента, принудительные обновления и каналы
поэтапного распространения в первый этап не входят.

## 10. Этапы и критерии готовности

| Этап | Результат | Проверка готовности |
| --- | --- | --- |
| 1. Compose | API и PostgreSQL работают на сервере | Запуск после перезагрузки без ручного входа; доступ с клиентского ПК; данные переживают пересоздание API |
| 2. Бэкапы | Копии уходят в Timeweb S3 по расписанию | Скачивание и восстановление в отдельную БД; чтение данных; уведомление о сбое/пропуске |
| 3. Sentry | Ошибки обеих частей доступны в одном сервисе | Контрольные ошибки со стеком и версией; нет дублей и чувствительных данных; работа при недоступном Sentry |
| 4. Деплой backend | Доверенный выпуск обновляет API через Actions | Успешная миграция; проверка готовности; остановка при ошибке; проверенный возврат совместимого образа |
| 5. Flutter updater | Приложение обновляется по кнопке | Установка версии A и обновление до B; сохранение настроек; отказ при неверной подписи; обработка обрыва загрузки и несохранённой формы |

Для каждого этапа изменения кода/workflow и эксплуатационная инструкция
должны быть доступны для review. Проверки сбоев выполняются в тестовом
окружении. Рабочие данные не используются как площадка для аварийных тестов.

## 11. Открытые решения перед реализацией

1. **Сервер:** остаётся ли Windows 10 + WSL обязательным условием; редакция ОС,
   обновления безопасности, Docker Desktop или Docker Engine внутри WSL,
   ресурсы машины и способ автозапуска.
2. **Доступ:** API нужен только в локальной сети или извне; домен, HTTPS
   и адрес сервера для Flutter.
3. **Выпуск backend:** ветка/тег, событие запуска и необходимость ручного
   запуска/подтверждения production. Автоматический вариант остаётся допустимым.
4. **Выпуск Flutter:** сохранить ветку `deploy` или выпускать по тегам;
   источник версии, постоянный URL appcast и политика тестовых выпусков.
5. **Бэкапы:** рабочие часы, часовой пояс, допустимая потеря данных,
   целевое время восстановления, хранение предмиграционных копий,
   необходимость шифрования самих файлов дампов и хранение ключа.
6. **Оповещения:** канал, получатель, пороги Sentry и допустимый возраст копии;
   способ обнаруживать пропуск задания при остановке сервера.
7. **Updater:** подтвердить auto_updater/WinSparkle на двух тестовых сборках,
   формат установщика и требования целевых компьютеров.
8. **Доступы:** Sentry-проекты, GHCR, регистрация deploy runner, отдельные
   S3-ключи и резервное хранение ключей подписи/восстановления.

Эти пункты не требуют немедленной реализации всех возможных механизмов.
При review выбирается минимальный вариант, удовлетворяющий рабочим условиям.
