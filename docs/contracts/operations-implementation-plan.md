## 0. Подготовка инфраструктуры — можно параллельно с этапом 1

### Ты

- Подготовить Windows-ПК с поддержкой Hyper-V и виртуализацией.
- Создать Ubuntu Server VM: стартовый ориентир 2 vCPU, 4 ГБ RAM,
  диск 60 ГБ на SSD. Установить Ubuntu Server без графического интерфейса.
- Подключить VM к локальной сети, закрепить её адрес, обеспечить вход
  для администрирования. Проверить доступ с рабочего Windows-ПК.
- Создать VPS с Ubuntu Server: рекомендованный старт 1–2 vCPU,
  2 ГБ RAM и 30 ГБ SSD; VPS выделен под мониторинг.
- Выбрать домен/поддомен мониторинга и направить DNS на VPS.
- В Timeweb создать приватный бакет резервных копий и отдельный доступ к нему.
- Сохранить серверные пароли, SSH-ключи и S3-ключи в безопасном месте.

### Я

- Подготовить пошаговые инструкции установки Docker Engine/Compose,
  автозапуска VM и служб, сетевых правил и первого запуска.
- Подготовить перечень серверных переменных и GitHub Secrets с назначением
  каждого параметра, без реальных значений в репозитории.
- Проверить совместимость версий компонентов при реализации и зафиксировать
  выбранные версии в конфигурациях.

### Готовность

Есть доступная в локальной сети Ubuntu VM, доступный для администрирования
VPS, домен мониторинга и приватный S3-бакет. Платный VPS не обязателен для
начала написания кода этапа 1. Docker можно установить по моей инструкции
после подготовки самих серверов; не нужно заранее собирать Compose вручную.

Для настройки понадобятся адрес VM, разрешённая локальная подсеть,
адрес/домен VPS и endpoint/имя S3-бакета. Секретные значения вводятся
непосредственно в серверное окружение или GitHub Secrets, а не в контракт.

## 1. Упаковка backend и первый запуск в VM

**Я:** Dockerfile и Compose для API/PostgreSQL, шаблон окружения, один worker,
постоянный том, проверки готовности, ротация логов, версия/commit SHA,
отдельный запуск миграций и инструкция первичной установки. Подготавливаю
автоматические CI-проверки/сборку для `master`; ручной deploy добавляется
на этапе 4.

**Ты:** установить Docker по инструкции, заполнить окружение, запустить стек
в VM, задать рабочий адрес API во Flutter. Проверить запуск после выключения
и повторного включения Windows-ПК. До переноса данных — только тестовые записи.

**Готовность:** вход и основные операции доступны с клиентского ПК; данные
переживают пересоздание API и перезапуск VM; PostgreSQL не открыт в интернет;
обычное выключение ПК не считается аварией.

## 2. Резервные копии и восстановление

**Я:** контейнер backup, S3-загрузка и проверка результата, расписание
17:00 Europe/Moscow, одна догоняющая копия после пропуска, постоянное состояние
расписания, хранение последних 30 успешных ежедневных копий, защита от
параллельных заданий, копия перед миграцией и инструкция восстановления.
Ошибки пока доступны в локальных логах; доставка в GlitchTip подключается
на этапе 3. Никаких алертов только из-за выключенного ПК.

**Ты:** заполнить S3-параметры на сервере; по инструкции выполнить первый
бэкап и пробное восстановление в отдельную временную БД.

**Готовность:** копия скачана из S3, восстановлена, данные прочитаны;
проверены ротация и сценарий «ПК был выключен в 17:00» без дублей.
Проверки не удаляют рабочие копии и не перезаписывают существующую БД.

## 3. GlitchTip и диагностика обеих частей

**Я:** отдельный Compose для VPS: Caddy, GlitchTip, его PostgreSQL;
инструкции HTTPS, обновления и резервного копирования мониторинга.
Подключаю Sentry SDK в backend и Flutter, исключение чувствительных данных,
версии/окружения и отправку ошибок backup. Подготавливаю проверки свободного
места VM, Windows-тома с VHDX и VPS с отправкой событий в operations.
Внешний контроль доступности API и heartbeat не добавляются.

**Ты:** запустить подготовленный Compose на VPS, создать администратора
GlitchTip и проекты backend/flutter/operations, заполнить DSN.
Установить подготовленную проверку диска Windows по инструкции.
При желании настроить дальнейшую доставку уведомлений; Telegram проверяется
отдельно и не блокирует приём событий в GlitchTip.

**Готовность:** контрольные ошибки из Flutter, backend и backup видны
в правильных проектах, со стеком/версией и без секретов. Проверена доставка
события о пороге диска без фактического заполнения диска. При отсутствии
интернета приложение работает; выключение локального ПК не создаёт алертов.

## 4. Ручной production-деплой backend через GitHub

**Я:** завершаю workflow: готовый образ в GHCR, идентификация по digest/SHA,
проверка версии/тега, ручной выбор проверенной сборки, сериализация деплоев,
предмиграционный бэкап, миграции, проверка готовности и инструкция возврата
совместимого выпуска. Готовлю инструкцию установки runner как службы Ubuntu.

**Ты:** зарегистрировать runner в VM, заполнить необходимые GitHub Secrets
и права чтения образов, выполнить первый ручной деплой кнопкой в Actions.
VM в этот момент должна быть включена и иметь доступ в интернет.

**Готовность:** выбранный проверенный образ устанавливается без пересборки;
неудачные проверки/бэкап/миграция не допускают продолжения выпуска;
на тестовом окружении проверен возврат совместимого образа без отката данных.

## 5. Установщик и обновления Flutter

**Я:** проверяю updater на двух сборках, добавляю установщик, проверку подписи,
кнопки проверки/обновления, защиту несохранённых изменений, единый номер версии,
возрастающий build number, appcast и workflow: CI → тег → ручная публикация.
Настраиваю публикацию описания обновления по постоянному HTTPS-адресу.

**Ты:** по инструкции создать ключ подписи в своей среде, сохранить приватную
часть в GitHub Secrets и отдельную безопасную резервную копию. Проверить
тестовый установщик на обычной учётной записи Windows, затем обновление
между двумя тестовыми версиями. Первый установщик поставить вручную.

**Готовность:** версия A обновляется до B по кнопке; настройки и токены
сохраняются; неверная подпись блокирует установку; обрыв загрузки не портит
рабочее приложение. Тестовые сборки не публикуются как production-обновления.

## 6. Первый рабочий выпуск и передача в эксплуатацию

**Я:** свожу инструкции запуска, бэкапа, восстановления, обновления и
диагностики; проверяю версии `1.0.0`, соответствие контракту и список
необходимых настроек. Если нужны исходные рабочие данные, готовлю конкретную
процедуру переноса после определения их источника.

**Ты:** выбрать момент первого рабочего запуска, проверить реальные сценарии
на клиентских ПК, при необходимости перенести рабочие данные по инструкции,
запустить ручной выпуск backend и публикацию Flutter `1.0.0`, установить
приложение пользователям. Проверить бэкап уже рабочей базы.

**Готовность:** до трёх пользователей работают с локальным API; есть проверенная
копия рабочей БД в S3, доступ к диагностике и понятная процедура восстановления.
Перенос существующих рабочих данных не подразумевается автоматически:
его источник и порядок уточняются до первого рабочего запуска.
