«Разработчик» — агент, готовящий код, конфигурацию, проверки и инструкции.

## 0. Инфраструктура

**Готово владельцем:** Hyper-V + Ubuntu Server VM, локальный доступ
`192.168.0.25`, SSH; приватный холодный бакет Timeweb и отдельный S3-пользователь.
Серверные секреты введены в окружение VM, ключи обновлений Flutter настроены
в GitHub и сохранены владельцем отдельно.

**Готово разработчиком:** Docker Engine/Compose и systemd-службы локального
стека; инструкции, шаблоны окружения, проверки готовности и доставки.
Рабочий каталог — `/opt/mountain-fairytale`.

**Осталось владельцу:** выбрать рабочий Windows-ПК, закрепить адрес VM,
проверить автозапуск и корректное завершение VM при выключении Windows.
Ориентир для VM — 2 vCPU, 4 ГБ RAM, SSD-диск 60 ГБ; это оценка, не измеренные
минимальные требования. GlitchTip размещается на этой же VM отдельным Compose-проектом;
ресурсы общего стека и запас диска уточняются при внедрении. VPS не покупается.
У владельца есть статический публичный IP, доменное имя и Keenetic с WireGuard/SSTP.

- Сериализация операций, временный дамп, проверка размера/SHA-256 и manifest.

- Реальная копия Timeweb скачана и восстановлена в отдельный PostgreSQL 17;

**Осталось:** после появления рабочих данных проверить их копию и чтение

и периодические restore-пробы. Отдельно резервировать секреты/конфигурацию.
Шифрования файла дампа отдельным клиентским ключом сейчас нет.

Сервис скачивает/проверяет дамп; `pg_restore` запускается оператором в отдельно
подготовленную БД. Автоматического восстановления поверх production нет.
Ошибки видны в логах/status; GlitchTip — этап 3. Возраст копии и выключенный ПК
не порождают алерты. Инструкция: [backups.md](../operations/backups.md).

Автозапуск включён и перезапуск unit проверен. Ещё нужны сохранение владельцем

Инструкция и точные границы проверки: [monitoring.md](../operations/monitoring.md).

**Разработчик:** подготовить отдельный Compose-проект GlitchTip и его PostgreSQL
в той же Ubuntu VM, с постоянными томами и автозапуском. Доступ — HTTP/8080

Сохраняются текущие 2 vCPU, 4 ГБ RAM и диск 60 ГБ; расширение — по фактической нагрузке.

Подготовить создание администратора и проектов backend/flutter/operations,
настроить хранение событий 30 дней и проверить очистку. Настроить ежедневный
backup БД в отдельный S3-префикс, хранить 3 последние успешные копии. Прежние
удалять только после проверки новой. Конфигурацию/секреты/версию образа сохранять
защищённо вне ПК после изменений; используемые файлы включить в восстановление.
Подготовить инструкцию установки, обновления и восстановления отдельно GlitchTip.

**Владелец:** задать и сохранить административные доступы, проверить вход
в дашборд; организовать еженедельный экспорт всей VM отдельно от дампов БД.
Контрольные точки остаются инструментом текущей разработки и отключаются у клиента.
Первый этап использует только дашборд, Telegram/почта настраиваются отдельно.

**Приёмка 3А:** дашборд доступен по LAN и VPN, посторонний источник блокируется;

проектов, DSN и настроек. API работает при остановленном GlitchTip.

### 3Б. SDK и эксплуатационные события

**Выполнено 25 октября:** Python SDK 2.73.0, Flutter SDK 10.2.0, публичный
`GET /public/monitoring/config`, корреляция `X-Request-ID`, фильтрация личных
данных/секретов и ограничение дублей. Проверены настоящие события Python/Flutter
в GlitchTip, тип/стек/версия, исключение приватного маркера, прекращение отправки
после смены сервера. Проверка диска/состояний обоих backup включена systemd timer,
готовый backup-образ не изменён. Warning/critical/recovery и подавление повторов
проверены на изолированных входных состояниях без поломки рабочей БД/диска.
Docker backend и Windows release собираются. API-контейнер на VM не заменялся:
активация нового кода — после commit/PR/CI и выбора выпуска владельцем,
затем обычное обновление Flutter. [Инструкция](../operations/monitoring.md#этап-3б-sdk-и-эксплуатационные-события).

**Дополнено 26 октября:** на VM включены четыре info-события в `operations`:
`api_started`, `api_deployed`, `backup_succeeded`, `api_deploy_failed`.
Host observer проверяет последнее состояние раз в 5 минут, подавляет повторы;
начальное состояние принимается без отправки истории. Четыре тестовых события
проверены в реальном GlitchTip. [Поведение и ограничения](../operations/monitoring.md#информационные-события).

**Осталось:** приёмка после выпусков и следующего ребута Ubuntu; после полной
настройки сформировать свежий recovery bundle и один раз загрузить зашифрованно
в приватный S3, ключ сохранить отдельно. Это подтверждённая отложенная мини-задача.

**Разработчик:** подключить совместимые Sentry SDK в Python/FastAPI и Flutter.
Backend выдаёт Flutter конфигурацию мониторинга (включённость, публичный ключ,
проект, порт). Flutter берёт адрес машины из выбранного URL API и отправляет
события напрямую в GlitchTip на порт мониторинга; FastAPI их не пересылает.
При смене сервера конфигурация обновляется, отправка в прежний проект прекращается.
Получение конфигурации не блокирует приложение; до её получения доставка
не гарантируется. DSN backend/operations задаются в серверном `.env` и передаются
только нужным сервисам. Административные секреты клиентам не выдаются.

Подключить явные события ошибок backup и контроль только диска Ubuntu VM:
интервал 5 минут, warning при свободном месте меньше 20%, critical — меньше 10%.
Повторные события ограничиваются, восстановление фиксируется.
Windows-диск/VHDX автоматически не проверяется, скрипты на Windows не устанавливаются.
При заполнении физического диска возможна остановка VM без события в GlitchTip;
это принятое ограничение, о полной недоступности сообщает пользователь.

Исключить секреты/персональные данные, добавить версию и окружение, исключить
дублирование через handlers/logging/SDK. Ожидаемые бизнес-ошибки и обычная
недоступность API не должны создавать поток аварийных событий. Обычный stdout
остаётся в Docker с ротацией; трассировка, профилирование, запись сессий и
централизованный поиск всех текстовых логов в объём не входят.

**Приёмка 3Б:** контрольные события backend/Flutter/backup видны со стеком и версией
без секретов и дублей. Flutter проверен по LAN и VPN, при смене сервера и отказе
получения конфигурации. Отказ GlitchTip не останавливает API/Flutter; интернет/VPN
не нужны для локального приёма. Пороги диска проверены без реального заполнения.
Своя дисковая очередь и гарантия досылки всех событий не вводятся; возможны потери
при недоступном приёмнике или аварии VM. Выключенный ПК, heartbeat и отсутствие
внешнего uptime-контроля не порождают алерты.

## 4. Ручное разрешение backend-деплоя — реализовано

**Выполнено:** публичный GHCR, каталог `deployment/releases/<SHA>.json`,
**Select production backend** с полным SHA и записью `production.json`.
VM забирает указание локальным Python-скриптом по systemd timer: первый запуск
через 90 секунд, последующие через 60 секунд после окончания проверки.
Self-hosted runner, webhook и GitHub-токен на VM не используются.
VPN поддержки не участвует в доставке backend и не требуется для неё.

**Проверено:** установка точного образа без сборки в VM, остановка только API,
преддеплойный S3-backup, миграции, readiness/версия/commit, сохранение ENV и
контейнеров PostgreSQL/backup. Проверены повтор ID, последнее указание после
недоступности VM и совместимый rollback. История — 20 успешных образов.

**Штатная работа владельца:** дождаться CI итогового master-коммита, выбрать
его SHA кнопкой. Для rollback выбрать ранее установленный совместимый образ
и подтвердить совместимость. При разных миграциях обычный rollback запрещён;
автоматического downgrade/restore БД нет. После прерывания/ошибки миграции
требуется ручная проверка maintenance-состояния по инструкции.

Успех workflow означает запись указания. Фактический результат — на VM и
`/health/ready`; обратной отправки результата в GitHub сейчас нет.
Тег backend для доставки не нужен. Изменения Compose/systemd/ENV, major PG
и backup-образа обслуживаются отдельно от API-образа.
Инструкция: [backend-deploy.md](../operations/backend-deploy.md).

## 5. Установщик и обновления Flutter — первый выпуск опубликован

Сборка использует Flutter 3.47.4, версию из `pubspec.yaml` и build number
`github.run_number`. Публичный ключ/адрес API — Variables, приватный ключ — Secret.

**Проверено:** 260 Flutter-тестов (4 пропуска), release-скрипты, Windows-сборка
и Setup.exe в GitHub CI PR. Локальная установка A → B без администратора,
подпись и отказ после изменения файла. Владелец подтвердил обновление через
интерфейс `0.9.9` → `1.0.0+1`. Временный debug-feed остановлен; HTTP-исключение
не входит в Profile/Release. PR объединён в master.

**Первый выпуск:** подписанная сборка по тегу и ручная публикация v1.0.0
состоялись; владелец подтвердил успех, релиз доступен в GitHub Releases.
Для будущих версий сохраняется порядок: изменить pubspec/release-notes → PR/master
→ тег vX.Y.Z → успешный tag CI → Publish Flutter release по кнопке.

**Осталось владельцу:** на рабочих ПК поставить первый установщик вручную;
проверить сохранение авторизации/темы/окна при переходе с прежней ZIP-копии
и дальнейшее обновление с публичного GitHub feed. Отдельно проверить
отмену/обрыв нативной загрузки.

PR/master установщики находятся в Actions Artifacts (`windows-preview-<run_number>`),
а не в Releases. Срок хранения артефактов — 30 дней. Создание тега само не
публикует релиз. Истёкший артефакт требует нового выпуска с новой версией.
Опубликованный v1.0.0 включает установщик и feed; старые ZIP-релизы
не заменяют новый канал обновлений. Владелец не меняет ключ подписи при каждом новом выпуске.

Инструкция: [Flutter Windows](https://github.com/boradydev/mountain_fairytale/blob/master/docs/windows-updates.md).
