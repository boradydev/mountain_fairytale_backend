# План эксплуатации: выполненные этапы и оставшиеся работы

Актуализирован: 23 октября 2026 года по фактической реализации.
Основание: [контракт эксплуатации и обновлений](operations-deployment-updates.md).

«Разработчик» — агент, готовящий код, конфигурацию, проверки и инструкции.
«Владелец» — пользователь, управляющий инфраструктурой, аккаунтами, секретами
и ручным разрешением выпусков. SSH-доступ к Ubuntu VM предоставлен; первый
запуск, настройка backup и доставка backend выполнены через этот доступ.
Автозапуск Hyper-V/поведение Windows-хоста остаются ответственностью владельца.

## 0. Инфраструктура

**Готово владельцем:** Hyper-V + Ubuntu Server VM, локальный доступ
`192.168.0.25`, SSH; приватный холодный бакет Timeweb и отдельный S3-пользователь.
Серверные секреты введены в окружение VM, ключи обновлений Flutter настроены
в GitHub и сохранены владельцем отдельно.

**Готово разработчиком:** Docker Engine/Compose и systemd-службы локального
стека; инструкции, шаблоны окружения, проверки готовности и доставки.
Рабочий каталог — `/opt/mountain-fairytale`.

**Осталось владельцу:** выбрать рабочий Windows-ПК, закрепить адрес VM,
проверить автозапуск и корректное завершение VM при выключении Windows.
Ориентир для VM — 2 vCPU, 4 ГБ RAM, SSD-диск 60 ГБ; это оценка, не измеренные
минимальные требования. VPS под GlitchTip — рекомендуемый старт 1–2 vCPU,
2 ГБ RAM, 25–30 ГБ SSD; тариф/домен ещё предстоит выбрать.

## 1. Упаковка backend и первый запуск — реализовано

**Выполнено:** Dockerfile и Compose для API/PostgreSQL 17, один Uvicorn worker,
постоянный том, health endpoints, ротация логов Docker, `restart: unless-stopped`,
версия/commit SHA, отдельный контейнер миграции и автоматический CI на master.
API доступен локально по HTTP, PostgreSQL не публикует порт на хост.

**Осталось владельцу:** на выбранных рабочих ПК проверить вход, основные
операции и цепочку Windows → Hyper-V → Docker → приложение после перезагрузки.
Обычное выключение ПК допустимо и не создаёт сигналов аварии.

Исторический отчёт: [stage1-validation.md](../operations/stage1-validation.md).

## 2. Резервные копии и восстановление — реализовано

**Выполнено:** самостоятельный проект
[`postgres_s3_backup`](https://github.com/boradydev/postgres_s3_backup), публичный
образ 0.1.0 с закреплённым digest в backend Compose. Контейнер постоянно
работает с внутренним планировщиком; ежедневный запуск не зависит от GitHub.

- Расписание 17:00 `Europe/Moscow`; одна догоняющая копия после пропуска,
  сохранённое состояние расписания, без воспроизведения каждого пропущенного дня.
- Независимые ENV-лимиты: daily/manual/predeploy — по умолчанию 30/30/30.
  Ротация только после создания, загрузки и проверки новой копии.
- Сериализация операций, временный дамп, проверка размера/SHA-256 и manifest.
- Преддеплойный backup обязателен и включён в доставку backend.
- Реальная копия Timeweb скачана и восстановлена в отдельный PostgreSQL 17;
  версия Alembic и числа строк 15 таблиц совпали. Тестовый контейнер удалён.

**Осталось:** после появления рабочих данных проверить их копию и чтение
после изолированного восстановления; согласовать целевое время восстановления
и периодические restore-пробы. Отдельно резервировать секреты/конфигурацию.
Шифрования файла дампа отдельным клиентским ключом сейчас нет.

Сервис скачивает/проверяет дамп; `pg_restore` запускается оператором в отдельно
подготовленную БД. Автоматического восстановления поверх production нет.
Ошибки видны в логах/status; GlitchTip — этап 3. Возраст копии и выключенный ПК
не порождают алерты. Инструкция: [backups.md](../operations/backups.md).

## 3. GlitchTip и диагностика — отложено

**Владелец:** подготовить Ubuntu VPS, домен/DNS и доступ; после настройки
создать администратора и проекты backend/flutter/operations, ввести DSN.
Дальнейшую доставку уведомлений, включая возможный Telegram, настраивать отдельно.

**Разработчик:** подготовить Compose с GlitchTip, его PostgreSQL и Caddy;
подключить Sentry SDK в backend/Flutter и явную отправку ошибок backup.
Исключить секреты/персональные данные, добавить версию и окружение, исключить
дублирование ошибок. Подготовить контроль свободного места VM, Windows-тома
VHDX и VPS; согласовать пороги и интервалы. Описать backup/обновление самого
мониторинга. Точные зависимости и версии проверяются перед внедрением.

**Приёмка:** контрольные события видны со стеком и версией, без секретов;
сбой интернета/GlitchTip не блокирует приложение, проверен порог диска без
реального заполнения. Уведомлений за выключенный ПК, heartbeat и внешнего
uptime-контроля не будет. Централизованный поиск всех текстовых логов не входит
в текущий объём; основной предмет GlitchTip — ошибки и согласованные алерты.

## 4. Ручное разрешение backend-деплоя — реализовано

**Выполнено:** публичный GHCR, каталог `deployment/releases/<SHA>.json`,
**Select production backend** с полным SHA и записью `production.json`.
VM забирает указание локальным Python-скриптом по systemd timer: первый запуск
через 90 секунд, последующие через 60 секунд после окончания проверки.
Self-hosted runner, webhook, VPN и GitHub-токен на VM не используются.

**Проверено:** установка точного образа без сборки в VM, остановка только API,
преддеплойный S3-backup, миграции, readiness/версия/commit, сохранение ENV и
контейнеров PostgreSQL/backup. Проверены повтор ID, последнее указание после
недоступности VM и совместимый rollback. История — 20 успешных образов.

**Штатная работа владельца:** дождаться CI итогового master-коммита, выбрать
его SHA кнопкой. Для rollback выбрать ранее установленный совместимый образ
и подтвердить совместимость. При разных миграциях обычный rollback запрещён;
автоматического downgrade/restore БД нет. После прерывания/ошибки миграции
требуется ручная проверка maintenance-состояния по инструкции.

Успех workflow означает запись указания. Фактический результат — на VM и
`/health/ready`; обратной отправки результата в GitHub сейчас нет.
Тег backend для доставки не нужен. Изменения Compose/systemd/ENV, major PG
и backup-образа обслуживаются отдельно от API-образа.
Инструкция: [backend-deploy.md](../operations/backend-deploy.md).

## 5. Установщик и обновления Flutter — первый выпуск опубликован

**Выполнено:** WinSparkle 0.9.2 через Windows-мост, Ed25519, per-user Inno Setup,
защита открытых форм и модальная блокировка работы на время updater,
пассивная проверка при запуске/раз в четыре часа и ручная кнопка.
Сборка использует Flutter 3.47.4, версию из `pubspec.yaml` и build number
`github.run_number`. Публичный ключ/адрес API — Variables, приватный ключ — Secret.

**Проверено:** 260 Flutter-тестов (4 пропуска), release-скрипты, Windows-сборка
и Setup.exe в GitHub CI PR. Локальная установка A → B без администратора,
подпись и отказ после изменения файла. Владелец подтвердил обновление через
интерфейс `0.9.9` → `1.0.0+1`. Временный debug-feed остановлен; HTTP-исключение
не входит в Profile/Release. PR объединён в master.

**Первый выпуск:** подписанная сборка по тегу и ручная публикация v1.0.0
состоялись; владелец подтвердил успех, релиз доступен в GitHub Releases.
Для будущих версий сохраняется порядок: изменить pubspec/release-notes → PR/master
→ тег vX.Y.Z → успешный tag CI → Publish Flutter release по кнопке.

**Осталось владельцу:** на рабочих ПК поставить первый установщик вручную;
проверить сохранение авторизации/темы/окна при переходе с прежней ZIP-копии
и дальнейшее обновление с публичного GitHub feed. Отдельно проверить
отмену/обрыв нативной загрузки.

PR/master установщики находятся в Actions Artifacts (`windows-preview-<run_number>`),
а не в Releases. Срок хранения артефактов — 30 дней. Создание тега само не
публикует релиз. Истёкший артефакт требует нового выпуска с новой версией.
Опубликованный v1.0.0 включает установщик и feed; старые ZIP-релизы
не заменяют новый канал обновлений. Владелец не меняет ключ подписи при каждом новом выпуске.

Инструкция: [Flutter Windows](https://github.com/boradydev/mountain_fairytale/blob/master/docs/windows-updates.md).

## 6. Первый рабочий запуск и эксплуатация — остаётся

**Разработчик:** поддерживать согласованность контракта и инструкций,
поддерживать последующие выпуски Flutter, подготовить этап мониторинга.
Если нужны исходные данные, сначала определить источник и отдельную процедуру
переноса; автоматический перенос существующих данных не подразумевается.

**Владелец:** выбрать рабочие ПК и время ввода, проверить реальные сценарии
до трёх пользователей, автозапуск/сеть, установить клиент, проверить рабочую
копию БД и доступ к инструкции восстановления. Хранить доступы и резервные
ключи под собственным управлением; production-выпуски разрешать вручную.

**Критерий рабочего ввода:** пользователи работают с локальным API, данные
сохраняются после перезапуска, внешний backup пригоден для восстановления,
порядок обновления/диагностики понятен. GlitchTip остаётся отдельным этапом;
до него диагностика доступна локально, без обещания централизованных алертов.
