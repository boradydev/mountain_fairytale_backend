# Backend: GitHub → файл версии → Ubuntu VM

GlitchTip временно отложен. Репозиторий и backend-образ публичные;
на VM нет self-hosted runner, GitHub-токена, входящего webhook или нового порта.

## Сборка и разрешение установки

1. PR в `master`: тесты, Ruff для изменённых Python-файлов, сборка без публикации.
2. Push в `master`: те же проверки, затем публикация `linux/amd64` образа
   `ghcr.io/boradydev/mountain_fairytale_backend:sha-<полный SHA коммита>`.
3. В ветке `deployment` автоматически появляется `releases/<SHA>.json`:
   digest, версия из `pyproject.toml`, commit SHA, CI run ID и контрольные суммы
   миграций. Повторный CI не заменяет уже опубликованный выпуск этого коммита.
4. Для установки открыть Actions → **Select production backend** → **Run workflow**.
   Ветка запуска — `master`; вставить полный SHA успешной сборки, выбрать `deploy`.
5. Workflow проверит успешный master Backend CI и обновит `deployment/production.json`.
   `deploymentId` увеличивается при каждом новом указании, включая откат/повтор.

Зелёный Select workflow означает **разрешение установки**, а не подтверждение
установки на VM. Обычный push в master не изменяет `production.json`.
Версия приложения не обязана меняться для каждой технической сборки; конкретная
сборка всегда определяется SHA/digest, а не изменяемым `latest`.

При первой публикации GitHub создаёт пакет приватным. В GitHub Packages открыть
`mountain_fairytale_backend` → Package settings → Change visibility → Public.
После этого скачивание на VM не требует авторизации. Секреты .env/backup.env
не передаются в сборку, каталог выпусков или файл production.json.

## Что делает VM

Штатный `mountain-fairytale-deploy.timer` запускает проверку через 90 секунд
после старта, затем через 60 секунд после окончания предыдущей проверки.
Используются локально установленные Python-скрипты, Python 3.12+ и Git;
дополнительные Python-пакеты не нужны. Сначала через `git ls-remote` определяется
актуальный коммит ветки deployment, затем JSON читается по неизменяемому SHA.
Это исключает кеширование файла по имени ветки и не расходует GitHub API quota.
Публичный production.json содержит только данные; shell-команды и скрипты из
ветки deployment не скачиваются и не выполняются.

Порядок применения нового задания:

1. Проверить ID, разрешённое имя registry/repository и неизменяемый digest.
2. Скачать образ, сверить его версию, commit SHA и фактические миграции.
3. Убедиться, что уже применённые миграции не переписаны и не удалены.
4. Поставить локальный маркер обслуживания и остановить только API.
5. Сделать подтверждённый S3-бэкап категории `predeploy`.
6. Для обычного deploy выполнить `alembic upgrade head` из выбранного образа.
7. Записать новый `API_IMAGE` в серверный .env, сохраняя остальные настройки.
8. Пересоздать API; проверить readiness, версию и полный commit SHA.
9. Сохранить успешный выпуск и историю последних 20 успешных образов;
   удалить маркер обслуживания.

PostgreSQL, его том и планировщик backup обычный деплой не пересоздаёт.
Compose/systemd и сам скрипт деплоя обновляются отдельно администратором,
а production.json управляет только backend-образом. Конфигурационные изменения
новой версии проверяются до разрешения её установки.

Если ПК выключен, запрос останется на GitHub; после включения VM увидит
последнее указание. Несколько указаний за время простоя не создают очередь
обязательных промежуточных установок. Миграции выбранного выпуска должны
поддерживать обновление с реально установленной схемы.

## Откат

Открыть тот же workflow, указать SHA ранее успешно установленной на этой VM
сборки, выбрать `rollback` и подтвердить совместимость поведения/данных.
Workflow создаст новый ID, хотя версия приложения станет старее.

VM разрешает такой откат только если:

- образ есть в локальной истории успешных установок;
- текущая БД соответствует текущему образу;
- целевая ревизия и контрольные суммы миграций полностью совпадают с текущими.

Перед откатом также выполняется S3-бэкап. `alembic downgrade` и восстановление
БД не запускаются. Совпадение схемы — техническое ограничение, а не доказательство
совместимости логики и данных: её подтверждает оператор при выборе rollback.
Смена схемы требует отдельного плана восстановления или исправления вперёд.
Самый первый локальный образ `stage1-local` не входит в GitHub-каталог: обычный
откат кнопкой доступен после двух успешных установок опубликованных образов.

## Ошибки и прерванные операции

- Нет связи с GitHub: действующее приложение работает, проверка повторится позже.
- Образ/проверки до остановки API не прошли: текущий API остаётся работать.
- Бэкап не получился: миграции не запускаются, прежний API запускается обратно.
- Началась миграция, а затем произошла ошибка: автоматического отката БД/образа
  нет; API остаётся остановлен, сохраняется маркер обслуживания.
- Неудачный ID не запускается заново каждую минуту. Для повтора до миграции
  достаточно исправить причину и снова разрешить сборку кнопкой (новый ID).
- Если процесс/ПК оборвался во время обслуживания, сохраняется interrupted;
  требуется проверить БД и осознанно продолжить. systemd основного приложения
  не запускает прежний API при наличии `.deploy/maintenance`.

После ручной проверки прерванной миграции оператор может разрешить новый ID
и выполнить `sudo python3 -m scripts.deploy.pull_deploy --recover` из
`/opt/mountain-fairytale`. Флаг снимает только блокировку обслуживания;
проверки схемы и метаданных не обходятся. Если текущая БД уже не соответствует
старому образу, сначала требуется отдельная процедура восстановления/исправления.

Неудачный контейнер `mf-migration-<ID>` сохраняется для локальной диагностики.
После успешной миграции такой контейнер удаляется. Данные тома не удаляются.

## Установка и диагностика на VM

Передать проверенные `scripts/deploy/{pull_deploy,release_manifest}.py`,
`scripts/deploy/install_pull_deploy.sh` и `deploy/mountain-fairytale*.service/timer`
в `/opt/mountain-fairytale`, сохраняя структуру каталогов. Затем:

```sh
cd /opt/mountain-fairytale
sudo sh scripts/deploy/install_pull_deploy.sh
sudo systemctl list-timers mountain-fairytale-deploy.timer
sudo python3 -m scripts.deploy.pull_deploy --status
sudo journalctl -u mountain-fairytale-deploy.service -n 60 --no-pager
```

Состояние находится в `.deploy/state.json` с доступом только root. Оно не содержит
паролей и S3-ключей. Пока обратная отправка статуса в GitHub не настроена,
результат фактической установки смотрим на VM и через `/health/ready`.

Отключить только автоматическое применение новых указаний:

```sh
sudo systemctl disable --now mountain-fairytale-deploy.timer
```

Это не останавливает уже работающие API/PostgreSQL/backup. Сборка, каталог
выпусков и workflow выбора остаются доступны на GitHub.
