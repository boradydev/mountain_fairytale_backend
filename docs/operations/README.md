# Эксплуатация Mountain Fairytale

Точка входа для владельца, который устанавливает/обслуживает backend
самостоятельно. Команды выполняются на Ubuntu VM, а не в Windows PowerShell,
если инструкция явно не говорит обратного. Production не требует Poetry,
сборки исходников, self-hosted runner или GitHub-токена на VM.

Минимальный комплект восстановления вне Windows-ПК: пригодная S3-копия с
manifest, доступы к бакету, защищённый `.env`, сведения об образе
и схеме БД, проверенная версия Compose/systemd/скриптов. Одного Docker volume
или снимка Hyper-V недостаточно. Дампы и секреты не публикуются в GitHub.

GlitchTip и operations-проверка работают на VM. SDK приложений готовы в коде
и проверены, рабочая активация выполняется обычными выпусками backend/Flutter.
Текущая диагностика приложений доступна в Docker/systemd и health.
Windows/VM могут штатно выключаться; алертов за отсутствие работающего ПК нет.
Обычный deploy не удаляет данные и не обновляет конфигурацию сервера;
GitHub Select workflow подтверждает указание, фактический результат — на VM.

[stage1-validation.md](stage1-validation.md) — исторический отчёт от 22 октября,
не пошаговая инструкция актуального развёртывания. Старый путь через TAR и
`stage1-local` не требуется для установки опубликованных GHCR-образов.

Проверка инструкций 23 октября: на отдельном Docker Desktop-проекте пройдены
новая БД → миграции → опубликованный API, backup в S3-эмулятор → скачивание
с проверкой SHA-256 → restore в изолированный PostgreSQL и в новую БД с другой
ролью. Проверены ревизия/контрольные записи, тестовые ресурсы удалены.
Команды Bash и локальные ссылки проверены отдельно. Полная повторная установка
чистой Hyper-V VM в эту проверку не входила; сетевые правила/systemd на Ubuntu
имеют отдельную историческую проверку, а Windows-автозапуск принимает владелец.
