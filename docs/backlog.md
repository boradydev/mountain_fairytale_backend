## DB-RETRY-01 — тихое восстановление соединений PostgreSQL

**Статус:** идея / не начинать до отдельного согласования.  
**Приоритет:** после релиза, по результатам наблюдения.  
**Контекст:** FastAPI + SQLAlchemy 2 async + asyncpg + PostgreSQL, UOW.

### Зачем

При коротком разрыве подключения к PostgreSQL (перезапуск БД, разрыв TCP,
устаревшее соединение в пуле) по возможности самостоятельно восстановить
подключение и выполнить **безопасную** операцию повторно, чтобы не показывать
пользователю HTTP 500 из-за кратковременной инфраструктурной ошибки.
Если БД действительно недоступна, не скрывать аварию бесконечным ожиданием.

### Что исследовать перед реализацией

1. **Пул SQLAlchemy.** Проверить и при необходимости включить штатный
   `pool_pre_ping=True` при `create_async_engine`; оценить `pool_recycle`
   и текущее управление `AsyncSession`. Сейчас в
   `src/common/infra/db/postgres/database.py` движок создаётся без явно
   заданного `pool_pre_ping`. Эта мера предупреждает выдачу *устаревшего*
   соединения из пула, но **не восстанавливает незавершённую транзакцию**.
2. **Где допустим retry.** Выбрать явную границу **всей операции/транзакции**
   (например, application use case или вызывающий UOW orchestration),
   создавая **новую сессию и новую транзакцию** на каждую попытку. Нельзя
   просто повторять отдельный SQL-запрос внутри потерянной транзакции
   или делать универсальный retry в `UOW.commit()`/HTTP middleware.
3. **Строгое разделение ошибок.** Ограничить повторы временными
   техническими сбоями соединения; транзакционные SQLSTATE
   `40001` (serialization failure) и `40P01` (deadlock) рассматривать
   отдельно и только при доказанной безопасности повтора всей операции.
   Бизнес-ошибки, валидация, ограничения UNIQUE/FK, некорректные
   запросы и ошибки программирования — не кандидаты для retry.
4. **Неопределённый результат COMMIT — критическое исключение.**
   Если соединение потеряно при/сразу после `COMMIT`, неизвестно,
   успела ли БД зафиксировать изменения. **Нельзя слепо повторять
   создание маршрута, самовывоза, начисление комиссии, аудит или иные записи**:
   это может создать дубликаты. Требуются явная идемпотентность
   (стабильный ключ операции/ID, дедупликация или чтение результата
   прежней попытки) либо возврат контролируемой ошибки с возможностью
   безопасной повторной проверки клиентом. Особенно учесть запись событий
   в `IPostgresUOW.commit` до фактического `session.commit`.
5. **Лимиты и наблюдаемость.** Спроектировать короткие ограниченные
   попытки (например 2–3 с малым exponential backoff + jitter) и
   общий latency budget; окончательные значения подобрать по замерам.
   Логировать количество повторов, типы ошибок и длительность с
   request ID; не скрывать сбои от мониторинга и не засорять его
   единичными восстановленными ошибками. При исчерпании попыток
   возвращать понятный контролируемый ответ (возможно HTTP 503 для
   временной недоступности), не обещая отсутствие любых 500.
6. **Выбор реализации.** Сначала оценить, хватает ли штатных средств
   SQLAlchemy и небольшого явного `async`-помощника без новой
   зависимости. Если нужна библиотека: сравнить **Tenacity**
   (гибкая политика, поддержка async и условий) и **Backoff**
   (компактные async-декораторы). Оба инструмента лишь управляют
   *когда повторять*; они не определяют безопасность повторного
   выполнения транзакции. Не добавлять библиотеку автоматически.

### Критерии будущей проверки

- Сбой **до выдачи соединения**: stale pooled connection
  обнаруживается, новое подключение работает, пользователь не видит
  ложную ошибку.
- Сбой **до начала записи** и во время чтения: разрешённая операция
  ограниченно повторяется на новой сессии с правильными данными.
- Сбой **внутри транзакции**: rollback/invalidated session, никаких
  неполных записей и повторов без новой транзакции.
- **Потеря ответа COMMIT**: нет повторного создания документа,
  начисления или дублирования событий при неоднозначном результате.
- Длительная недоступность PostgreSQL: быстрый и понятный отказ после
  исчерпания лимита, без бесконечных повторов и блокировки API.
- Конкурентные запросы, отмена async-задачи, connection pool limits,
  Sentry/логи/метрики — без каскада повторов и роста нагрузки.
