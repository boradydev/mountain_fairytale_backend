# Правила backend-проекта

## Общий подход

- Сохранять существующую архитектуру, именование и стиль проекта.
- Перед изменением изучить соответствующую фичу, её контракт и соседние реализации.
- Делать минимально необходимые изменения; не переносить и не переименовывать посторонние модули.
- Писать простой, явный и типизированный код. Переиспользовать существующие интерфейсы и базовые классы.
- Не добавлять новые архитектурные слои или абстракции без конкретной задачи.
- Не придумывать бизнес-правила. Проверять контракт и реализацию; при существенной неоднозначности уточнять требования.

## Git, pull request и защита master

- Главная ветка — `master`. Она защищена на GitHub; прямой push запрещён, включая аккаунт администратора.
- Изменения, в том числе документацию, готовить в отдельной рабочей ветке и направлять через PR в `master`.
- Порядок: подготовить изменения → проверить diff → создать PR → дождаться успешного CI → проверить итоговый diff → слить PR.
- Обязательная проверка перед слиянием — `checks` из workflow `Backend CI` (GitHub Actions).
  Она включает линтер, тесты и сборку runtime-образа без публикации. `publish` не требуется в PR:
  публикация образа выполняется после успешных проверок при попадании изменений в `master`.
- Ветка PR должна быть актуальна относительно `master`. Если GitHub требует обновления,
  обновить ветку и дождаться повторных проверок. Новые коммиты в открытый PR запускают CI заново.
- Одобрение другого человека не требуется: владелец может сам слить свой PR после успешных проверок.
- Force push и удаление `master` запрещены. Не отключать и не обходить защиту ради доставки изменений.
- Деплой на VM остаётся отдельным ручным выбором версии в Actions; слияние PR само его не запускает.
- Агент может создавать рабочие ветки и менять файлы, но без явного указания пользователя
  не создаёт коммиты, не выполняет push и не сливает PR. Пользователь контролирует diff и фиксацию изменений.

## Структура и зависимости

- Фичи расположены плоско в `src/feat/`; не вкладывать одну фичу в другую.
- `api/` содержит FastAPI routers, request/response schemas и зависимости HTTP-слоя.
- `app/` содержит DTO, use cases и необходимые им контракты, например UOW в `app/abcs/`.
- `domain/` содержит сущности, бизнес-инварианты, доменные исключения, события и контракты репозиториев в `domain/abcs/`.
- `infra/` содержит реализации репозиториев и UOW, фабрики use cases и инфраструктуру конкретной фичи.
- `src/common/` содержит общие компоненты соответствующих слоёв: API, домен, PostgreSQL, сервисы и сборку зависимостей.
- `src/core/` содержит небольшие технические основы и утилиты, например генерацию UUID и общие пути.
- Следовать существующему потоку: router -> use case -> UOW/repository -> PostgreSQL.
- Use case — отдельный класс с зависимостями через конструктор. Сборку зависимостей выполнять через существующие фабрики, `AppContext` и FastAPI dependencies.
- Не обращаться к БД из router и не помещать HTTP-логику в доменные сущности.
- Доменные сущности в текущем проекте также являются SQLAlchemy-моделями; не вводить отдельную копию ORM-моделей без необходимости.
- Суффикс `abcs` и существующие короткие имена модулей допустимы. Не переименовывать их ради другого архитектурного шаблона.

## HTTP API и контракты

- Согласованный публичный контракт хранить в `docs/contracts/`. При изменении поведения синхронизировать документ, router descriptions, schemas и тесты.
- При интеграции Flutter опираться на backend и согласованный контракт, а не на demo JSON или устаревшие модели клиента.
- Использовать `BaseSchema` для JSON-полей в `camelCase` и существующую обёртку `StdResponse` с полезной нагрузкой в `data`.
- Имена query-параметров брать из router; не менять их автоматически на `camelCase`.
- UUID передавать в JSON строкой. Новые идентификаторы создавать существующим генератором `uuid7`, где это принято в фиче.
- Для частичных обновлений использовать существующий `BasePatchSchema`: различать отсутствующее поле и явный `null`, соблюдать ограничения сущности и отклонять пустое тело.
- Сохранять существующие способы авторизации и проверки доступа. Защищённые endpoints размещать под `/protected` через общую сборку routers.
- Доменные ошибки переводить в HTTP-ответы через `APP_EXCEPTION_MAP` и общие handlers; поддерживать описания responses актуальными.
- Проверка дубля, уникальность и правила нормализации определяются контрактом конкретной фичи. Например, совпадение водителя — предупреждение, а госномер автомобиля уникален, включая деактивированные записи.

## Исключения и сообщения об ошибках

- Внутренние исключения приложения наследуются от `BaseAppException` напрямую или через существующий доменный базовый класс. Они описывают причину ошибки и необходимые данные, а не HTTP-ответ или текст интерфейса.
- Исключения с полезной нагрузкой объявлять через `@dataclass`, с явно типизированными полями вместо ручного `__init__`. Для исключений без полей допустим обычный класс.
- `APP_EXCEPTION_MAP` интерпретирует внутреннее исключение для API: задаёт HTTP-статус, обязательный короткий диагностический `detail` на английском языке и при необходимости `extra_fields`. Ответ формируется общим handler, а не самим исключением.
- `extra_fields` — явный фильтр полезной нагрузки: передавать только выбранные публичные поля исключения. Не сериализовать исключение целиком через `__dict__`, `asdict()` или аналогичный механизм. Не передавать секреты и внутренние технические данные.
- Поля полезной нагрузки API именовать в `camelCase`, описывать в контракте и передавать как структурированные данные. Например, `clients: [{clientId, name}]` или `ownerName`.
- Flutter формирует сообщения для конкретных сценариев из структурированных данных. Не определять причину ошибки путём разбора или сравнения текста `detail`.
- Существующее использование `detail` во Flutter как запасного текста сохраняется. Английский диагностический `detail` не является локализованным пользовательским сообщением; наличие полезной нагрузки позволяет Flutter сформировать собственный текст.

## База данных и миграции

- Используется PostgreSQL: асинхронные SQLAlchemy sessions и существующие Repository/UOW.
- Для запросов использовать SQLAlchemy; SQL Registry и SQL-файлы сохранять там, где такой подход уже применяется.
- Согласовывать ограничения SQLAlchemy-моделей с SQL миграций: типы, `NULL`, уникальность, check constraints, индексы и значения по умолчанию.
- Миграции находятся в `src/common/infra/db/postgres/alembic/migrations/versions/`. Каждая содержит `migration.py`, `upgrade.sql` и `downgrade.sql`; SQL загружается через существующий `sql_reader`.
- **Текущий этап разработки: база очищается и создаётся заново из миграций.** Изменения существующей таблицы вносить в её исходную миграцию создания, а не создавать дополнительную миграцию обновления этой таблицы.
- Для новой таблицы создавать новую миграцию. Сохранять корректную цепочку `revision` / `down_revision`; при правке SQL существующей миграции не менять её идентификатор без необходимости.
- Если изменение уже оформлено отдельной миграцией обновления, перенести его в исходную миграцию и убрать ставшую ненужной ревизию, проверив ссылки последующих миграций.
- При изменении исходной миграции согласовать `upgrade.sql` и `downgrade.sql`. Если downgrade уже удаляет таблицу целиком, отдельное удаление её ограничений не требуется.
- Пока база пересоздаётся, не добавлять перенос, очистку или нормализацию старых записей только ради миграции.
- Это правило действует, пока нет базы с данными, которую нужно сохранить. После перехода к такому окружению изменения схемы оформлять новыми миграциями, не переписывая уже применённые.
- Проверять изменённую цепочку миграций на пересоздаваемой тестовой БД. Не очищать рабочую БД автоматически только на основании этого документа.
- В работе приложения сохранять историю бизнес-сущностей: использовать активацию/деактивацию, если она предусмотрена контрактом. Сброс базы на этапе разработки не означает физическое удаление через API.

## Код и проверки

- Python и зависимости определены в `pyproject.toml`; использовать окружение проекта `.venv`.
- Соблюдать настройки Ruff из `pyproject.toml`: Python 3.13, длина строки 120, форматирование и правила импортов.
- Использовать точную типизацию. `Any` и `# type: ignore` применять только при обоснованной необходимости.
- Не менять настройки линтера или типизатора для сокрытия ошибок.
- Не выводить токены, пароли и другую чувствительную информацию в логи или результаты команд.
- После изменений проверить затронутые файлы линтером и просмотреть итоговый diff.

## Тесты

- Использовать pytest и pytest-asyncio; переиспользовать существующие fixtures и `tests/helpers.py`.
- API-тесты находятся в `tests/integration/api/`, тесты репозиториев — в `tests/integration/infra/repos/`.
- Интеграционные тесты используют реальный PostgreSQL. Подготовка тестовой БД в `tests/integration/db_helpers.py` пересоздаёт схему и применяет Alembic migrations.
- При изменении бизнес-поведения добавлять или обновлять тесты значимых сценариев, ошибок и сохранения состояния.
- Ожидания API-тестов брать из согласованного контракта, router, schemas и отображения исключений; не выводить ожидаемое поведение из use cases или репозиториев, которые сами могут содержать ошибку.
- В API-тестах изменять состояние через HTTP. Подготовка через repository/UOW fixtures допустима для данных, которые невозможно создать через публичный API.
- Проверять статус, тело ответа и фактическое состояние после изменения. Для деактивации проверять сохранность записи и возможность повторной активации.
- Не ослаблять проверки ради прохождения тестов. Запускать проверки, соответствующие изменению; расширять их при новых ошибках или рисках.
