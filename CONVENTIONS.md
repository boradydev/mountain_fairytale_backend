# Правила проекта

## Общие правила

- Сохраняй существующую архитектуру и стиль проекта.
- Не вводи новые архитектурные паттерны, если существующие уже решают задачу.
- Не изменяй код, не относящийся к текущей задаче.
- Не угадывай отсутствующие модули, интерфейсы или бизнес-правила — сначала запроси необходимый контекст.
- Предпочитай простой, явный и типизированный код.
- Не добавляй лишние абстракции.

## Архитектура

- Следуй существующей архитектуре и паттернам проекта.
- Используй Repository, UOW и Use Case в соответствии с существующей реализацией.
- Для доступа к БД используй текущий подход проекта: SQLAlchemy или SQL Registry там, где он уже применяется.
- Use Case — отдельный класс с зависимостями через конструктор.
- Используй существующий механизм Dependency Injection FastAPI.
- Не обращайся к БД напрямую, если для этого уже существует Repository/UOW.
- Переиспользуй существующие интерфейсы и базовые классы.

## База данных

- Используется PostgreSQL и асинхронный доступ к БД.
- Следуй существующим правилам миграций и SQL.
- Исторические данные должны сохраняться.
- Бизнес-сущности не удаляются физически, если для них предусмотрена активация/деактивация.

## Код

- Соблюдай настройки Ruff из `pyproject.toml`.
- Предпочитай точную типизацию.
- Используй `Any` и `# type: ignore` только когда это действительно оправдано.
- Не меняй настройки линтеров или типизатора, чтобы скрыть проблему.
- Не усложняй код без необходимости.

## Тесты

- Используй pytest.
- При изменении бизнес-логики добавляй или изменяй соответствующие тесты.
- Переиспользуй существующие фикстуры и тестовые утилиты.
- Не ослабляй существующие тесты ради прохождения тестов.

## Изменения

- Перед изменением изучи существующую реализацию и следуй её паттернам.
- Для нетривиальных задач сначала определи затрагиваемые слои и файлы.
- Делай минимально необходимое изменение.
- После изменений проверь итоговый diff.
